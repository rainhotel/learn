# 跨层系统设计哲学 Projects

## Project Rule

持续演化同一个项目，而不是堆许多互不相关的 Demo。每个版本都必须记录：

- 关键不变量。
- 故障模型与假设。
- 方案和替代方案。
- 正确性测试。
- 性能/可靠性指标。
- 故障注入结果。
- 机制明确不能保证什么。

## Capstone: 高并发预约与库存服务

场景可以是抢票、实验室设备预约、课程名额或限量商品下单。

### Core Invariants

- 可售库存不得小于零。
- 一个幂等请求最多产生一个有效订单。
- 成功订单必须对应一次库存占用。
- 取消或超时订单最终释放库存。
- 同一资源不能被两个用户在重叠时段成功预约。
- 每次状态变化都能通过审计记录解释。

建议优先使用熟悉的 Java；第一版保持单进程、单数据库，不急着拆微服务。

## V0: 可测量的单进程版本

实现：

- 内存库存、预约与订单状态机。
- 最小 HTTP API。
- Request ID、结构化日志和基本指标。
- 可重复的负载生成器。

验证：

- 单线程下不变量成立。
- 绘制并发增加时的吞吐、P50、P95、P99。
- 保存测试环境、请求模型和原始数据。

## V1: 并发正确性

演进：

- 先复现超卖和 Lost Update。
- 分别使用全局锁、按资源锁、CAS/版本号、单所有者队列修复。
- 比较吞吐、竞争、等待和实现复杂度。

验证：

- 高并发下不超卖。
- 能观测锁等待、失败重试和队列长度。
- 能说明最终方案保护的具体不变量。

## V2: 缓存与热点

演进：

- 增加资源详情和库存展示缓存。
- 使用 Cache Aside、随机 TTL、Singleflight。
- 明确库存展示允许的陈旧窗口。
- 增加缓存失效和缓存不可用路径。

验证：

- 复现并修复缓存击穿。
- 对比命中率、数据库负载和 P99。
- 测试缓存全 miss 时后端是否存活。

## V3: 数据库事务与恢复

演进：

- 使用关系数据库持久化库存和订单。
- 用唯一约束、条件更新和事务保护不变量。
- 复现至少一种隔离异常。
- 建立状态审计与崩溃恢复测试。

验证：

- 任意关键步骤终止进程后，重启仍能解释最终状态。
- 数据库约束承担关键不变量的最后防线。
- 隔离级别选择有业务依据。

## V4: 异步任务、Outbox 与幂等消费

演进：

- 异步执行通知、超时释放和审计派生任务。
- 引入 Transactional Outbox。
- 消费者实现业务幂等、退避重试和死信处理。
- 队列设置容量、积压指标和超限策略。

验证：

- 模拟发布失败后最终仍会处理。
- 重复消息不产生重复业务结果。
- 消费者停机后能够追平积压，或明确何时无法追平。

## V5: 多实例、超时、重试与租约

演进：

- 服务扩展到多个实例。
- 写接口支持幂等 Key，并校验请求体冲突。
- 实现端到端 Deadline、指数退避、Jitter 和 Retry Budget。
- 只有确需协调时才使用租约，并加入 Fencing Token。

验证：

- 响应丢失后客户端重试不会产生重复订单。
- 多层调用不会产生乘法重试放大。
- 旧租约持有者不能覆盖新持有者结果。

## V6: 复制与分片模型

可使用模拟器，不要求自行实现生产级数据库。

演进：

- 按资源 Key 分片。
- 模拟热点资源、分片再平衡和只读副本延迟。
- 为读接口定义一致性等级。
- 设计分片迁移和失败恢复流程。

验证：

- 下单后读取订单不会无解释地“消失”。
- 节点增减时迁移量可测。
- 跨分片操作有明确限制、协调或补偿策略。

## V7: 过载保护与高可用

演进：

- 入口限流、优先级和 Admission Control。
- 有界线程池、连接池和消息队列。
- 对慢依赖使用隔舱、熔断和降级。
- 定义 SLI、SLO、RTO 和 RPO。

验证：

- 数倍设计流量下，核心路径仍满足已定义目标或快速拒绝。
- 过载不会变成无限排队和内存耗尽。
- 单个依赖故障不会拖垮全部接口。
- 完成一次可重复 Game Day。

## V8: Final Report

最终报告至少包含：

- 系统上下文图、状态所有权图和故障传播图。
- 不变量、负载模型和容量模型。
- 缓存一致性、事务、消息和重试语义。
- 复制、分片和客户端可观察一致性。
- SLO、RTO、RPO 和恢复步骤。
- 压测与故障注入数据。
- 三个曾被实验推翻的原始判断。
- 当前明确不值得引入的复杂度。
