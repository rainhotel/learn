## Why This Matters

系统课程最容易被学成彼此隔离的知识点：操作系统讲锁和页表，数据库讲事务和索引，后端讲 Redis 和 MQ，分布式系统讲 CAP 和 Raft。

真实工程里，这些内容会在同一条请求路径中同时出现。一次下单可能经历：

> CPU Cache → 线程调度 → Socket 缓冲区 → 负载均衡 → 应用线程池 → Redis → 数据库 Buffer Pool → WAL → 消息队列 → 下游重试。

每一层都可能缓存、排队、重试、复制和失败。只知道组件用法，很难判断问题为什么出现；理解共同哲学后，才能追踪复杂度被转移到了哪里。

## The Ten Questions

学习或设计任何机制时，固定回答：

1. 它解决的是资源问题、正确性问题，还是恢复问题？
2. 必须始终成立的不变量是什么？
3. 状态由谁拥有，谁有权修改？
4. 哪一步是提交点或线性化点？
5. 哪些操作可以并发，哪些必须排序？
6. 系统假设了哪些失败不会发生？
7. 超时之后我们真正知道什么、不知道什么？
8. 过载时请求会排队、拒绝、丢弃还是降级？
9. 性能收益来自哪里，复杂度被转移到了哪里？
10. 哪些指标和实验可以证明设计有效？

## Mastery Path

### 1. 先学会定义问题

- 不变量
- 状态所有权
- 正常路径与失败路径
- 延迟、吞吐、并发量、饱和度和长尾

### 2. 再理解单机机制

- 缓存与局部性
- 锁、原子操作、调度和 I/O
- 日志、事务与崩溃恢复

### 3. 然后引入网络不确定性

- 部分失败
- 超时结果未知
- 重复、乱序和重试
- 复制、分片与一致性

### 4. 最后进入生产可靠性

- 有界资源与过载保护
- SLO 与错误预算
- 故障隔离、降级、恢复和演练

## Priority

优先掌握：

- 不变量与状态所有权。
- 并发、锁、原子性和内存可见性。
- 缓存、局部性和副本一致性。
- 排队、背压和过载。
- 数据库事务、WAL 和崩溃恢复。
- 网络超时、幂等和安全重试。
- 复制、一致性、共识和 fencing。
- 故障隔离、可观测性和恢复目标。

暂时不要把重点放在：

- 记忆大量中间件命令。
- 过早搭建复杂 Kubernetes 集群。
- 把微服务数量当成系统能力。
- 没有问题背景地通读论文。
- 为了技术栈完整而加入缓存、MQ 或分布式锁。

## Engineering Advice

- 先写不变量和失败语义，再画架构图。
- 先做单机正确版本，再增加网络和副本。
- 优先通过分区、单所有者和串行状态机减少共享状态。
- 关键业务状态优先让数据库约束承担最后防线。
- 缓存是正确性模型的一部分，不是透明加速器。
- 每个重试都必须有 Deadline、次数上限、退避、Jitter 和幂等依据。
- 每个队列都必须有容量、积压指标和超限策略。
- 备份只有成功恢复过才算备份。
- 每引入一个组件，都回答“不用它会怎样，它又新增了哪些失败模式”。
