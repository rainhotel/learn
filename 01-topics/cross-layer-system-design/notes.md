# 跨层系统设计哲学 Notes

## Unified Model

操作系统、数据库和分布式 Web 系统面对同一组母问题，只是尺度和故障模型不同：

- 资源有限。
- 多个执行者并发竞争。
- 生产者与消费者速度不匹配。
- 状态必须持久化并可恢复。
- 副本提升性能或可用性，同时制造一致性成本。
- 抽象隐藏复杂性，也可能隐藏真实代价。
- 故障不能消灭，只能检测、隔离、降级、恢复和修复。

统一分析链条：

> 约束 → 不变量 → 状态所有权 → 机制 → 性能收益 → 新增风险 → 失效边界 → 验证方法

## Core Design Philosophies

### 1. Mechanism And Policy

机制提供“能做什么”，策略决定“何时、对谁、以什么代价做”。

- OS：上下文切换机制与 CFS/优先级调度策略。
- 数据库：存储引擎能力与查询优化器策略。
- Web：限流框架与业务配额策略。

### 2. Indirection

用映射层将逻辑身份与物理资源分离：

- 虚拟地址 → 物理页。
- 文件描述符 → 内核对象。
- 域名 → IP。
- 服务名 → 实例。
- 逻辑 Key → 数据分片。

收益是迁移、替换和扩容；代价是多一层状态、缓存和失效问题。

### 3. Locality

CPU Cache、页缓存、数据库索引、Buffer Pool、CDN 和 Redis 都依赖访问分布不均匀。

不了解工作集、热点和访问分布，缓存设计只是猜测。

### 4. Single Ownership

共享可变状态会引入协调。状态如果能由一个线程、Actor、分片 Leader 或状态机负责修改，通常更容易证明正确。

优先顺序：

1. 消除共享状态。
2. 划分状态所有权。
3. 使用数据库约束和原子状态转换。
4. 使用乐观并发控制。
5. 最后才考虑范围更大的锁与协调。

### 5. Batching And Amortization

系统调用合并、顺序磁盘写、网络 Pipeline、数据库批量插入和消息批处理，都是以额外等待换取更高吞吐。

批处理不是免费优化：批越大，单条等待时间、失败影响和重试成本通常越大。

### 6. Logs And Replay

文件系统 Journal、数据库 WAL、复制日志、Kafka Log 和应用事件日志都在使用顺序追加与重放。

必须区分每一层保护的语义：文件系统日志正确不代表数据库事务正确，Kafka 消息持久化也不代表业务副作用只发生一次。

### 7. Backpressure And Admission Control

稳定系统必须有权拒绝工作。

- Semaphore、线程池和连接池限制同时执行的工作数。
- TCP 流控保护 Socket 缓冲区。
- Reactive Streams 传播消费能力。
- 限流、负载卸载和熔断保护服务与下游依赖。

无界队列只是把立即拒绝变成长时间等待、内存耗尽和级联失败。

### 8. Failure Isolation

进程、容器、线程池、连接池、租户、服务、Cell 和可用区都是故障域。

冗余只有在副本不被同一原因同时击穿时才有价值。共享数据库、DNS、证书、配置中心和部署流水线都可能成为隐藏的共同故障点。

### 9. End-To-End Correctness

底层机制可以降低风险，但最终业务正确性仍需端到端验证：

- TCP 成功不等于订单正确提交。
- 锁服务成功不等于旧持有者无法写资源。
- 消息投递成功不等于副作用只执行一次。
- 多副本不等于数据可恢复，误删除也会被复制。

### 10. Optimize The Common Case, Design The Failure Case

性能系统优化常见路径；高可用系统必须同时回答：

- 超时之后怎么办？
- 队列满了怎么办？
- 副本落后怎么办？
- 缓存全失效时后端能否存活？
- 旧 Leader 或旧租约持有者恢复后能否继续写？
- 恢复过程中再次失败怎么办？

## Cross-Layer Map

| 基础系统机制 | Web / 分布式机制 | 共同哲学 | 关键边界 |
| --- | --- | --- | --- |
| CPU Cache、页缓存 | CDN、本地缓存、Redis | 局部性、空间换时间 | Web 缓存没有硬件级一致性 |
| Cache Coherence、内存屏障 | 失效通知、版本号、强一致 KV | 定义副本可见顺序 | 网络会分区，节点会独立暂停 |
| Mutex、Semaphore | 数据库锁、租约、分布式协调 | 串行化冲突、限制并发 | 分布式租约过期后旧持有者可能仍运行 |
| CAS | 条件更新、版本比较、etcd Transaction | 明确原子状态转换点 | 远程 CAS 依赖共识与网络故障模型 |
| 虚拟内存、页表 | 分片路由、服务发现 | 逻辑身份与物理位置分离 | 跨分片访问涉及部分失败和事务 |
| Working Set、Thrashing | 热点集、缓存抖动、回源风暴 | 容量必须覆盖有效工作集 | 远程 miss 会继续压垮后端 |
| CPU 调度、Run Queue | 请求调度、负载均衡 | 公平、吞吐、延迟、优先级 | Web 调度器看到的状态滞后且不完整 |
| 管道、流控、缓冲区 | 消息队列、背压、批处理 | 解耦速度、吸收短期突发 | 队列无法处理长期供需失衡 |
| Journaling、WAL | Outbox、事件日志、复制日志 | 顺序追加、崩溃恢复 | 一层日志不能替另一层提供语义 |
| RAID、镜像 | 多副本、跨区复制 | 冗余提高耐久性和可用性 | 副本会延迟、冲突和共同失效 |
| 进程与 cgroup 隔离 | Bulkhead、Cell、租户隔离 | 限制爆炸半径 | 隐性共享依赖可能破坏隔离 |
| Watchdog、超时 | RPC Deadline、健康检查 | 对异常设置时间边界 | 超时只是怀疑，不是失败证明 |
| Checkpoint、快照 | 备份、PITR、状态快照 | 保存可恢复状态 | 备份必须实际恢复验证 |

## Cache: From CPU To Redis

### Shared Principle

缓存用更近、更快或更便宜的副本减少访问高成本资源。

简化平均访问时间：

\[
T_{avg}=H\cdot T_{hit}+(1-H)\cdot T_{miss}
\]

其中命中率高不一定代表收益高，还要看 miss penalty、热点分布、回源放大和缓存维护成本。

### Important Boundaries

- CPU 缓存一致性由硬件协议维护；Redis/本地缓存依赖 TTL、事件通知和应用约定。
- TTL 是陈旧窗口或回收机制，不是可靠的一致性协议。
- 缓存改变了正确性模型：读取可能陈旧，数据库和缓存可能短暂分叉。
- 缓存不可用和全 miss 路径必须容量测试，它们常是事故真正发生的路径。

### Web Cache Questions

- 允许多旧的数据？
- 谁负责填充和失效？
- 写成功、失效失败时如何收敛？
- 同一热点 miss 是否会被合并？
- 缓存故障时 fail-open、fail-closed 还是返回陈旧值？
- 后端能否承受全 miss？

## Locks: From Mutex To Distributed Leases

### Lock Protects Invariants

锁保护的不是一段代码，而是不变量，例如：

- 库存不能小于零。
- 一个幂等请求最多产生一个有效订单。
- 一个用户名只能属于一个账户。
- 同一版本的数据最多成功更新一次。

### Strong Analogies

- CAS ↔ `UPDATE ... WHERE version = old_version`。
- Semaphore ↔ 连接池或并发请求上限。
- Condition Variable ↔ 收到通知后重新检查真实状态。
- Immutable Snapshot / RCU ↔ MVCC 与配置快照。
- Critical Section ↔ 最小数据库原子状态转换。

### Why Distributed Lock Is Not Remote Mutex

单机 Mutex 默认依赖共享内存、原子指令、单一内核和明确所有权。

分布式环境中：

- 没有可靠全局时钟。
- 网络延迟没有可靠上界。
- 无法区分崩溃、分区和长时间暂停。
- 租约可能已过期，但旧客户端仍在运行。
- 锁服务与被保护资源通常不是同一原子系统。

典型错误：A 获得租约后暂停；租约过期，B 接管并写入；A 恢复后继续用旧身份覆盖 B。

正确性敏感场景需要 fencing token：锁服务为每次授予返回单调递增编号，最终资源拒绝比已见编号更旧的写入。

### Efficiency Lock Vs Correctness Lock

- 效率锁：偶尔重复只造成额外计算，例如缓存重建、重复报表；简单租约可能足够。
- 正确性锁：涉及资金、唯一资源、排他写入或不可逆副作用；必须有明确一致性、会话、fencing 和资源端验证，很多时候应改用数据库约束或状态机。

## Scheduling, Queues And Backpressure

### Shared Goals

- 吞吐量
- 平均延迟
- 尾延迟
- 公平性
- 截止时间
- 缓存亲和性
- 饥饿风险

### Key Insight

队列只能吸收短期突发，不能创造处理能力。长期到达率大于处理率时，任何队列最终都会溢出。

系统接近饱和后，排队等待往往非线性增长。在线系统通常需要容量余量，而不是追求 100% 利用率。

### Pool As Concurrency Limit

线程池、连接池和对象池的首要价值不仅是复用，更是限制同时进入下游的工作量。

应观察：active、idle、pending、wait time、timeout、utilization 和 downstream saturation。

## I/O And Async Systems

阻塞 I/O、事件循环、Async/Await 和消息驱动的共同目标，是在等待高延迟 I/O 时释放执行资源。

边界：

- 异步不会增加 CPU、数据库或磁盘的真实容量。
- CPU 密集任务会阻塞事件循环。
- 非阻塞 API 不代表系统具备背压。
- 无限接受异步任务可能更快耗尽内存。
- 异步执行不等于可靠交付。

## Transactions, WAL And Recovery

先记录可顺序追加的意图或状态转换，再修改复杂结构；崩溃后通过重放恢复。

需要区分：

- 文件系统 Journal：保护文件系统结构或块更新。
- 数据库 WAL：保护事务与数据页恢复。
- 复制日志：让副本应用同一状态转换。
- Kafka Log：保护消息保留与消费位置。
- 应用事件日志：表达业务状态变化。

事务设计必须从业务不变量出发。隔离级别名称不能替代异常分析；唯一约束、条件更新和状态机通常是关键不变量的最后防线。

## Network Failure, Retry And Idempotency

### Timeout Means Unknown

RPC 超时后，远端可能：

1. 尚未收到请求。
2. 收到但尚未执行。
3. 已经执行但响应丢失。
4. 仍在执行。

因此超时通常表示“调用方不再等待”，不是“操作没有发生”。

### Safe Retry Checklist

- 错误是否瞬态？
- 操作是否天然幂等，或能可靠去重？
- 是否有整体 Deadline？
- 是否指数退避并加入 Jitter？
- 是否有 Retry Budget？
- 调用链是否只由一层主导重试？
- 是否能查询最终状态或进行对账？

### Exactly Once Boundary

所谓恰好一次通常是限定作用域内的端到端效果：

> 至少一次投递 + 去重 + 原子状态转换 + 明确提交边界

## Replication, Consistency And Consensus

复制提高读取能力、耐久性或可用性，同时引入延迟、冲突、脑裂、旧 Leader 和恢复问题。

一致性必须写成客户端可观察的契约：

- 是否读己之写？
- 是否单调读？
- 是否线性一致？
- 允许陈旧多久？
- 分区时拒绝还是返回可能陈旧的结果？

共识解决多个节点如何对一系列决定形成一致顺序。它不自动解决业务建模、容量、跨分片事务、缓存一致性或外部副作用。

CAP 应用于网络分区发生时，线性一致性与持续可用响应之间的选择；不是平时给数据库贴“三选二”标签。

## High Availability

高可用的对象不是“进程永不挂”，而是关键用户任务在规定时间内能够成功、降级或恢复。

需要共同定义：

- SLI / SLO / Error Budget
- RTO / RPO
- 负载卸载与优先级
- 超时、并发限制、隔舱与熔断
- 故障域与容量余量
- 检测、降级、恢复和对账路径

多副本不能替代灾难恢复；副本会忠实复制误删除和逻辑损坏。

## Mental Model

最值得记住的一张图不是组件拓扑，而是四条路径：

1. 状态路径：数据在哪里产生、提交、复制、缓存和恢复。
2. 请求路径：请求在哪里排队、超时、重试和被拒绝。
3. 故障路径：一个依赖变慢后，压力如何传播和放大。
4. 证据路径：哪些指标、日志、Trace 和实验能证明系统符合预期。
