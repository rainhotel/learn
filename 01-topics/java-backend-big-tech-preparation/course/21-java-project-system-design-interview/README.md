# 第 21 章：Java、项目与系统设计面试

## 章节定位

- 类型：Interview System + Closed-book Recall + Project Defense + Evidence Practice
- 难度：综合深入
- 建议学习时间：28-36 小时，之后每周滚动复训
- 先修章节：第 01-19 章；第 20 章事实台账与证据表达
- 对应项目：NotifyFlow 可靠通知平台与 Agent 事故助手
- 对应岗位：Java 后端、Agent/AI 应用后端、先进制造数字化研发

## 当前状态

- 阶段：八件套完整内容初稿，模拟面试实验 Pending
- 调研日期：2026-07-15
- 已完成：回答协议、知识追问树、项目追问树、证据引用规范、模拟评分表和纠错循环设计
- 未完成：学习者闭卷录音、陌生面试官追问、复训成绩、真实求职面试反馈与课程修订

本章没有声称任何真实面试已经发生，不能标记为 Lab Verified、Release Candidate 或 Released。

## 为什么单独设置这一章

学过一个概念，不等于能在压力下解释机制；做过一个项目，不等于能证明个人贡献；背过一道系统设计题，也不等于能根据约束做取舍。

本章把前十九章的知识压缩成四种可观察能力：

1. 闭卷口述：不看笔记给出短而准确的机制解释。
2. 承受追问：从定义进入实现、失败、替代方案和证据。
3. 项目答辩：把 NotifyFlow 的需求、架构、可靠性和个人工作串成一条证据链。
4. 陌生题推导：在信息不完整时先澄清、计算、建模，再提出可验证方案。

## 与相邻章节的边界

- 第 13 章训练完整系统设计与项目答辩内容；本章训练在有限时间、连续追问和证据核验下表达。
- 第 20 章维护简历事实台账；本章只允许引用已经进入事实台账或课程实验记录的事实。
- 第 22 章训练算法和更完整的 Teach-back；本章只保留岗位面试所需的算法沟通接口，不重复算法课程。
- 本章不是“面试原题命中库”，也不把社区经验帖当作机制证据。

## 核心问题

1. 如何在 30、90、180 秒三个时限内回答同一道问题？
2. 如何用“结论、机制、场景、失败、证据、边界”替代背诵长答案？
3. 面试官从一个问题还能沿哪些方向追问？
4. Java、JMM、并发和 JVM 的高频概念怎样连接到生产故障？
5. Spring、MySQL、Redis、Kafka 的答案怎样落到一致性和恢复语义？
6. 网络、连接池、Docker、Kubernetes 如何与延迟、容量和发布故障连接？
7. 怎样回答 NotifyFlow 的个人贡献、技术选型、性能数字和未完成项？
8. RAG 与 Agent 面试中，如何同时讨论质量、权限、成本和可靠执行？
9. 系统设计题如何从需求澄清推进到容量、数据、故障、观测和演进？
10. 如何用录音、评分、错误标签和延迟复训形成可验证进步？

## 能力矩阵

| 能力域 | 闭卷输出 | 深挖要求 | 必须连接的证据 |
|---|---|---|---|
| Java/JMM/并发 | happens-before、原子性、线程池、中断 | 交错、饱和、取消、故障放大 | Java 实验、源码、JFR |
| JVM | 内存、GC、类加载、排障 | 现象到假设再到命令与证据 | GC/JFR/线程与堆证据 |
| Spring | 代理、事务、Bean、Web 链路 | 失效条件、传播、异步边界 | 测试、日志、SQL |
| MySQL/Redis/Kafka | 数据真相、缓存、事件 | 重复、乱序、死锁、积压、恢复 | DDL、执行计划、时间线 |
| 网络与容器 | 超时、池、DNS/TCP/TLS、探针 | UNKNOWN、端口、优雅下线 | 指标、配置、故障演练 |
| NotifyFlow | 需求、主链路、可靠性 | 个人贡献、数字、替代方案 | 事实台账与项目证据 |
| RAG/Agent | ingestion、检索、引用、Tool | ACL、注入、评测、预算、恢复 | 数据集、ranking、审计 |
| 系统设计 | 澄清、估算、API、状态机 | 瓶颈、降级、安全、成本、演进 | 公式、ADR、验证计划 |

## 退出标准

- 随机抽取 40 个核心问题，90 秒回答得分不低于 80%，且没有事实性硬错。
- 对任意根问题至少展开四层追问：机制、失败、替代方案、证据。
- 能在 60 秒内定位所引用的实验、代码、SQL、日志或报告。
- 能完成 3/8/15 分钟三个版本的 NotifyFlow 项目介绍，事实口径一致。
- 能完成一轮 45 分钟综合模拟面试，并对每个扣分点形成纠错卡。
- 48 小时后闭卷重答同类题，错误不靠阅读原答案临时消失。
- 遇到未实现或未验证内容时能明确说“设计方案”或“实验 Pending”。
- 能为一个陌生系统设计题写出假设、容量模型、状态真相、故障路径和验证计划。

这些标准在录音、评分表和复训证据生成前均为 Pending。

## 本章交付物

- 个人核心问题地图与追问树。
- 40 题闭卷口述录音及逐题评分。
- NotifyFlow 项目证据索引和三档介绍稿。
- Java/中间件/Agent 综合模拟面试记录。
- 系统设计白板或文档、容量计算和 ADR。
- 错误标签、纠错卡、48 小时复训结果。
- 事实边界审计表：实习事实、独立项目、静态设计、真实实验分别标注。

## 建议学习顺序

1. 先读讲义，掌握统一回答协议。
2. 建立八个能力域的根问题清单。
3. 每天闭卷回答 8-12 题，不先看参考答案。
4. 为错误题画追问树并绑定证据。
5. 完成 NotifyFlow 3/8/15 分钟项目介绍。
6. 进行 45 分钟综合模拟并录音。
7. 按错误类型纠正，48 小时后重答。
8. 只有证据和陌生评审通过后，才把表述加入求职材料。
