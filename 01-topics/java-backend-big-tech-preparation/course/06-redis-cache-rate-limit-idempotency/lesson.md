# Redis 缓存、限流与短期幂等

## 课程信息

- 所属模块：缓存与高并发工程
- 难度：进阶
- 建议时长：18-24 小时
- 先修章节：MySQL 索引与事务、Spring 事务与代理
- 对应项目：NotifyFlow 租户限流、模板缓存、短期幂等和热点治理
- 对应岗位：Java 后端、Agent 平台后端、先进制造平台研发

## 学习目标

完成本章后，学习者能够：

1. 根据访问模式选择 Redis 数据结构和 key 设计。
2. 区分单命令原子性、`MULTI/EXEC`、`WATCH` 和 Lua 的能力边界。
3. 实现并评审固定窗口、滑动窗口或令牌桶限流。
4. 设计缓存更新、击穿保护、穿透治理和雪崩恢复方案。
5. 把 Redis 幂等当作快速路径，并用数据库约束保存最终事实。
6. 解释持久化、复制、Sentinel、Cluster 和故障窗口。
7. 识别热 key、大 key、慢命令、fork 和 swap 引发的尾延迟。
8. 解释分布式锁的 owner、TTL、续期和 fencing token。

## 为什么要学

Redis 在简历中很常见，但“项目用了 Redis”本身没有价值。面试官真正关注：

- 为什么这里需要 Redis？
- Redis 故障后系统还能否工作？
- 缓存与数据库不一致怎么办？
- 限流是否存在竞态和边界突发？
- 幂等 key 被淘汰后会不会重复执行？
- 锁过期后旧线程为什么仍可能破坏数据？
- Cluster 和副本是否真的保证不丢数据？

NotifyFlow 的正确目标不是“到处加缓存”，而是把 Redis 放在能带来可测收益、且丢失后仍可恢复的位置。

## 一、先判断是否需要 Redis

### 适合 Redis 的信号

- 数据访问频率高、允许短暂陈旧、可从权威数据源重建。
- 需要低延迟原子计数或短生命周期状态。
- 需要跨实例共享的限流、配额或去重快速路径。
- 需要使用 Set、ZSet、Bitmap、Stream 等原生结构减少应用侧复杂度。

### 不适合只用 Redis 的状态

- 计费、资金、订单和通知最终状态。
- 必须永久保存的幂等结果。
- 对任何重复副作用都不可接受的设备控制或 Agent 工具执行。
- 需要跨多个独立系统强原子提交的流程。

原则：

> Redis 可以加速正确系统，但不应成为掩盖数据模型和恢复协议缺失的捷径。

## 二、数据结构从访问模式出发

| 结构 | 典型操作 | NotifyFlow 候选 | 主要风险 |
|---|---|---|---|
| String | GET/SET/INCR | 缓存对象、计数器、幂等占位 | 大 value、序列化不兼容 |
| Hash | 字段级读写 | 任务进度摘要、渠道配置 | field 过多形成大 key |
| List | 两端队列 | 简单队列、最近记录 | 不替代可靠 MQ，积压成大 key |
| Set | 去重、集合关系 | 临时去重、订阅成员 | 大集合操作延迟 |
| ZSet | score 排序、范围 | 延迟任务候选、滑动窗口 | 清理不及时导致无限增长 |
| Bitmap | 位状态 | 活跃统计、批量布尔状态 | 稀疏大偏移浪费空间 |
| HyperLogLog | 近似基数 | UV 估算 | 有误差，不能列出成员 |
| Stream | 消息流、消费组 | 轻量事件流实验 | 运维语义不同于专业 MQ |

不要因为“排行榜用 ZSet”就把所有排序数据放进去。先列出写入频率、查询方式、数据规模、TTL、原子操作和恢复来源。

## 三、key 和序列化是数据协议

### key 设计

推荐包含：系统、业务、租户、资源、版本。

```text
nf:rate:create-task:{tenantId}:20260714T120501
nf:cache:template:v2:{tenantId}:{templateId}
nf:idem:create-task:{tenantId}:{idempotencyKey}
```

注意：Cluster 中 `{...}` 是 hash tag。它能让多 key 落入同一槽，也可能把一个大租户的流量集中到单槽。必须有意识使用。

### value 设计

- 明确编码：字符串、JSON、二进制协议。
- 保留 schema/version 字段。
- 控制最大长度。
- 考虑灰度期间新旧应用能否互读。
- 不在不可信环境使用 Java 原生反序列化。

`StringRedisTemplate` 便于人工检查；JSON 可读但体积更大。二进制协议紧凑但调试和兼容治理成本更高。

## 四、TTL、过期和淘汰不是一回事

### TTL

TTL 是业务生命周期：多久后数据不再有效。缓存、限流窗口、临时幂等和锁都需要明确 TTL。

常见错误：

- `INCR` 成功但 `EXPIRE` 未执行，key 永不过期。
- 更新 value 时意外清除 TTL。
- 大量 key 使用相同过期时刻，引发集中失效。
- 把 TTL 当作缓存一致性的唯一保证。

### eviction

eviction 是内存不足时的资源策略，不等于正常过期。`maxmemory` 达到上限后，Redis 可能拒绝写入或淘汰 key。

如果幂等 key 可以被淘汰，Redis 就不能是唯一重复保护。数据库唯一约束必须兜底。

### 指标

至少观察：

- `used_memory`、`maxmemory`。
- `evicted_keys`、`expired_keys`。
- keyspace hits/misses。
- rejected commands。
- 单 key 大小和元素数量。

## 五、Redis 原子性工具

### 1. 单命令

`SET ... NX EX/PX`、`INCR`、`HINCRBY` 等单命令是原子的。能用单命令表达时，通常优先单命令。

### 2. `MULTI/EXEC`

命令先排队，`EXEC` 时连续执行，其他客户端命令不会插入中间。但它不同于 MySQL 事务：

- 不提供执行阶段的数据库式回滚。
- 某条命令类型错误，其他已排队命令仍可能执行。
- 事务期间读取语义需要客户端框架特别处理。

### 3. `WATCH`

`WATCH` 是乐观并发控制。被监视 key 在提交前变化时，`EXEC` 中止，应用需要重新读取并有限重试。

### 4. Lua

Lua 把多条命令和判断放到服务端原子执行，适合限流、条件扣减、安全释放和状态转换。

风险：脚本执行期间会阻塞其他命令。脚本必须：

- 时间复杂度明确。
- 不扫描无界 keyspace。
- 不遍历超大集合。
- 输入大小受限。
- 有超时、指标和版本管理。

## 六、限流算法与真实需求

### 固定窗口

按租户和时间窗口计数：

```text
key = tenant + currentSecond
INCR key
EXPIRE key 2
```

优点：简单、内存低。缺点：窗口边界可突发，例如前一秒末尾 100 次、后一秒开头 100 次。

`INCR` 和首次 `EXPIRE` 必须原子组合，否则客户端崩溃可能留下无 TTL key。Lua 是常见做法。

### 滑动窗口日志

使用 ZSet 保存请求时间戳：

1. 删除窗口外成员。
2. 统计当前成员数。
3. 未超限则加入当前请求。
4. 设置 TTL。

更精确，但每次请求需要维护成员，内存和时间复杂度更高。member 必须唯一，清理必须有界。

### 令牌桶

保存剩余 token 和最后补充时间，Lua 中计算补充、消费和更新时间。支持稳定速率与一定突发量，适合供应商配额。

### 限流维度

- 租户总额度。
- API key。
- 渠道/供应商。
- 接口。
- 用户或设备。
- 全局保护阈值。

只按 IP 限流可能误伤 NAT 后大量用户，也可能被分布式攻击绕过。

### Redis 故障时怎么办

必须预先选择：

- fail-open：放行，保证可用性但可能压垮下游。
- fail-closed：拒绝，保护资源但影响用户。
- 本地降级限流：各实例独立，精度下降。
- 静态保守配额：适合高风险供应商或设备控制。

## 七、短期幂等不是最终幂等

### 快速路径

```text
SET idem-key PROCESSING NX PX 300000
```

成功表示当前请求获得处理资格；失败表示 key 已存在，需要读取状态或返回处理中。

### 状态模型

```text
ABSENT -> PROCESSING -> SUCCESS(result reference)
                     -> RETRYABLE_FAILURE
                     -> FINAL_FAILURE
```

只存一个布尔值无法区分正在执行、成功、失败和未知。

### 数据库兜底

Redis 可能过期、淘汰、故障转移丢写或被误删。NotifyFlow 仍使用数据库 `(tenant_id, idempotency_key)` 唯一约束保存最终结果。

推荐流程：

1. Redis 快速拒绝明显重复请求。
2. 数据库唯一约束决定最终是否首次创建。
3. Redis 保存数据库结果引用，缩短重复请求响应。
4. Redis 丢失时退化到数据库查询，正确性不变。

## 八、缓存一致性

### Cache Aside

读：

1. 读缓存。
2. miss 时读数据库。
3. 写缓存并设置 TTL。

写：

1. 更新数据库。
2. 删除缓存。

为什么通常删除而不是直接更新：应用可能无法原子协调数据库和 Redis，直接更新也会存在失败与并发覆盖。

### 仍然存在的竞态

- 旧读请求在数据库更新前读到旧值，随后在删除缓存后把旧值回填。
- 数据库提交成功，删除缓存失败。
- 多实例同时重建。

治理工具：

- 短 TTL 限制陈旧时间。
- 删除失败重试或通过 Outbox/CDC 驱动失效。
- 单飞/互斥重建降低击穿。
- value 带版本，拒绝旧版本覆盖新版本。
- 对强一致读绕过缓存。

不要把“延迟双删”背成强一致证明。它只是针对部分竞态的经验方案，时间参数和失败路径仍需验证。

## 九、穿透、击穿、雪崩、热 key、大 key

### 穿透

大量查询不存在数据，缓存一直 miss。

治理：参数校验、空值短缓存、Bloom Filter、访问控制。Bloom Filter 有误判且需要维护，不能替代数据库查询。

### 击穿

单个热点 key 失效，大量请求同时访问数据库。

治理：single-flight、互斥重建、逻辑过期、提前刷新、热点永不过期加主动更新。必须处理重建线程失败。

### 雪崩

大量 key 同时过期或 Redis 整体不可用。

治理：TTL 抖动、分批预热、多级缓存、限流降级、熔断和数据库容量保护。

### 热 key

单 key 或单槽流量过高，CPU、网络或某个 Cluster 节点成为瓶颈。

治理：本地缓存、请求合并、读副本（接受陈旧）、key 分片、业务拆分。写热点不能简单复制分片而不解决一致性。

### 大 key

value 太大或集合元素过多，会增加网络、序列化、删除、迁移和 fork 成本。

治理：限制大小、拆分结构、分页/分批处理、使用渐进删除命令，并用 `--bigkeys`、`--memkeys`、`--keystats` 诊断。

## 十、持久化与高可用

### RDB 与 AOF

- RDB：时间点快照，文件紧凑、恢复快，但可能丢失最近一段写入。
- AOF：记录写命令，通常更耐久，文件与重写成本更高。
- 可同时启用，也可在纯缓存场景关闭持久化。

持久化策略由恢复点目标和恢复时间目标决定，不由“生产必须 AOF”一句话决定。

### 复制

默认异步复制意味着主节点确认写后，副本可能尚未收到。`WAIT` 降低风险但不提供绝对强一致。

读副本会读到旧数据。幂等判定、锁 owner 和刚写后读等路径不能随意路由副本。

### Sentinel

Sentinel 提供监控、通知、故障转移和主节点发现。客户端必须支持 Sentinel 拓扑变化和连接恢复。

故障转移实验要观察：检测时间、选举时间、短暂错误、旧主恢复、写丢失窗口和客户端重连。

### Cluster

Cluster 使用 16384 个槽扩展容量与吞吐。多 key 操作需要同槽，hash tag 是数据建模的一部分。

#### 哈希槽是什么

哈希槽是 Redis Cluster 的逻辑分片单位，不是 Redis 的 Hash 数据结构。整个集群固定有 `16384` 个槽，key 按下面的规则映射到槽：

```text
slot = CRC16(key) % 16384
```

主节点负责一部分槽，副本节点复制对应主节点的数据但不独立负责槽。客户端根据本地保存的“槽 -> 节点”映射直接路由请求：

```text
key -> CRC16 -> slot -> owning master -> command
```

例如，假设 `user:1001` 计算出的槽是 `8234`，而槽 `8234` 属于 `master-2`，客户端就把请求发给 `master-2`。如果客户端路由表过期，节点会返回 `MOVED`，客户端刷新槽位映射后重试；扩缩容迁移期间可能收到临时的 `ASK`。

#### 为什么不直接对节点数取模

如果使用 `hash(key) % 节点数`，增加或减少一个节点会让大量 key 重新映射。哈希槽先把 key 放入固定的 16384 个逻辑桶，扩容时只需把部分槽及其 key 迁移给新节点，迁移范围更可控。

#### 多 key 操作与 hash tag

Cluster 中 `MGET`、涉及多个 key 的 Lua 脚本或事务，要求相关 key 位于同一个槽，否则会收到 `CROSSSLOT`。可以使用 `{...}` 指定 hash tag，让 Redis 只对大括号中的内容计算槽位：

```text
user:{1001}:profile  ->  hash("1001")
user:{1001}:quota    ->  hash("1001")
```

上面两个 key 会落入同一个槽，可以执行跨 key 操作。但 hash tag 也会把同一 tag 的流量集中到一个槽，不能滥用，否则可能制造热槽。

面试中可以这样回答：

> Redis Cluster 把整个 keyspace 划分为固定的 16384 个哈希槽，使用 `CRC16(key) % 16384` 计算 key 所属槽，再由槽位映射到主节点。扩容和缩容通过迁移槽完成；客户端通常缓存槽位映射，并根据 `MOVED` 或 `ASK` 更新路由。多 key 命令要求 key 在同一槽，可以用 hash tag 保证这一点，但要注意集中到单槽的热点评估。

Cluster 的目标是高性能、可扩展和可接受的数据安全，不是强一致数据库。关键事实仍需存放在能满足业务一致性要求的系统中。

## 十一、分布式锁的正确问题

### 获取

```text
SET lock-key unique-owner NX PX ttl
```

### 释放

只能在 value 仍等于自己的 owner 时删除。否则 A 的锁过期后 B 获得锁，A 恢复并执行普通 `DEL` 会错误删除 B 的锁。

### 续期

续期必须校验 owner，且必须限制最长持有时间和续期次数。进程存活不代表锁始终有效。

### fencing token

每次成功获取锁时生成单调递增 token，下游只接受比历史 token 更大的请求。这样旧持有者即使暂停后恢复，也无法覆盖新持有者结果。

对于 NotifyFlow 任务领取，数据库 lease、owner、version 与条件更新通常比额外 Redis 锁更直接。

## 十二、Spring Data Redis 工程边界

### `RedisTemplate`

- 配置后可以在线程间复用。
- key/value 序列化必须显式定义。
- 事务多操作需要确保同一连接，例如使用 `SessionCallback`。
- 异常路径要清理事务状态。

### Spring 事务集成

启用 Redis transaction support 会把连接绑定到当前线程，但这不等于 Redis 与 MySQL 获得一个全局原子事务。仍可能出现数据库提交成功、Redis 操作失败，或相反。

缓存和限流应设计成失败可恢复；跨资源最终一致仍使用 Outbox、补偿或重建。

### Cache abstraction

默认 non-locking writer 追求吞吐，但某些多命令操作可能重叠。locking writer 是 cache 级别锁，可能放大等待。

`@Cacheable` 只减少重复计算，不自动解决缓存击穿、强一致、租户隔离和批量清理风险。

## 十三、可观测性与排障顺序

### 指标

- QPS、命中率、P50/P95/P99。
- 连接数、阻塞客户端、超时和重连。
- 内存、碎片率、evicted/expired keys。
- 复制 offset、lag、failover 次数。
- slowlog、latency events。
- 大 key、热 key、单槽流量。

### 排障顺序

1. 确认业务症状和时间窗口。
2. 比较应用耗时、网络 RTT 和 Redis 服务耗时。
3. 查看慢命令、阻塞命令和大 key。
4. 检查内存、淘汰、swap、THP、fork 和 AOF。
5. 检查复制延迟、故障转移和客户端重连。
6. 用最小故障实验复现，不直接在生产执行危险全量命令。

## 常见错误

1. 把 Redis 当唯一数据库，却没有数据损失和恢复模型。
2. `INCR` 与 `EXPIRE` 分两次执行，留下永久限流 key。
3. 只加 TTL，不考虑 eviction。
4. 使用 Java 原生序列化存储不可信数据。
5. 缓存 key 没有租户和版本，发生串租户或灰度不兼容。
6. 认为 `WAIT`、副本或 Sentinel 等于零数据丢失。
7. 锁释放直接 `DEL`，没有 owner 校验。
8. 只看平均延迟和命中率，不看 P99、slowlog 和大 key。

## 本章小结

Redis 的价值来自低延迟数据结构和原子操作，但正确性来自明确的数据所有权、故障降级和持久化兜底。NotifyFlow 应把 Redis 用于限流、缓存和短期幂等快速路径，把最终任务状态和唯一约束留在数据库，并通过指标和故障实验证明收益。
