当前简历可确认的事实包括：

## 二、暑期独立项目：可靠消息通知平台

建议名称：`NotifyFlow - 企业消息通知与任务调度平台`。

简历属性：基于历史业务场景的独立工程化重构，不冒充实习期间上线成果。

### 业务场景

- 业务系统提交短信、邮件和站内信任务。
- 支持模板、变量、批量发送、定时任务和优先级。
- 面对供应商限流、超时、部分失败和回调乱序。
- 提供任务进度、失败审计、重试、取消和人工重放。

### 架构边界

- 单体模块化 Spring Boot 起步，不先拆微服务。
- MySQL 是事实状态源。
- Redis 用于明确的限流、短期幂等或热点缓存。
- Kafka 用于异步解耦、事件回放和 Agent/数据链路；RocketMQ 只作为选型对照，不在首版同时落地两套 MQ。
- RAG 知识服务作为独立模块，不污染核心消息链路。

### 核心数据模型

- `notification_task`：批次任务与总体状态。
- `notification_item`：单个接收方与渠道发送状态。
- `message_template`：模板版本与变量定义。
- `outbox_event`：待发布可靠事件。
- `delivery_attempt`：每次发送尝试和错误分类。
- `provider_callback`：供应商回调原文与去重键。

### 必做工程问题

1. API 重复提交如何幂等？
2. 数据库提交成功、消息发送失败怎么办？
3. 消费者收到重复消息怎么办？
4. 单条失败是否阻塞整个批次？
5. 供应商限流和超时如何处理？
6. 重试任务如何避免重试风暴？
7. 消息积压时如何扩容、降级和保护数据库？
8. 进程关闭时如何停止接单并等待任务完成？

### 必做实验

- 100、1,000、10,000 接收方批次压测。
- 无界队列与有界队列对比。
- 数据库慢查询与索引优化。
- 重复请求和重复消费。
- 下游 429、超时、500 和部分失败。
- MQ 消费者停止后制造积压，再恢复。
- 服务发送中途退出并重启恢复。

### 扩展后的真实需求场景

- AI 运维知识助手：模型解释告警并引用文档，不能越权执行危险操作。
- 容器化部署：NotifyFlow、MySQL、Redis、MQ 和 RAG 服务通过 Compose 一键复现。
- Kubernetes 发布：应用滚动升级，探针失败自动摘流，版本可回滚。
- 多实例任务：两个实例同时领取任务不能产生重复外部副作用。
- 下游故障：供应商变慢、MQ 积压、Pod 重启或节点失联时任务可以恢复。
- AI 成本与降级：模型超时、Token 超预算或服务不可用时退化到检索结果或规则建议。

### 扩展证据

- Dockerfile、Compose 文件和容器运行手册。
- Kubernetes 最小 manifests、滚动发布和回滚记录。
- 多实例并发领取、重复请求、实例重启和网络故障实验。
- 模型延迟、Token 成本、RAG 质量和降级行为报告。

## 三、RAG 模块：运维知识助手

### 目标

输入告警、错误码或故障描述，检索产品文档、历史故障和处理手册，输出带引用的处理建议。

### 数据管道

文档解析 -> 清洗 -> 结构化切分 -> 元数据 -> Embedding -> 向量索引 -> 检索 -> 重排 -> 上下文组装 -> 生成与引用。

### 必做对比

- 固定长度切分与按标题/段落切分。
- Dense Retrieval 与 BM25。
- 纯向量与 Hybrid Search。
- 有无 Reranker。
- Top-K 与上下文长度变化。

### 评测集

每条包含：问题、期望证据文档、关键事实、不可回答条件。

评测至少覆盖：

- 精确错误码查询。
- 同义描述。
- 跨文档组合问题。
- 文档中没有答案的问题。
- 过期版本与版本过滤。
