## 1. 数据库概览

### 1.1 数据、数据处理、数据管理

数据是描述事物的符号记录。数据不只包括数字，还可以包括文字、图像、声音、视频等。

数据处理是对数据进行收集、存储、加工、传播和使用的过程。

数据管理是数据处理的核心，主要包括：

- 数据组织。
- 数据存储。
- 数据维护。
- 数据检索。
- 数据共享。
- 数据安全控制。

### 1.2 数据管理技术的发展阶段

#### 人工管理阶段

特点：

- 数据不保存或保存很少。
- 应用程序直接管理数据。
- 数据面向具体应用。
- 数据共享性差。
- 数据冗余大。
- 数据独立性差。

适用背景：

- 早期计算机主要用于科学计算。
- 外存设备和操作系统能力有限。

#### 文件系统阶段

特点：

- 数据可以长期保存。
- 由文件系统统一管理文件。
- 数据和程序之间有一定独立性。
- 仍然面向具体应用。
- 数据共享性仍然差。
- 数据冗余和不一致问题仍然明显。

缺点：

- 文件之间联系弱。
- 数据结构隐藏在程序中。
- 修改数据结构会影响应用程序。

#### 数据库系统阶段

特点：

- 数据结构化。
- 共享性高。
- 冗余度低。
- 易扩充。
- 数据独立性高。
- 由 DBMS 统一管理和控制。

DBMS 提供：

- 数据定义。
- 数据操纵。
- 数据库运行管理。
- 数据库建立和维护。
- 安全性控制。
- 完整性控制。
- 并发控制。
- 恢复。

### 1.3 基本概念

#### 数据库 DB

数据库是长期存储在计算机内、有组织、可共享的大量数据集合。

关键词：

- 长期存储。
- 有组织。
- 可共享。
- 数据集合。

#### 数据库管理系统 DBMS

DBMS 是位于用户和操作系统之间的数据管理软件。

主要功能：

- 数据定义功能。
- 数据操纵功能。
- 数据库运行管理。
- 数据库建立和维护。
- 通信功能。

#### 数据库系统 DBS

数据库系统通常包括：

- 数据库。
- 数据库管理系统。
- 应用程序。
- 数据库管理员 DBA。
- 用户。
- 计算机硬件和软件环境。

区别：

- DB 是数据集合。
- DBMS 是管理数据的软件。
- DBS 是包含 DB、DBMS、人员、应用和环境的完整系统。

### 1.4 数据库系统特点

#### 数据结构化

数据库系统不仅保存数据本身，还保存数据之间的联系。

与文件系统相比：

- 文件系统的数据结构通常面向某个程序。
- 数据库系统的数据结构面向全组织或多个应用。

#### 数据共享性高、冗余低

共享性高意味着多个用户、多个应用可以使用同一份数据。

好处：

- 减少重复存储。
- 降低冗余。
- 减少数据不一致。

#### 数据独立性高

数据独立性分为：

- 物理独立性。
- 逻辑独立性。

物理独立性：

- 内模式改变时，模式可以尽量不变，应用程序不用改。
- 例如存储结构、索引、存储位置改变。

逻辑独立性：

- 模式改变时，外模式和应用程序可以尽量不变。
- 例如增加属性、增加关系。

#### 数据由 DBMS 统一管理和控制

统一控制包括：

- 安全性控制：防止非法访问。
- 完整性控制：保证数据正确、有效、相容。
- 并发控制：保证多用户并发访问时数据一致。
- 恢复：故障后恢复数据库。

### 1.5 三级模式结构

数据库系统三级模式：

```text
外模式
模式
内模式
```

#### 模式

模式也叫概念模式，是数据库中全体数据的逻辑结构和特征描述。

特点：

- 一个数据库只有一个模式。
- 是全局逻辑视图。
- 不涉及物理存储细节。

#### 外模式

外模式也叫用户模式或子模式，是数据库用户能看到和使用的局部逻辑结构。

特点：

- 一个数据库可以有多个外模式。
- 一个外模式可以被多个应用使用。
- 同一数据在不同外模式中可以有不同表现。

#### 内模式

内模式也叫存储模式，是数据物理结构和存储方式的描述。

内容：

- 存储路径。
- 索引方式。
- 文件组织。
- 记录存储方式。

### 1.6 两级映像

两级映像：

- 外模式/模式映像。
- 模式/内模式映像。

#### 外模式/模式映像

作用：

- 保证逻辑独立性。
- 当模式改变时，只要修改外模式/模式映像，就可以尽量保持外模式和应用程序不变。

#### 模式/内模式映像

作用：

- 保证物理独立性。
- 当内模式改变时，只要修改模式/内模式映像，就可以尽量保持模式不变。

### 1.7 数据模型

数据模型是现实世界数据特征的抽象。

三要素：

- 数据结构。
- 数据操作。
- 完整性约束。

#### 数据结构

描述系统静态特性，即数据对象及对象之间的联系。

#### 数据操作

描述系统动态特性，即允许对数据执行的操作。

常见操作：

- 查询。
- 插入。
- 删除。
- 修改。

#### 完整性约束

描述数据必须满足的限制条件。

例如：

- 学号不能为空。
- 成绩在 0 到 100。
- 选课表中的学号必须存在于学生表。

### 1.8 数据模型的层次

数据抽象通常经历两步：

```text
现实世界 -> 概念模型 -> DBMS 支持的数据模型
```

#### 概念数据模型

概念数据模型也叫概念模型或信息模型。

特点：

- 面向用户。
- 按用户观点对信息建模。
- 与具体 DBMS 无关。
- 是现实世界到机器世界的中间层次。
- 是数据库设计人员和用户交流的语言。

常用概念模型：

- E-R 模型。

#### 逻辑数据模型

逻辑数据模型是 DBMS 支持的数据模型。

常见逻辑模型：

- 层次模型。
- 网状模型。
- 关系模型。
- 面向对象模型。
- 对象关系模型。

本课程重点是关系模型。

#### 物理数据模型

物理数据模型描述数据在计算机中的存储结构和存取方法。

### 1.9 E-R 模型基础

E-R 模型用于描述现实世界中的实体、属性和联系。

#### 实体

实体是客观存在并可相互区别的事物。

例：

- 学生。
- 课程。
- 客户。
- 商品。
- 订单。

#### 属性

属性是实体具有的某一特性。

例：

- 学生的学号、姓名、性别。
- 商品的商品编号、商品名称、单价。

#### 联系

联系是实体之间的关联。

联系类型：

- `1:1`。
- `1:n`。
- `m:n`。

#### 码

码是能唯一标识实体的属性或属性组。

例：

- 学号可以作为学生实体的码。
- 商品编号可以作为商品实体的码。

## 2. 关系数据模型

### 2.1 关系模型特点

关系模型建立在严格的数学理论基础之上，主要基础是集合论和谓词逻辑。

特点：

- 数据结构简单清晰。
- 用户易懂易用。
- 能表达丰富语义。
- 用二维表统一表示实体和实体之间的联系。
- 查询语言具有较强的非过程化特点。

关系模型三要素：

- 关系数据结构。
- 关系操作。
- 关系完整性约束。

### 2.2 二维表与关系

一个关系就是一个规范化的二维表。

二维表组成：

- 表名。
- 表头。
- 若干行数据。
- 若干列。

对应关系术语：

```text
表       -> 关系
行       -> 元组
列       -> 属性
列名     -> 属性名
单元格值 -> 分量
取值范围 -> 域
```

规范化含义：

- 每一列都是原子项。
- 不允许表中表。
- 每个分量不可再分。

### 2.3 域、笛卡尔积和关系

#### 域

域是一组具有相同数据类型的值的集合。

例：

```text
性别域 = {男, 女}
成绩域 = {0, 1, 2, ..., 100}
```

#### 笛卡尔积

给定一组域 `D1, D2, ..., Dn`，它们的笛卡尔积是所有可能 n 元组的集合：

```text
D1 x D2 x ... x Dn = { (d1, d2, ..., dn) | di 属于 Di }
```

#### 关系

关系是笛卡尔积的有限子集。

如果关系有 n 个属性，则称为 n 目关系。

### 2.4 关系的性质

关系作为规范化二维表，具有这些性质：

1. 每一列中的分量来自同一个域，是同类型数据。
2. 不同列可以来自同一个域，但属性名必须不同。
3. 列的顺序可以任意交换。
4. 任意两个元组不能完全相同。
5. 行的顺序可以任意交换。
6. 每个分量必须是不可再分的数据项。

考点：

- 关系中不允许重复元组。
- 行列顺序无关。
- 分量必须原子。

### 2.5 关系模式

关系模式是对关系的描述。

完整表示：

```text
R(U, D, DOM, F)
```

其中：

- `R`: 关系名。
- `U`: 属性名集合。
- `D`: 属性来自的域。
- `DOM`: 属性到域的映像。
- `F`: 属性间数据依赖集合。

通常简写为：

```text
R(U)
```

或：

```text
R(A1, A2, ..., An)
```

关系模式和关系的区别：

- 关系模式是型，是静态描述。
- 关系是值，是某一时刻的元组集合。

### 2.6 关系数据库

在一个给定应用领域中，所有关系的集合构成关系数据库。

关系数据库模式是这些关系模式的集合。

### 2.7 码

#### 候选码

设关系 `R` 的属性集为 `U`，`K` 是 `U` 的子集。

如果：

1. `K` 能唯一标识关系中的每一个元组。
2. `K` 的任何真子集都不能唯一标识元组。

则 `K` 是候选码。

记忆：

```text
候选码 = 最小唯一标识元组的属性集
```

#### 全码

如果关系模式的所有属性组合起来才是候选码，则称为全码。

#### 主码

若一个关系有多个候选码，选定其中一个作为主码。

#### 主属性

包含在任何候选码中的属性称为主属性。

#### 非主属性

不包含在任何候选码中的属性称为非主属性。

#### 外码

如果关系 `R` 的属性或属性组 `K` 不是 `R` 的主码，而是另一个关系 `S` 的主码，则称 `K` 为 `R` 的外码。

术语：

- `R`: 参照关系。
- `S`: 被参照关系或目标关系。

注意：

- 参照关系和被参照关系可以是同一个关系。
- 外码和对应主码不一定同名。
- 外码和对应主码必须定义在相同或相容的域上。

### 2.8 关系操作

关系操作对象和结果都是集合。

常见操作：

- 查询。
- 插入。
- 删除。
- 修改。

关系查询语言可分为：

- 关系代数语言。
- 关系演算语言。
- 兼具两者特点的语言，如 SQL。

### 2.9 关系完整性

关系模型的完整性约束包括：

- 实体完整性。
- 参照完整性。
- 用户定义完整性。

#### 实体完整性

规则：

```text
主码的任何属性都不能取空值
```

原因：

- 主码用于唯一标识元组。
- 若主码为空，就不能区分实体。

#### 参照完整性

若关系 `R` 的外码 `F` 参照关系 `S` 的主码 `K`，则 `R` 中每个元组在 `F` 上的取值必须：

- 等于 `S` 中某个元组的主码值；或
- 取空值，前提是外码允许为空。

例：

```text
SC.Sno 必须存在于 Student.Sno
SC.Cno 必须存在于 Course.Cno
```

#### 用户定义完整性

用户定义完整性是针对具体应用领域的约束。

例：

- 成绩必须在 0 到 100。
- 性别只能为男或女。
- 学分必须大于 0。
- 姓名不能为空。

### 2.10 关系代数概述

关系代数是一种抽象查询语言，用对关系的运算表达查询。

关系代数运算分为：

- 传统集合运算：并、差、交、笛卡尔积。
- 专门关系运算：选择、投影、连接、除。

### 2.11 并、差、交、笛卡尔积

这些运算要求参与运算的关系通常具有相同的目，且对应属性来自相同或相容的域。

#### 并

```text
R ∪ S
```

结果包含属于 `R` 或属于 `S` 的元组。

#### 差

```text
R - S
```

结果包含属于 `R` 但不属于 `S` 的元组。

#### 交

```text
R ∩ S
```

结果包含同时属于 `R` 和 `S` 的元组。

也可表示为：

```text
R ∩ S = R - (R - S)
```

#### 笛卡尔积

```text
R x S
```

若 `R` 有 m 个属性、k 个元组，`S` 有 n 个属性、l 个元组，则：

- `R x S` 有 `m+n` 个属性。
- `R x S` 有 `k*l` 个元组。

### 2.12 选择

选择从行的角度进行运算。

记号：

```text
σ_F(R)
```

含义：

- 从关系 `R` 中选出满足条件 `F` 的元组。

例：

```text
σ_所在省市='江苏南京'(CustomerInfo)
```

表示查询江苏南京的所有客户。

### 2.13 投影

投影从列的角度进行运算。

记号：

```text
π_A1,A2,...,Ak(R)
```

含义：

- 从关系 `R` 中选出若干属性列。
- 投影结果会自动去除重复元组。

例：

```text
π_客户编号,客户姓名(CustomerInfo)
```

### 2.14 连接

连接是从两个关系的笛卡尔积中选取满足条件的元组。

#### θ 连接

```text
R ⋈_{A θ B} S
```

等价于：

```text
σ_{A θ B}(R x S)
```

其中 `θ` 可以是 `=, <, >, <=, >=, <>`。

#### 等值连接

当 `θ` 为 `=` 时，称为等值连接。

#### 自然连接

自然连接是一种特殊等值连接：

- 自动按同名属性做等值连接。
- 结果中去掉重复的同名属性列。

### 2.15 除运算

除运算常用于表达“全部”“至少包含所有”的查询。

设：

```text
R(X, Y)
S(Y)
```

则：

```text
R ÷ S
```

结果是那些 `X` 值，使得对于 `S` 中每一个 `Y` 值，`(X,Y)` 都在 `R` 中出现。

典型题：

```text
查询选修了全部课程的学生
```

可理解为：

```text
π_Sno,Cno(SC) ÷ π_Cno(Course)
```

### 2.16 关系代数答题模板

写关系代数时先判断查询类型：

- 条件筛选：选择 `σ`。
- 取列：投影 `π`。
- 多表关联：连接 `⋈`。
- “或/合并”：并 `∪`。
- “有 A 没 B”：差 `-`。
- “同时满足”：交 `∩`。
- “全部”：除 `÷` 或双重差/双重否定思路。

例：查询选修 1 号课程学生的学号。

```text
π_Sno(σ_Cno='1'(SC))
```

例：查询选修 1 号课程学生的姓名。

```text
π_Sname(Student ⋈ σ_Cno='1'(SC))
```

## 3. SQL 概述

### 2.1 SQL 的含义

SQL 是 Structured Query Language，即结构化查询语言。

它是关系数据库的标准语言。

SQL 功能很强，能完成：

- 定义数据库结构。
- 查询数据。
- 插入、修改、删除数据。
- 定义视图。
- 控制访问权限。

### 2.2 SQL 的特点

#### 综合统一

SQL 集成：

- DDL：数据定义语言。
- DML：数据操纵语言。
- DCL：数据控制语言。

#### 高度非过程化

SQL 只需要说明“做什么”，不用说明“怎么做”。

例如查询学生姓名，只写查询条件，不需要写具体访问路径。

访问路径由 DBMS 优化器选择。

#### 面向集合

SQL 操作对象和结果都是集合。

一条 SQL 可以处理多个元组，而不是一次只处理一条记录。

#### 语法简洁

核心动词少：

- `CREATE`
- `DROP`
- `ALTER`
- `SELECT`
- `INSERT`
- `UPDATE`
- `DELETE`
- `GRANT`
- `REVOKE`

#### 可独立使用，也可嵌入使用

SQL 可以直接在数据库交互工具中执行，也可以嵌入高级语言程序。

### 2.3 SQL 组成

#### DDL

数据定义语言。

常用语句：

- `CREATE DATABASE`
- `CREATE TABLE`
- `ALTER TABLE`
- `DROP TABLE`
- `CREATE INDEX`
- `DROP INDEX`
- `CREATE VIEW`

#### DML

数据操纵语言。

常用语句：

- `SELECT`
- `INSERT`
- `UPDATE`
- `DELETE`

#### DCL

数据控制语言。

常用语句：

- `GRANT`
- `REVOKE`

## 4. SQL 数据定义

### 3.1 数据库定义

创建数据库：

```sql
CREATE DATABASE 数据库名;
```

删除数据库：

```sql
DROP DATABASE 数据库名;
```

### 3.2 基本表定义

基本格式：

```sql
CREATE TABLE 表名 (
    列名 数据类型 [列级约束],
    列名 数据类型 [列级约束],
    [表级约束]
);
```

常见数据类型：

- `char(n)`: 定长字符串。
- `varchar(n)`: 变长字符串。
- `int`: 整数。
- `float`: 浮点数。
- `datetime`: 日期时间。

### 3.3 常见约束

#### 主键约束

```sql
PRIMARY KEY
```

作用：

- 唯一标识元组。
- 不能取空值。
- 一个表只能有一个主键约束，但主键可以由多个列组成。

列级写法：

```sql
Sno char(9) PRIMARY KEY
```

表级写法：

```sql
PRIMARY KEY (Sno, Cno)
```

#### 外键约束

```sql
FOREIGN KEY (列名) REFERENCES 被参照表(列名)
```

作用：

- 保证参照完整性。
- 子表中的外键值必须在父表中存在，或按规则允许为空。

例：

```sql
FOREIGN KEY (Sno) REFERENCES Student(Sno)
```

#### 非空约束

```sql
NOT NULL
```

作用：该列不能取空值。

#### 唯一约束

```sql
UNIQUE
```

作用：该列或列组取值不能重复。

注意：

- `UNIQUE` 和 `PRIMARY KEY` 都能保证唯一。
- 主键不能空，唯一约束通常允许空值，具体取决于 DBMS。

#### 默认值约束

```sql
DEFAULT 默认值
```

例：

```sql
Ssex char(2) DEFAULT '男'
```

#### 检查约束

```sql
CHECK (条件)
```

例：

```sql
CHECK (Grade >= 0 AND Grade <= 100)
```

### 3.4 修改基本表

添加列：

```sql
ALTER TABLE 表名 ADD 列名 数据类型;
```

删除列：

```sql
ALTER TABLE 表名 DROP COLUMN 列名;
```

添加约束：

```sql
ALTER TABLE 表名 ADD CONSTRAINT 约束名 CHECK (条件);
```

删除约束：

```sql
ALTER TABLE 表名 DROP CONSTRAINT 约束名;
```

### 3.5 删除基本表

```sql
DROP TABLE 表名;
```

注意：

- 被其他表通过外键引用的表不能随便删除。
- 删除表会删除表结构和表中数据。

### 3.6 索引

索引用于加快查询速度。

创建索引：

```sql
CREATE INDEX 索引名 ON 表名(列名);
```

唯一索引：

```sql
CREATE UNIQUE INDEX 索引名 ON 表名(列名);
```

删除索引：

```sql
DROP INDEX 索引名;
```

注意：

- 索引能提高查询速度。
- 索引会占用存储空间。
- 更新数据时维护索引会产生额外开销。

## 5. SQL 数据查询

### 4.1 SELECT 基本结构

标准结构：

```sql
SELECT [DISTINCT] 目标列
FROM 表名
WHERE 条件
GROUP BY 分组列
HAVING 分组条件
ORDER BY 排序列 [ASC|DESC];
```

逻辑执行顺序：

```text
FROM
WHERE
GROUP BY
HAVING
SELECT
ORDER BY
```

### 4.2 单表查询

#### 查询全部列

```sql
SELECT *
FROM Student;
```

#### 查询指定列

```sql
SELECT Sno, Sname
FROM Student;
```

#### 去重

```sql
SELECT DISTINCT Sdept
FROM Student;
```

### 4.3 条件查询

常见条件：

- 比较：`=`, `<>`, `>`, `<`, `>=`, `<=`
- 范围：`BETWEEN ... AND ...`
- 集合：`IN`
- 字符串匹配：`LIKE`
- 空值：`IS NULL`
- 逻辑：`AND`, `OR`, `NOT`

#### BETWEEN

```sql
SELECT *
FROM Student
WHERE Sage BETWEEN 18 AND 22;
```

#### IN

```sql
SELECT *
FROM Student
WHERE Sdept IN ('CS', 'MA', 'IS');
```

#### LIKE

通配符：

- `%`: 任意长度字符串。
- `_`: 任意单个字符。

例：

```sql
SELECT *
FROM Student
WHERE Sname LIKE '刘%';
```

#### ESCAPE

当查询字符串本身含有 `%` 或 `_` 时，需要转义。

例：

```sql
SELECT Cno, Ccredit
FROM Course
WHERE Cname LIKE 'DB\_%' ESCAPE '\';
```

### 4.4 空值查询

判断空值必须使用：

```sql
IS NULL
IS NOT NULL
```

不能写：

```sql
= NULL
```

例：

```sql
SELECT Sno, Cno
FROM SC
WHERE Grade IS NULL;
```

### 4.5 排序

```sql
ORDER BY 列名 ASC
ORDER BY 列名 DESC
```

默认升序 `ASC`。

例：

```sql
SELECT Sno, Grade
FROM SC
WHERE Cno = '1'
ORDER BY Grade DESC;
```

### 4.6 聚集函数

常用聚集函数：

- `COUNT(*)`
- `COUNT(列名)`
- `SUM(列名)`
- `AVG(列名)`
- `MAX(列名)`
- `MIN(列名)`

注意：

- 除 `COUNT(*)` 外，聚集函数通常忽略空值。
- `COUNT(*)` 统计元组个数。
- `COUNT(列名)` 统计该列非空值个数。

### 4.7 分组查询

```sql
SELECT Cno, AVG(Grade)
FROM SC
GROUP BY Cno;
```

`WHERE` 与 `HAVING` 区别：

- `WHERE` 作用于分组前的元组。
- `HAVING` 作用于分组后的组。
- 聚集函数条件通常写在 `HAVING`。

例：

```sql
SELECT Cno, COUNT(*) AS Num
FROM SC
GROUP BY Cno
HAVING COUNT(*) > 3;
```

### 4.8 连接查询

#### 等值连接

```sql
SELECT Student.Sno, Sname, Cno, Grade
FROM Student, SC
WHERE Student.Sno = SC.Sno;
```

#### 自然连接

自然连接会去掉重复属性列。

SQL 中常用显式写法代替：

```sql
SELECT Student.Sno, Sname, Cno, Grade
FROM Student JOIN SC ON Student.Sno = SC.Sno;
```

#### 多表连接

```sql
SELECT Sname, Cname, Grade
FROM Student
JOIN SC ON Student.Sno = SC.Sno
JOIN Course ON SC.Cno = Course.Cno;
```

### 4.9 外连接

外连接不仅保留满足连接条件的行，还保留某一侧或两侧不匹配的行。

#### 左外连接

保留左表所有行。

```sql
SELECT Student.Sno, Sname, Cno, Grade
FROM Student LEFT JOIN SC
ON Student.Sno = SC.Sno;
```

适用题型：

- 查询所有学生及其选课情况。
- 即使学生没有选课，也要显示学生信息。

#### 右外连接

保留右表所有行。

```sql
SELECT *
FROM A RIGHT JOIN B
ON A.id = B.id;
```

#### 全外连接

保留两边所有行。

```sql
SELECT *
FROM A FULL JOIN B
ON A.id = B.id;
```

### 4.10 嵌套查询

嵌套查询是一个查询块嵌套在另一个查询块的 `WHERE` 或 `HAVING` 条件中。

#### IN

例：查询选修了 1 号课程的学生姓名。

```sql
SELECT Sname
FROM Student
WHERE Sno IN (
    SELECT Sno
    FROM SC
    WHERE Cno = '1'
);
```

#### 比较运算符

当子查询只返回一个值时，可以用比较运算符。

```sql
SELECT Sno, Grade
FROM SC
WHERE Grade > (
    SELECT AVG(Grade)
    FROM SC
);
```

#### ANY

`> ANY` 表示大于子查询结果中的某一个值，本质是大于最小值。

```sql
SELECT *
FROM SC
WHERE Grade > ANY (
    SELECT Grade
    FROM SC
    WHERE Cno = '1'
);
```

#### ALL

`> ALL` 表示大于子查询结果中的所有值，本质是大于最大值。

#### EXISTS

`EXISTS` 只关心子查询是否返回结果。

例：查询至少选修一门课程的学生。

```sql
SELECT *
FROM Student S
WHERE EXISTS (
    SELECT *
    FROM SC
    WHERE SC.Sno = S.Sno
);
```

`NOT EXISTS` 常用于表达“全部”语义。

### 4.11 集合查询

集合操作要求参与操作的查询结果列数相同，列类型相容。

#### UNION

并集，默认去重。

```sql
SELECT Sno FROM SC WHERE Cno = '1'
UNION
SELECT Sno FROM SC WHERE Cno = '2';
```

#### UNION ALL

并集，不去重。

#### INTERSECT

交集。

```sql
SELECT Sno FROM SC WHERE Cno = '1'
INTERSECT
SELECT Sno FROM SC WHERE Cno = '2';
```

#### EXCEPT

差集。

```sql
SELECT Sno FROM SC WHERE Cno = '1'
EXCEPT
SELECT Sno FROM SC WHERE Cno = '2';
```

## 6. SQL 数据更新

### 5.1 插入元组

```sql
INSERT INTO 表名 [(列1, 列2, ...)]
VALUES (值1, 值2, ...);
```

注意：

- 如果省略列名，必须按建表列顺序给所有列赋值。
- 如果指定部分列，未指定列取默认值或空值。
- 若列有 `NOT NULL` 且无默认值，则必须赋值。

### 5.2 插入子查询结果

```sql
INSERT INTO 表名 (列1, 列2)
SELECT 列1, 列2
FROM 另一个表
WHERE 条件;
```

要求：

- 子查询结果列数和目标列数一致。
- 数据类型相容。

### 5.3 修改数据

```sql
UPDATE 表名
SET 列名 = 表达式
WHERE 条件;
```

例：

```sql
UPDATE SC
SET Grade = Grade + 5
WHERE Cno = '1';
```

注意：

- 不写 `WHERE` 会修改全表。
- 修改主键或外键可能违反完整性约束。

### 5.4 删除数据

```sql
DELETE FROM 表名
WHERE 条件;
```

注意：

- 不写 `WHERE` 会删除全表数据。
- `DELETE` 删除元组，不删除表结构。
- `DROP TABLE` 删除表结构和数据。

### 5.5 更新操作与完整性

插入、修改、删除时 DBMS 会检查：

- 实体完整性。
- 参照完整性。
- 用户定义完整性。

例如：

- 插入重复主键会失败。
- 插入不存在的外键值会失败。
- 删除被引用的父表元组可能失败或触发级联操作。
- 成绩超过 `0-100` 会违反 `CHECK`。

## 7. 视图

### 6.1 视图概念

视图是从一个或多个基本表或视图导出的表。

特点：

- 视图是虚表。
- 数据库中只保存视图定义，不一定保存视图数据。
- 查询视图时，DBMS 根据视图定义从基本表中取数据。

### 6.2 创建视图

```sql
CREATE VIEW 视图名 [(列名列表)]
AS
SELECT 查询语句
[WITH CHECK OPTION];
```

例：

```sql
CREATE VIEW CS_Student
AS
SELECT Sno, Sname, Sage
FROM Student
WHERE Sdept = 'CS';
```

### 6.3 WITH CHECK OPTION

作用：

- 通过视图进行插入或修改时，必须满足视图定义中的条件。

例：

```sql
CREATE VIEW CS_Student
AS
SELECT *
FROM Student
WHERE Sdept = 'CS'
WITH CHECK OPTION;
```

通过该视图插入学生时，`Sdept` 必须是 `CS`。

### 6.4 删除视图

```sql
DROP VIEW 视图名;
```

删除视图不删除基本表数据。

### 6.5 视图作用

视图的作用：

- 简化用户操作。
- 使用户从多角度看同一数据。
- 提高逻辑独立性。
- 提供安全保护。
- 可以屏蔽复杂查询。

### 6.6 视图更新限制

并非所有视图都可更新。

通常不可更新的视图包括：

- 含聚集函数。
- 含 `GROUP BY`。
- 含 `DISTINCT`。
- 含集合操作。
- 含多表连接且无法唯一对应基本表元组。
- 含计算列。

可更新视图一般要求：

- 来源于单个基本表。
- 包含主键或足够定位元组的列。
- 不包含聚集、分组、去重等操作。

### 7.1 授权

```sql
GRANT 权限列表

TO 用户列表

```

例：

```sql
GRANT SELECT

TO user1;
```

允许用户继续授权：

```sql
GRANT INSERT
```

## 9. 数据库设计

### 8.1 数据库设计含义

广义数据库设计：

- 数据库及其应用系统的设计。

狭义数据库设计：

- 数据库本身的设计，即设计数据库各级模式。

基本任务：

- 根据用户需求设计数据库结构。
- 构造最优数据库模式。
- 建立数据库及其应用系统。
- 使系统能有效存储和管理数据。

### 8.2 数据库设计特点

数据库设计不是单纯写表结构，它同时涉及：

- 数据。
- 处理。
- 约束。
- 应用环境。
- 用户需求。

特点：

- 结构设计和行为设计结合。
- 数据设计和应用设计结合。
- 需要反复迭代。
- 需求分析非常重要。

### 8.3 数据库设计六阶段

经典六阶段：

1. 需求分析。
2. 概念结构设计。
3. 逻辑结构设计。
4. 物理结构设计。
5. 数据库实施。
6. 数据库运行和维护。

### 8.4 需求分析

需求分析目标：

- 准确了解用户的信息需求。
- 准确了解用户的处理需求。
- 明确系统边界。
- 建立数据字典和数据流图。

调查内容：

- 组织机构。
- 业务流程。
- 数据流程。
- 数据项。
- 数据结构。
- 数据存储。
- 数据处理。
- 安全性和完整性要求。

常用工具：

- 数据流图 DFD。
- 数据字典 DD。

### 8.5 数据字典

数据字典记录系统中各类数据对象的定义。

常包含：

- 数据项。
- 数据结构。
- 数据流。
- 数据存储。
- 处理过程。

作用：

- 对需求分析结果做规范描述。
- 后续概念结构设计的重要依据。

### 8.6 概念结构设计

概念结构设计目标：

- 把用户需求抽象为独立于具体 DBMS 的概念模型。

特点：

- 能真实反映现实世界。
- 易于理解。
- 易于修改。
- 易于转换为关系模型。

常用工具：

- E-R 模型。

### 8.7 E-R 模型

基本元素：

- 实体。
- 属性。
- 联系。

#### 实体

客观存在并可相互区别的事物。

例：

- 学生。
- 课程。
- 教师。
- 客户。
- 商品。

#### 属性

实体具有的特征。

例：

- 学生的学号、姓名、性别、年龄。
- 商品的编号、名称、单价。

#### 码

能唯一标识实体的属性或属性组。

例：

- 学号唯一标识学生。
- 商品编号唯一标识商品。

#### 联系

实体之间的关联。

类型：

- 1:1。
- 1:n。
- m:n。

### 8.8 E-R 图集成冲突

当多个局部 E-R 图集成为全局 E-R 图时，会出现冲突。

#### 属性冲突

同一属性在不同局部图中定义不一致。

例：

- 性别在一个系统中用“男/女”，另一个系统中用 `0/1`。

处理：

- 统一类型。
- 统一取值范围。
- 统一单位。

#### 命名冲突

包括：

- 同名异义。
- 异名同义。

例：

- 一个局部应用把教室称为“房间”，另一个把宿舍称为“房间”。
- 一个系统叫“客户”，另一个叫“顾客”，实际含义相同。

处理：

- 统一命名。
- 保留清晰语义。

#### 结构冲突

同一对象在不同局部图中抽象方式不同。

例：

- 某对象在一个局部图中作为实体，在另一个局部图中作为属性。
- 同一联系的类型不同。

处理：

- 按全局语义重新建模。
- 合并冗余联系和实体。

### 8.9 E-R 图到关系模式转换

#### 实体转换

一个实体型转换为一个关系模式。

实体属性转换为关系属性。

实体码转换为关系码。

#### 1:1 联系转换

方法：

- 可转换为独立关系模式。
- 也可将一方主键加入另一方作为外键，并加入联系属性。

#### 1:n 联系转换

常用方法：

- 在 n 端关系中加入 1 端主键作为外键。
- 同时加入联系属性。

例：

```text
系(系号, 系名)
学生(学号, 姓名, 系号)
```

#### m:n 联系转换

必须转换为一个独立关系模式。

该关系模式包含：

- 两端实体的主键。
- 联系本身的属性。

其主键通常是两端主键的组合。

例：

```text
学生(学号, 姓名)
课程(课程号, 课程名)
选课(学号, 课程号, 成绩)
```

`选课` 的主键通常为 `(学号, 课程号)`。

### 8.10 逻辑结构设计

逻辑结构设计目标：

- 把概念模型转换为具体 DBMS 支持的数据模型。

对关系数据库来说，就是转换为：

- 关系模式。
- 主键。
- 外键。
- 完整性约束。
- 视图。

### 8.11 物理结构设计

物理结构设计关注数据库在存储设备上的实现。

内容：

- 存储结构。
- 存取方法。
- 索引设计。
- 聚簇设计。
- 数据分布。

目标：

- 提高访问效率。
- 降低存储开销。
- 满足响应时间和吞吐量要求。

### 8.12 数据库运行与维护

运行维护包括：

- 数据库装载。
- 试运行。
- 性能监控。
- 性能调整。
- 安全性维护。
- 完整性维护。
- 备份和恢复。
- 数据库重组织和重构造。

## 10. 关系规范化理论

### 9.1 为什么需要规范化

不好的关系模式会造成：

- 数据冗余。
- 插入异常。
- 删除异常。
- 修改异常。

#### 数据冗余

同一数据重复存储。

后果：

- 浪费空间。
- 更新时容易不一致。

#### 插入异常

应该能插入的数据因为缺少其他信息而不能插入。

例：

- 想插入新商品信息，但没有客户订购它，若商品信息和订购信息混在一个表里，就无法插入。

#### 删除异常

删除某些数据时，不该丢失的信息也被删除。

例：

- 删除最后一条订购记录时，商品基本信息也丢失。

#### 修改异常

同一信息重复出现，修改时必须多处修改，否则不一致。

例：

- 商品单价出现在多条订购记录中，改价时漏改某条。

### 9.2 函数依赖

设关系模式 `R(U)`，`X` 和 `Y` 是属性集 `U` 的子集。

如果对 `R` 的任意一个可能关系 `r`，任意两个元组在 `X` 上取值相等，则在 `Y` 上取值也相等，则称：

```text
X -> Y
```

读作：`X` 函数决定 `Y`，或 `Y` 函数依赖于 `X`。

例：

```text
学号 -> 姓名
学号 -> 所在系
课程号 -> 课程名
(学号, 课程号) -> 成绩
```

### 9.3 平凡与非平凡函数依赖

若 `Y` 是 `X` 的子集，则 `X -> Y` 是平凡函数依赖。

例：

```text
(学号, 课程号) -> 学号
```

若 `Y` 不是 `X` 的子集，则是非平凡函数依赖。

例：

```text
学号 -> 姓名
```

### 9.4 完全函数依赖与部分函数依赖

设 `X -> Y`，如果 `Y` 不依赖于 `X` 的任何真子集，则称 `Y` 完全函数依赖于 `X`。

记作：

```text
X -F-> Y
```

如果 `Y` 依赖于 `X` 的某个真子集，则称 `Y` 部分函数依赖于 `X`。

例：

```text
(学号, 课程号) -> 成绩
```

通常是完全依赖。

```text
(学号, 课程号) -> 姓名
```

因为 `学号 -> 姓名`，所以姓名部分依赖于组合码。

### 9.5 传递函数依赖

若：

```text
X -> Y
Y -> Z
Y 不决定 X
Z 不属于 Y
```

则称 `Z` 传递函数依赖于 `X`。

例：

```text
学号 -> 所在系
所在系 -> 系主任
```

所以：

```text
学号 -> 系主任
```

是传递依赖。

### 9.6 码

#### 候选码

若属性集 `K` 能函数决定关系模式 `R` 的全部属性，且 `K` 的任何真子集都不能决定全部属性，则 `K` 是候选码。

记忆：

```text
候选码 = 最小的能决定全部属性的属性集
```

#### 超码

能决定全部属性，但不一定最小。

候选码一定是超码，超码不一定是候选码。

#### 主码

从候选码中选定一个作为主码。

#### 主属性

包含在任一候选码中的属性。

#### 非主属性

不包含在任何候选码中的属性。

### 9.7 第一范式 1NF

定义：

- 关系中每个属性都是不可再分的数据项。

也就是属性值必须是原子值。

不满足 1NF 的例子：

```text
学生(学号, 姓名, 联系方式)
```

如果联系方式里同时存手机、邮箱、QQ，就不是原子值。

### 9.8 第二范式 2NF

定义：

- `R` 属于 1NF。
- 每个非主属性完全函数依赖于码。

也就是：

```text
2NF 消除非主属性对码的部分依赖
```

典型问题：

组合码中，某些非主属性只依赖组合码的一部分。

例：

```text
选课(学号, 课程号, 姓名, 课程名, 成绩)
```

候选码：

```text
(学号, 课程号)
```

依赖：

```text
学号 -> 姓名
课程号 -> 课程名
(学号, 课程号) -> 成绩
```

姓名、课程名都部分依赖于组合码，因此不满足 2NF。

分解：

```text
学生(学号, 姓名)
课程(课程号, 课程名)
选课(学号, 课程号, 成绩)
```

### 9.9 第三范式 3NF

定义：

- `R` 属于 2NF。
- 每个非主属性不传递依赖于码。

也就是：

```text
3NF 消除非主属性对码的传递依赖
```

例：

```text
学生(学号, 姓名, 所在系, 系主任)
```

依赖：

```text
学号 -> 所在系
所在系 -> 系主任
```

所以：

```text
学号 -> 系主任
```

是传递依赖。

分解：

```text
学生(学号, 姓名, 所在系)
系(所在系, 系主任)
```

### 9.10 BCNF

BCNF 比 3NF 更严格。

定义：

- 对每个非平凡函数依赖 `X -> Y`，`X` 都必须包含候选码。

记忆：

```text
BCNF 要求每个决定因素都是码
```

3NF 和 BCNF 区别：

- 3NF 允许某些决定因素不是码，只要被决定的是主属性。
- BCNF 不允许这种情况。

### 9.11 范式判断步骤

1. 写出属性集和函数依赖集。
2. 求候选码。
3. 标出主属性和非主属性。
4. 判断是否 1NF。
5. 看非主属性是否部分依赖于候选码，若有则不是 2NF。
6. 看非主属性是否传递依赖于候选码，若有则不是 3NF。
7. 对每个非平凡依赖 `X -> Y`，看 `X` 是否为超码，若都满足则是 BCNF。

### 9.12 Armstrong 公理

#### 自反律

若 `Y` 是 `X` 的子集，则：

```text
X -> Y
```

#### 增广律

若：

```text
X -> Y
```

则：

```text
XZ -> YZ
```

#### 传递律

若：

```text
X -> Y
Y -> Z
```

则：

```text
X -> Z
```

### 9.13 常用推理规则

#### 合并律

若：

```text
X -> Y
X -> Z
```

则：

```text
X -> YZ
```

#### 分解律

若：

```text
X -> YZ
```

则：

```text
X -> Y
X -> Z
```

#### 伪传递律

若：

```text
X -> Y
WY -> Z
```

则：

```text
WX -> Z
```

### 9.14 属性闭包

属性集 `X` 关于函数依赖集 `F` 的闭包记为：

```text
X+
```

含义：

- 在 `F` 推导下，`X` 能决定的所有属性集合。

求闭包步骤：

1. 初始 `X+ = X`。
2. 对每个依赖 `A -> B`，如果 `A` 包含于 `X+`，则把 `B` 加入 `X+`。
3. 重复直到不能增加属性。

用途：

- 判断 `X` 是否为超码。
- 求候选码。
- 判断函数依赖是否被蕴含。

### 9.15 模式分解

模式分解是把一个低级范式关系模式分解为若干高级范式关系模式。

好的分解应满足：

- 无损连接。
- 保持函数依赖。

#### 无损连接

分解后自然连接能还原原关系，不产生多余元组。

二元分解判定：

设 `R` 分解为 `R1` 和 `R2`。

如果：

```text
(R1 ∩ R2) -> R1
```

或：

```text
(R1 ∩ R2) -> R2
```

则分解具有无损连接性。

#### 保持函数依赖

分解后各子模式上的依赖能够推出原依赖集。

意义：

- 完整性约束可以在单个子关系上检查。
- 不需要连接后才能检查依赖。

## 11. 并发控制

### 10.1 为什么需要并发控制

数据库是共享资源，多个用户可能同时访问同一数据。

如果不控制并发操作，可能：

- 读取错误数据。
- 覆盖别人修改。
- 破坏一致性。

并发控制的目标：

- 保证事务隔离性。
- 保证数据库一致性。
- 尽量提高并发度。

### 10.2 事务

事务是一系列数据库操作的有限序列，是数据库的基本执行单元。

事务是：

- 并发控制的基本单位。
- 恢复的基本单位。

### 10.3 ACID

#### 原子性 Atomicity

事务中的操作要么全做，要么全不做。

故障时需要撤销未完成事务。

#### 一致性 Consistency

事务执行前后，数据库都必须处于一致状态。

例如转账：

- A 减少 100。
- B 增加 100。
- 总金额不变。

#### 隔离性 Isolation

并发执行的事务之间不能互相干扰。

一个事务的中间结果不能被其他事务随意看到。

#### 持久性 Durability

事务一旦提交，其对数据库的改变必须永久保存。

即使系统故障，也不能丢失已提交事务的结果。

### 10.4 事务活动过程

事务可能经历：

- 开始。
- 读写。
- 提交 `COMMIT`。
- 回滚 `ROLLBACK`。
- 失败。

### 10.5 并发执行导致的问题

#### 丢失修改

两个事务读入同一数据并修改，后提交的结果覆盖先提交的结果。

例：

```text
T1 读 A=16
T2 读 A=16
T1 A=A-1 写回 15
T2 A=A-1 写回 15
```

实际卖出两张票，却只减少一张。

#### 脏读

也叫读未提交数据。

事务 T1 修改数据后尚未提交，T2 读取了该数据。随后 T1 回滚，T2 读到的就是无效数据。

#### 不可重复读

T1 第一次读取某数据后，T2 修改并提交该数据，T1 再次读取时结果不同。

广义不可重复读还包括：

- 读取结果集合中的记录被插入或删除。
- 统计结果前后不一致。

### 10.6 调度与可串行化

调度是多个事务操作组成的执行序列。

串行调度：

- 事务一个接一个执行，没有交叉。

可串行化调度：

- 并发调度的结果与某个串行调度结果等价。

可串行化是并发调度正确性的准则。

### 10.7 封锁

封锁是实现并发控制的重要技术。

基本思想：

- 事务访问某数据前先申请锁。
- 如果锁不相容，则等待。
- 访问结束后释放锁。

### 10.8 X 锁与 S 锁

#### 排他锁 X 锁

也叫写锁。

如果事务 T 对数据 A 加 X 锁：

- T 可以读 A。
- T 可以写 A。
- 其他事务不能再对 A 加任何锁。

#### 共享锁 S 锁

也叫读锁。

如果事务 T 对数据 A 加 S 锁：

- T 可以读 A。
- T 不能写 A。
- 其他事务可以再对 A 加 S 锁。
- 其他事务不能对 A 加 X 锁。

### 10.9 锁相容矩阵

```text
        已有 S   已有 X
申请 S    是      否
申请 X    否      否
```

记忆：

- 读读相容。
- 读写冲突。
- 写写冲突。

### 10.10 三级封锁协议

#### 一级封锁协议

规则：

- 事务在修改数据前必须先加 X 锁。
- X 锁直到事务结束才释放。

解决：

- 防止丢失修改。

不能解决：

- 脏读。
- 不可重复读。

#### 二级封锁协议

规则：

- 一级封锁协议。
- 事务读数据前必须先加 S 锁。
- 读完即可释放 S 锁。

解决：

- 防止丢失修改。
- 防止脏读。

不能完全解决：

- 不可重复读。

#### 三级封锁协议

规则：

- 一级封锁协议。
- 事务读数据前必须先加 S 锁。
- S 锁直到事务结束才释放。

解决：

- 防止丢失修改。
- 防止脏读。
- 保证可重复读。

### 10.11 两段锁协议

两段锁协议要求事务分两个阶段：

#### 加锁阶段

事务可以申请锁，但不能释放锁。

#### 解锁阶段

事务可以释放锁，但不能再申请新锁。

性质：

- 两段锁协议是可串行化调度的充分条件。
- 不是必要条件。
- 遵守两段锁的事务可能发生死锁。

注意：

- “遵守两段锁一定可串行化”是对的。
- “可串行化一定遵守两段锁”是错的。

## 12. 数据库恢复

### 11.1 故障类型

常见故障：

- 事务故障。
- 系统故障。
- 介质故障。

#### 事务故障

事务在正常结束前被终止。

原因：

- 输入错误。
- 运算溢出。
- 违反完整性约束。
- 死锁被撤销。

恢复：

- 撤销该事务已做的修改，即 UNDO。

#### 系统故障

系统停止运行，内存内容丢失，但外存数据库未破坏。

原因：

- 停电。
- 操作系统故障。
- DBMS 崩溃。

恢复：

- 撤销未完成事务。
- 重做已提交但尚未写入数据库的事务。

#### 介质故障

外存介质损坏，数据库本身被破坏。

原因：

- 磁盘损坏。
- 磁头碰撞。
- 文件损坏。

恢复：

- 使用备份副本恢复数据库。
- 利用日志重做备份后的已提交事务。

### 11.2 恢复基本原理

数据库恢复依靠冗余数据。

冗余数据包括：

- 数据库备份。
- 日志文件。

基本思想：

```text
备份 + 日志 = 恢复到一致状态
```

### 11.3 数据转储

数据转储是 DBA 定期把数据库复制到其他存储介质的过程。

#### 静态转储

转储期间不允许对数据库进行存取和修改。

优点：

- 实现简单。
- 副本一致。

缺点：

- 降低数据库可用性。

#### 动态转储

转储期间允许数据库继续运行。

优点：

- 可用性高。

缺点：

- 转储副本可能不是一致状态。
- 必须配合日志文件恢复。

#### 海量转储

也叫全量备份。

每次备份整个数据库。

#### 增量转储

只备份上次转储后更新过的数据。

优点：

- 备份量小。
- 速度快。

缺点：

- 恢复时需要多个备份和日志。

### 11.4 日志文件

日志文件记录事务对数据库的更新操作。

日志通常记录：

- 事务开始。
- 事务提交。
- 事务中止。
- 更新前值。
- 更新后值。
- 更新对象。

日志作用：

- 支持事务故障恢复。
- 支持系统故障恢复。
- 支持介质故障恢复。

### 11.5 恢复策略

#### 事务故障恢复

对未完成事务执行 UNDO。

恢复到事务开始前状态。

#### 系统故障恢复

系统重启时自动完成。

步骤：

1. 根据日志找出故障时未完成事务和已提交事务。
2. 对未完成事务执行 UNDO。
3. 对已提交但可能未写入数据库的事务执行 REDO。

#### 介质故障恢复

步骤：

1. 装入最近一次数据库备份。
2. 从日志中找出备份后已提交事务。
3. 对这些事务执行 REDO。
4. 恢复到故障前一致状态。
