# 练习答案与评分标准

## A. 数据结构与 key

### 1. 结构选择（8 分）

- 模板缓存：String JSON 或 Hash，取决于是否需要字段级更新；通常整对象 String 更简单。（2 分）
- 滑动窗口：ZSet，score 保存时间，支持范围删除和计数。（2 分）
- 临时去重：String `SET NX TTL` 或 Set；需要单对象状态时优先 String。（2 分）
- 任务进度：String JSON 或小 Hash，最终状态仍在 MySQL。（2 分）

### 2. 租户、版本和 hash tag（7 分）

租户维度避免串数据和冲突；版本支持 schema/缓存灰度隔离。hash tag 让多 key 同槽以支持多 key 操作，但可能把大租户集中到单 slot，形成热点和扩展瓶颈。

## B. 原子性与事务

### 1. 四类工具（8 分）

- 单命令：最低成本原子状态变化。（2 分）
- `MULTI/EXEC`：连续执行一组已排队命令，不被其他客户端插入。（2 分）
- `WATCH`：乐观锁，key 变化则放弃事务并重试。（2 分）
- Lua：服务端执行判断和多命令组合，消除客户端往返竞态。（2 分）

### 2. 与 MySQL 差异（4 分）

Redis 事务没有数据库式执行阶段回滚、隔离级别和持久化原子语义；某条命令执行错误时其他命令仍可能执行。Redis `MULTI/EXEC` 主要保证排队命令连续执行。

### 3. `INCR`/`EXPIRE`（8 分）

客户端在 `INCR` 成功后、`EXPIRE` 前崩溃，key 无 TTL，窗口永不重置。（3 分）

参考 Lua：（3 分）

```lua
local value = redis.call('INCR', KEYS[1])
if value == 1 then
  redis.call('EXPIRE', KEYS[1], ARGV[1])
end
return value
```

还需限制 key 维度、TTL、返回值和脚本执行复杂度。（2 分）

## C. 缓存工程

### 1. Cache Aside（4 分）

读缓存，miss 读库并回填；写时先提交数据库，再删除缓存。缓存不可用时回源或按策略降级。

### 2. 竞态与失败（6 分）

- DB 成功、删除缓存失败。（2 分）
- 旧读请求在删除后回填旧值。（2 分）
- 多实例同时重建导致击穿。（1 分）
- 删除/重建消息重复、乱序或丢失。（1 分）

治理包括 TTL、Outbox/CDC 失效、版本校验、single-flight 和强一致路径绕缓存。

### 3. 三类问题（6 分）

- 穿透：查询不存在；参数校验、空值短缓存/Bloom Filter。（2 分）
- 击穿：单热点失效；互斥/单飞、逻辑过期或提前刷新。（2 分）
- 雪崩：大量同时失效或 Redis 故障；TTL 抖动、限流降级/多级缓存。（2 分）

### 4. 命中率边界（4 分）

高命中率仍可能存在单 key 热点、大 key、慢序列化、网络拥塞、P99 抖动、淘汰和陈旧数据。必须联合业务正确性、尾延迟和资源指标评估。

## D. 限流与幂等

### 1. 固定窗口（4 分）

窗口独立重置，前一窗口末尾和后一窗口开头可在很短时间内各通过一整份额度，形成约两倍瞬时突发。

### 2. 三算法（6 分）

- 固定窗口：简单低成本，边界突发明显。（2 分）
- 滑动窗口日志：精确，ZSet 内存和维护成本高。（2 分）
- 令牌桶：支持平均速率和受控突发，状态计算较复杂，通常用 Lua。（2 分）

### 3. 幂等兜底（5 分）

MySQL 对 `(tenant_id,idempotency_key)` 建唯一约束并保存结果。Redis 只快速占位和缓存结果引用；key 丢失时查询/写数据库，唯一冲突后返回已有结果。

### 4. Agent 工具故障策略（5 分）

设备控制、创建工单、支付等高风险副作用通常 fail-closed 或使用保守本地额度，因为重复/过载代价高。只读检索等低风险操作可 fail-open。决策依据是安全、下游容量、用户影响和补偿能力。

## E. 高可用、锁与排障

### 1. 复制与 `WAIT`（5 分）

Redis 默认异步复制，主确认时副本可能未持有写。`WAIT` 只确认副本接收数量，不把故障转移、持久化和分区协议变成强一致共识，因此仍存在已确认写丢失窗口。

### 2. Sentinel（4 分）

quorum 用于多个 Sentinel 同意主节点下线；实际 failover 还需选出 leader，并获得 Sentinel 多数授权。两者阈值和职责不同。

### 3. Cluster（5 分）

key 映射到 16384 slot；hash tag 让多个 key 同槽；异步复制和网络分区导致已确认写可能丢失，少数分区停止服务，多数分区满足副本条件后恢复。

### 4. owner 校验（4 分）

锁过期后新客户端可能获得同一 key。旧客户端恢复执行普通 `DEL` 会删掉新锁。唯一 value 标识 owner，释放时比较再删，避免误删。

### 5. fencing token（3 分）

每次持有权生成递增 token，下游拒绝小于已见最大 token 的旧请求，从而阻止暂停后恢复的旧持有者写入。

### 6. 排障顺序（4 分）

业务时间线 → 应用连接/网络 → slowlog/阻塞命令 → 大 key/热 key → 内存与 eviction → fork/AOF/THP/swap → 复制和 failover。只列工具不解释顺序最多 2 分。

| 机制解释 | 20% |

## 总评

- 90-100：进入 Redis 架构和故障答辩。
- 80-89：补做一个高可用或大 key 实验。
- 60-79：重做原子限流与缓存击穿。
- 低于 60：返回数据结构、TTL 和原子性基础。
