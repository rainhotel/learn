## 学习目标

完成本章后，学习者能够：

1. 从方法调用链解释 Spring 声明式事务的工作机制。
2. 判断一次调用是否真正经过事务代理。
3. 正确配置异常回滚规则并识别“捕获异常后仍回滚”的情况。
4. 区分逻辑事务和物理事务，选择合适的传播行为。
5. 识别事务与线程、网络调用、消息发送之间的边界。
6. 为 NotifyFlow 设计短事务、Outbox、幂等和补偿链路。

## 为什么要学

`@Transactional` 很容易写，却经常被错误理解成“给方法加一个数据库开关”。真实系统中，更常见的问题不是不会写注解，而是：

- 注解存在，但调用没有经过代理。
- 异常被捕获，调用方以为事务会提交，实际已被标记为 rollback-only。
- 检查异常抛出后，数据库数据意外提交。
- 一个长事务持锁调用第三方 API，拖垮连接池和并发能力。
- 新线程写数据库，却不在原事务中。
- 数据库提交成功，但消息没有发送；或者消息已发送，数据库又回滚。

这些问题直接关系到订单、支付、通知、任务调度和 Agent 工具执行的可靠性。

## 问题场景

NotifyFlow 接收到创建通知请求：

1. 校验租户和模板。
2. 插入 `notification_task`。
3. 写入审计记录。
4. 调用短信供应商。
5. 把任务更新为 `SENT`。

如果把五步全部放在一个 `@Transactional` 方法中，会产生错误预期：数据库事务只能协调它管理的数据资源，不能撤销已经发生的 HTTP 请求、短信发送或外部 Agent 工具副作用。

本章的目标不是“让所有步骤都在一个大事务中”，而是识别原子边界，缩短数据库事务，并用 Outbox、幂等、状态机和补偿连接多个边界。

## 问题地图

```text
调用是否经过代理？
  ├─ 否：事务 advice 不执行
  └─ 是：解析事务属性
       ├─ 当前是否已有事务？
       │    ├─ REQUIRED：加入或新建
       │    ├─ REQUIRES_NEW：挂起外层并新建
       │    └─ NESTED：通常建立 Savepoint
       ├─ 执行业务方法
       └─ 根据退出方式决定提交或回滚
            ├─ RuntimeException / Error：默认回滚
            ├─ checked exception：默认不回滚
            └─ rollbackFor / noRollbackFor：覆盖默认规则
```

## 一、Spring 管理的到底是什么

### 1. 事务抽象

Spring 通过 `TransactionManager` 抽象具体事务资源。传统 JDBC 场景常见的是 `PlatformTransactionManager` 的实现，例如 `DataSourceTransactionManager`。

应用不应把 `@Transactional` 理解成固定绑定某一种数据库。它描述的是事务属性：

- propagation：如何处理已有事务。
- isolation：隔离级别。
- timeout：超时。
- readOnly：只读提示。
- rollback rules：哪些异常触发回滚。

事务管理器把这些属性映射到具体资源的事务能力。

### 2. 逻辑事务与物理事务

逻辑事务是方法层看到的事务范围；物理事务是数据库连接上的真实事务。

多个 `REQUIRED` 方法可以各自形成逻辑事务范围，但共同使用同一个物理事务。某个内层逻辑范围把事务标记为 rollback-only，会影响整个物理事务。

这一区分是理解 `UnexpectedRollbackException` 的基础。

## 二、声明式事务为什么依赖代理

### 1. 调用链

代理模式下，一次正常调用大致如下：

```text
Controller / 调用者
        |
        v
Spring AOP Proxy
        |
        v
TransactionInterceptor
  1. 读取事务属性
  2. 获取或加入事务
  3. 调用目标方法
  4. 提交或回滚
        |
        v
Target Service
```

`@Transactional` 只是元数据。Bean 必须被 Spring 管理，事务基础设施必须启用，并且调用必须进入代理，事务 advice 才有机会运行。

### 2. 自调用为什么绕过事务

```java
public void createBatch() {
    createOne();
}

@Transactional
public void createOne() {
    // insert task
}
```

外部调用 `createBatch()` 进入目标对象后，`createOne()` 是通过 `this` 发生的普通 Java 调用。它没有重新回到代理，因此 `createOne()` 上的事务 advice 不会执行。

更准确的说法是：

> 不是注解“失效”，而是这次方法调用没有经过负责解释注解的代理。

优先解决方式是拆分职责：让批处理编排服务调用另一个事务服务。自注入可以使用，但会增加理解成本；`AopContext.currentProxy()` 会让业务代码直接耦合 Spring AOP，不适合作为常规方案。

### 3. JDK 动态代理与类代理

Spring 核心 AOP 通常按目标类型选择接口代理或类代理：

| 维度 | JDK 动态代理 | CGLIB 类代理 |
|---|---|---|
| 基础 | 接口 | 生成目标类的子类 |
| 可代理方法 | 接口中公开的方法 | 可被子类覆盖的方法 |
| 主要限制 | 调用方通常面向接口 | `final` 类/方法、`private` 方法不能被覆盖增强 |
| 是否解决自调用 | 否 | 否 |

不要用“Spring 事务一定是 JDK 代理”或“一定是 CGLIB”回答面试。Spring Boot 的默认设置还可能影响代理类型。稳定结论是：代理类型有差异，但代理模式下自调用都不会重新经过代理。

## 三、回滚不是“有异常就回滚”

### 1. 默认规则

默认情况下：

- `RuntimeException` 及其子类：回滚。
- `Error`：回滚。
- 检查异常：不自动回滚。

```java
@Transactional
public void importTasks() throws IOException {
    jdbcTemplate.update("insert ...");
    throw new IOException("file damaged");
}
```

如果没有自定义规则，方法虽然抛出 `IOException`，插入仍可能提交。

### 2. 显式规则

```java
@Transactional(rollbackFor = IOException.class)
public void importTasks() throws IOException {
    // ...
}
```

优先使用异常类型，而不是宽泛的类名字符串。类型规则可以在编译期检查，字符串模式可能误匹配相似名称或嵌套类。

### 3. 异常必须离开代理调用边界

事务拦截器需要观察方法如何退出，才能应用回滚规则。如果业务代码捕获异常并正常返回，拦截器通常会按正常返回处理，除非：

- 事务此前已被标记为 rollback-only。
- 代码显式调用事务状态的 `setRollbackOnly()`。
- 底层资源在提交阶段失败。

因此，不要机械地在事务方法中 `catch (Exception)` 后只打印日志。

## 四、传播行为解决的是“已有事务怎么办”

### 1. `REQUIRED`

`REQUIRED` 是常见默认值：

- 当前没有事务：创建物理事务。
- 当前已有事务：加入现有物理事务。

适合一个服务门面调用多个仓储操作，并要求一起成功或失败的场景。

### 2. `UnexpectedRollbackException`

考虑以下流程：

```text
outer(REQUIRED) 开始物理事务
  -> inner(REQUIRED) 加入同一物理事务
  -> inner 发生运行时异常，事务被标记 rollback-only
  -> outer 捕获异常并继续
  -> outer 正常返回，尝试 commit
  -> Spring 发现只能 rollback
  -> 抛出 UnexpectedRollbackException
```

异常的意义是防止调用方误以为提交成功。外层捕获业务异常并不能清除共享物理事务的 rollback-only 状态。

### 3. `REQUIRES_NEW`

`REQUIRES_NEW` 总是使用独立物理事务。内层事务可以提交，而外层随后回滚。

典型用途是确实需要独立持久化的审计或失败记录，但不能滥用：

- 外层事务仍占用连接。
- 内层需要再申请一个连接。
- 并发线程都这样做时，连接池可能耗尽。
- 独立提交也可能破坏业务原子性，让数据更难解释。

使用前必须回答：为什么这条数据即使主业务失败也必须存在？连接池容量是否覆盖最坏并发？

### 4. `NESTED`

`NESTED` 通常在同一个物理事务中建立 JDBC Savepoint。它允许回滚到局部保存点，但不等于独立事务，也不保证适用于所有事务管理器和数据库资源。

## 五、事务上下文有线程边界

传统 `PlatformTransactionManager` 管理的事务通常绑定当前执行线程。方法里启动新线程：

```java
@Transactional
public void createTask() {
    insertTask();
    new Thread(this::insertAudit).start();
}
```

新线程不会自动继承原事务。两个线程可能使用不同连接、不同提交时机，异常也不会自然合并。

同理，`@Async` 不是“把当前事务搬到线程池”。异步方法若需要事务，应在异步执行线程中重新建立自己的明确事务边界。

反应式事务使用 Reactor Context，不能简单套用 ThreadLocal 的解释；本章实验只讨论传统命令式事务。

## 六、为什么外部调用不应放在长事务中

数据库事务可以回滚数据库变更，却不能撤销已经完成的：

- HTTP 请求。
- 短信、邮件、推送。
- MQ 已确认发送。
- 文件上传。
- Agent 工具调用或设备控制指令。

而且网络调用耗时不稳定。持有事务等待网络会：

- 长时间占用数据库连接。
- 延长行锁和间隙锁生命周期。
- 放大死锁与超时。
- 让供应商抖动传导到数据库。

可靠系统通常把流程拆成多个短事务，用持久化状态连接它们。

## 七、NotifyFlow 推荐事务边界

### 1. 创建阶段

一个短事务完成：

1. 校验与幂等占位。
2. 插入通知任务。
3. 插入 Outbox 事件。
4. 提交。

任务和待发布事件在同一数据库事务中原子写入。

### 2. 发布与消费阶段

Outbox Publisher 在事务外读取事件并发送到 MQ。发送可能重复，因此消费者必须按业务幂等键去重。发布成功后再用短事务更新 Outbox 状态。

### 3. 执行阶段

Worker 使用短事务领取任务并写入 owner、lease、version，提交后释放锁。随后在事务外调用供应商。

### 4. 确认阶段

供应商返回后，再开启短事务，以任务 id、owner/version 和当前状态作为条件更新：

- 成功：`SENT`。
- 可重试失败：`RETRY_WAIT`。
- 不可重试失败：`FAILED`。

数据库状态机、供应商幂等键和对账任务共同处理“调用结果未知”。

## 八、声明式与编程式事务怎么选

| 方案 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|
| `@Transactional` | 简洁、服务层语义清晰 | 依赖代理边界，复杂分段不直观 | 稳定的服务方法原子边界 |
| `TransactionTemplate` | 边界显式，适合分段和循环 | 模板代码更多，业务与事务 API 有耦合 | 批处理分块、局部事务、需要精确返回值 |
| `REQUIRES_NEW` | 独立提交或回滚 | 额外连接、语义复杂 | 必须独立保存的少量记录 |
| Outbox | 协调数据库状态与异步消息 | 最终一致、需要发布器和去重 | 通知、订单事件、跨服务副作用 |
| Saga/补偿 | 处理多步骤跨服务流程 | 设计与运维复杂 | 长流程、无法使用单库事务的业务 |

## 九、常见错误

### 错误一：同类调用事务方法

- 表现：注解存在，但没有预期的回滚或传播效果。
- 原因：调用绕过代理。
- 修复：按职责拆成两个 Bean，让调用经代理进入。
- 预防：为回滚结果写集成测试，不只检查注解存在。

### 错误二：检查异常默认不回滚

- 表现：导入失败但部分数据已经提交。
- 原因：默认回滚规则不包含检查异常。
- 修复：明确异常模型，必要时配置 `rollbackFor`。
- 预防：测试每类业务异常的提交/回滚结果。

### 错误三：捕获异常后假装成功

- 表现：最终得到 `UnexpectedRollbackException`，或者错误数据提交。
- 原因：异常传播和 rollback-only 状态没有被正确理解。
- 修复：不要吞异常；需要降级时重新设计事务边界。

### 错误四：事务中调用供应商

- 表现：连接池耗尽、锁等待、吞吐骤降。
- 原因：把数据库原子性错误扩展到网络副作用。
- 修复：Outbox、任务状态机、短事务、幂等和补偿。

### 错误五：认为异步线程继承事务

- 表现：主事务回滚，但异步写入仍提交；或异步任务读不到未提交数据。
- 原因：传统事务上下文绑定当前线程。
- 修复：为异步线程定义独立事务和消息契约。

## 十、边界与反例

- `readOnly = true` 通常是优化提示，不应当作绝对写保护机制。
- `@Transactional` 放在 `private` 方法上不能让代理调用它。
- 类代理能处理部分非公开方法，不代表可以忽略外部调用边界。
- `REQUIRES_NEW` 不是“更安全的事务”，它改变了原子性并增加资源占用。
- H2 实验只能验证 Spring 事务语义的核心路径，不能替代 MySQL 锁、隔离和连接池复验。
- 事务测试若测试方法本身被框架自动回滚，可能掩盖真实提交行为；实验必须明确谁在开启事务。

## 面试回答框架

回答 Spring 事务问题时使用五步：

1. 调用是否经过 Spring 管理的代理？
2. 使用哪个事务管理器和资源？
3. 当前是否已有物理事务，传播行为是什么？
4. 方法如何退出，异常是否匹配回滚规则？
5. 是否存在网络副作用、线程切换或多个资源？

这个框架比背诵“八种失效场景”更容易迁移到真实故障。

## 本章小结

Spring 声明式事务的核心不是注解，而是代理对方法调用的拦截、事务管理器对资源的协调，以及异常退出规则。工程上最重要的能力是定义正确边界：数据库内部使用短事务保证原子性，跨线程、跨服务和外部副作用使用状态机、Outbox、幂等和补偿保证最终一致。
