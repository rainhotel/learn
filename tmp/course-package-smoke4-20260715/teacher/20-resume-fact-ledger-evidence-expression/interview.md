# 第 20 章面试追问：每句话都要守得住

## 一、事实与角色

### 这段经历里你具体负责什么？

先划分业务背景、团队结果和本人动作，再列出自己交付的代码、文档、测试或排障。避免用“我们”掩盖个人贡献，也避免把团队工作全部据为己有。

### 你为什么写“主导”？

回答决策权、任务拆分、工作比例、协作者、验收责任和关键争议。如果只是承担模块，应改为“负责”；如果共同完成，应写“参与/协作”。

### 这项技术真的是在大烨实习使用的吗？

只依据实习期间证据回答。后续在 NotifyFlow 中学习的技术明确说是独立项目，不把成长路径伪装成实习栈。

### 这是公司项目还是个人项目？

直接给出归属、时间和环境。公司业务背景与个人项目成果不能混合，课程实验也不能回答成线上生产。

## 二、技术实现

### 你写“使用 Redis 保证幂等”，具体怎么保证？

如果 claim 属于独立项目，说明 key、原子操作、过期、冲突返回、持久化边界和最终业务状态；如果没有真实运行，必须改成“设计”。若大烨实习未使用 Redis，不得将该回答关联到实习。

### 你写“基于 Kafka 实现可靠消息”，可靠指什么？

说明生产确认、消费 offset、至少一次、重复处理、幂等、Outbox、DLT/对账和故障边界。没有真实 Kafka 运行时不声称已经验证 rebalance、lag 或无消息丢失。

### 你的 Agent 与普通聊天接口有什么不同？

说明 Tool Schema、运行状态机、权限、幂等、超时/取消、Memory、引用、评测和审批。若只完成设计，明确当前未运行部分。

### 为什么选择 Java 作为主后端语言？

结合本人证据回答：类型与生态、并发模型、Spring/数据/消息组件、JVM 排障和目标岗位；不要贬低 Python。Agent 模型侧可以使用 Python，可靠业务后端以 Java 为主。

## 三、量化与因果

### “提升 60%”是怎么算的？

必须回答指标定义、基线与结果、环境、数据量、持续时间、重复次数和原始记录。回答不完整就不应保留该数字。

### 为什么能说是你的改动带来的？

说明对照、变量控制、前后版本、回滚或消融实验。只有时间上的先后不能证明因果。

### 本地压测能代表线上吗？

不能。它用于比较机制、发现瓶颈和建立可复现基线；需要声明机器、版本、数据和限制，不能外推真实生产容量。

### 为什么没有大 QPS 也值得写？

可靠性、数据正确性、故障模型、可观测性和工程取舍本身可构成证据。可信的小规模实验胜过不可验证的大数字。

## 四、项目深挖

### NotifyFlow 最难的状态是什么？

可从 timeout 后 UNKNOWN、Outbox 重复、lease/fencing、重试放大或高风险 replay 中选择一个，讲清状态机、失败时间线和证据。

### 哪个方案后来被你推翻了？

给出最初假设、失败证据、修订方案和仍然存在的限制。没有失败记录的“完美项目”通常缺乏可信过程。

### 你项目中哪些部分还没有完成？

按已运行、静态检查、设计和 Pending 分层回答。承认边界比虚构完成度更可靠，并给出下一实验的验收条件。

### 如果让你明天上线，最大的风险是什么？

从数据迁移、幂等、容量、依赖故障、密钥权限、可观测性、回滚和成本中排序，说明上线门禁，而不是只回答“多加测试”。

## 五、AI 辅助与原创性

### 这些文档和代码有多少是 AI 写的？

如实说明 AI 的辅助范围，并展示本人完成的需求定义、事实核验、代码运行、失败分析、取舍和修订。AI 生成不是事实证据；本人无法解释和维护的内容不得计为能力。

### 如何证明你真的理解？

现场修改一个约束、画状态机、解释失败日志、比较替代方案，或在新环境复现实验。背诵文档不等于理解。

### AI 会不会帮你虚构简历？

事实只来自台账和证据，AI 只能压缩、排序和检查表达。任何新事实、数字和技术都必须回到来源核验；无法证明就删除。
