# 线程池与异步通知任务

## 1. 学习目标

完成本章后，你能够：

1. 从资源治理角度解释线程池，而不是只把它看作“复用线程的工具”。
2. 画出 `ThreadPoolExecutor` 接收任务的完整决策路径。
3. 根据任务类型、下游容量和服务目标设计有界线程池。
4. 解释四种内置拒绝策略的行为与业务风险。
5. 正确处理超时、取消、中断、异常和优雅停机。
6. 为 NotifyFlow 设计隔离的通知执行器和监控指标。
7. 回答大厂面试中关于线程池参数、队列、动态调整和故障的连续追问。

## 2. 为什么要学

消息通知系统天然包含慢 I/O：短信、邮件或外部推送接口可能耗时数百毫秒，也可能超时数秒。如果 HTTP 请求线程同步等待全部发送完成，请求延迟会随着接收方数量增长，连接和线程也会被长期占用。

最直接的改进是异步执行。但“把任务扔进线程池”只是问题的开始：

- 请求到达速度长期高于发送速度时，任务放在哪里？
- 队列可以无限增长吗？
- 下游供应商只能承受每秒 100 次调用时，增加线程有用吗？
- 队列满后是拒绝、降速、降级还是落库等待？
- 服务关闭时，已经接收的通知会不会丢？
- 如何知道线程池正在接近危险状态？

线程池的本质是：在任务到达率、处理能力、延迟、内存和下游容量之间建立明确边界。

## 3. 问题场景

NotifyFlow 接收一个包含 1,000 个收件人的通知批次。单次供应商调用平均耗时 200ms，P99 可能达到 2s。供应商限制单租户每秒最多 100 次调用。

错误方案：

```java
ExecutorService executor = Executors.newFixedThreadPool(200);
for (Recipient recipient : recipients) {
    executor.submit(() -> provider.send(recipient));
}
```

这段代码没有回答：

- `newFixedThreadPool` 背后的队列是否有界？
- 200 个线程是否超过供应商限流？
- 任务失败是否被观察？
- 应用退出时如何处理？
- 多个渠道是否互相拖垮？
- 批次是否需要持久化和恢复？

## 4. 线程池解决的两个问题

Java 21 官方文档指出，线程池主要解决两类问题：

1. 减少大量异步任务每次创建线程的开销，提高执行效率。
2. 对执行任务所消耗的线程等资源进行边界管理。

第二点更重要。在线上系统中，线程池首先是容量和故障隔离工具，其次才是性能工具。

## 5. 核心组成

```text
提交者
  |
  v
ThreadPoolExecutor
  |-- corePoolSize
  |-- maximumPoolSize
  |-- keepAliveTime
  |-- workQueue
  |-- threadFactory
  `-- rejectedExecutionHandler
```

### 5.1 corePoolSize

正常情况下希望保留的核心线程数。默认不会在构造时立即启动，而是在任务到达时按需创建；也可以预启动。

### 5.2 maximumPoolSize

线程池允许创建的最大线程数。它是否真正生效，与队列类型密切相关。

### 5.3 keepAliveTime

超过核心线程数的空闲线程，达到该时间后可以被回收。开启 `allowCoreThreadTimeOut` 后，也可以作用于核心线程。

### 5.4 workQueue

保存尚未开始执行的任务。队列不是免费的缓冲区：每个排队任务都会占用内存，并增加等待延迟。

### 5.5 threadFactory

决定线程名称、优先级、守护状态和未捕获异常处理。生产环境至少应该设置可识别的线程名称。

### 5.6 rejectedExecutionHandler

当线程池关闭，或线程数与队列同时达到容量上限时，决定如何处理无法接收的任务。

## 6. execute 的任务接收过程

对一个仍在运行的线程池，可以先用以下模型理解：

```text
收到任务
  |
  v
当前工作线程 < corePoolSize ?
  | yes                         | no
创建核心工作线程                尝试进入队列
                                |
                     入队成功 ? +---- yes ---> 等待执行
                                |
                                no
                                v
                  当前工作线程 < maximumPoolSize ?
                                | yes             | no
                         创建非核心线程           拒绝任务
```

因此，很多人背诵的“核心线程满了以后创建非核心线程”并不准确。默认决策是核心线程达到上限后先排队；只有无法入队时，才尝试继续创建线程直到最大线程数。

线程池还包含运行状态复检、关闭竞争等细节。课程当前先掌握容量决策模型，源码章节再分析 `ctl`、worker 和状态位。

## 7. 队列如何改变线程池行为

### 7.1 无界队列

例如不指定容量的 `LinkedBlockingQueue`。

当核心线程都忙时，任务仍能持续入队，因此通常不会继续创建超过核心数的线程，`maximumPoolSize` 近似失去作用。

风险：当平均到达率长期高于平均处理率时，队列持续增长，最终造成高延迟、内存压力甚至 OOM。

### 7.2 有界队列

例如 `ArrayBlockingQueue<>(capacity)`。

队列满后线程池可以继续扩展到最大线程数；线程和队列都满后触发拒绝。它把过载显式暴露出来，便于监控和治理。

代价：容量需要结合业务负载、内存和延迟目标调整。

### 7.3 直接移交

`SynchronousQueue` 不保存任务。提交任务时必须找到线程接手，否则尝试创建新线程。

它减少排队，但如果最大线程数缺少边界，可能造成线程数快速增长。

## 8. 拒绝不是异常细节，而是业务决策

### 8.1 AbortPolicy

抛出 `RejectedExecutionException`。优点是失败可见，调用者可以返回“系统繁忙”、持久化任务或触发降级。默认优先考虑它，而不是静默丢失。

### 8.2 CallerRunsPolicy

由调用 `execute` 的线程执行任务，除非线程池已经关闭。它会让提交速度变慢，形成简单的反馈控制。

边界：如果提交线程是 HTTP 请求线程，它可能被慢任务长时间占用；如果调用者持有锁，还可能扩大临界区或引发依赖问题。

### 8.3 DiscardPolicy

静默丢弃。对必须送达的通知通常不可接受。

### 8.4 DiscardOldestPolicy

丢弃队首尚未执行的任务，再重试提交。它可能丢掉等待最久、最接近 SLA 超时的任务，官方文档也提示该策略极少合理。

### 8.5 通知系统的推荐策略

关键通知不应只存在于内存队列。更可靠的模型是：

1. API 接收任务并写入数据库。
2. Outbox/MQ 负责将任务交给执行器。
3. 线程池只是单实例内部的并发边界。
4. 拒绝时不丢业务事实，而是让消息稍后重试、暂停消费或进入可观察失败状态。

## 9. 参数不是套公式得出的

常见公式：

```text
线程数 ≈ CPU 核数 × (1 + 等待时间 / 计算时间)
```

它可以作为估算起点，但不能直接成为生产参数，原因包括：

- 等待时间并不稳定，存在长尾。
- 下游有连接池、限流或配额。
- 每个任务占用的内存不同。
- 服务还有其他线程池和进程。
- 目标不是只追求吞吐，还要控制 P95/P99。

### 9.1 参数设计步骤

1. 明确任务：CPU 密集还是阻塞 I/O。
2. 测量单任务平均和长尾耗时。
3. 明确目标吞吐与允许排队时间。
4. 找出外部边界：供应商 QPS、HTTP 连接池、数据库连接池。
5. 估算并发需求。
6. 确定队列容量和内存预算。
7. 确定拒绝后的业务行为。
8. 压测并观察吞吐、延迟、队列和拒绝。
9. 故障注入后重新调整。

### 9.2 一个估算示例

假设供应商稳定允许 100 QPS，平均调用耗时 200ms：

```text
并发需求 ≈ 吞吐 × 平均响应时间
        ≈ 100/s × 0.2s
        ≈ 20
```

20 只是基于平均值的并发估算。还需要考虑 P99、重试、连接池和安全余量，并通过限流确保线程数不会把供应商压垮。

## 10. 队列容量与延迟预算

如果稳定处理能力是每秒 100 个任务，队列容量为 1,000，那么新任务在极端情况下可能仅排队就等待约 10 秒，尚未包含执行耗时。

因此队列容量不能只看“内存装得下多少”，还要看业务允许等待多久。

可以用 Little's Law 建立直觉：

```text
系统中的平均任务数 L = 到达率 λ × 平均停留时间 W
```

它不是线程池参数公式，但能帮助理解队列、吞吐和延迟之间的关系。

## 11. execute、submit 与异常观察

### execute

- 接收 `Runnable`。
- 任务抛出的未捕获异常可以到达线程的未捕获异常处理逻辑。
- 没有返回值用于等待或取消。

### submit

- 返回 `Future`。
- 可以获取结果、取消或等待。
- 任务异常被封装在 `Future` 中；如果从不调用 `get`，异常可能在业务层面被忽略。

因此，“使用 submit 就更安全”并不成立。你必须明确由谁观察 Future、记录失败和更新任务状态。

## 12. CompletableFuture 与线程池隔离

未显式传入执行器的 `CompletableFuture.supplyAsync/runAsync` 通常使用 `ForkJoinPool.commonPool()`。如果把慢 I/O、业务计算和其他库的异步任务混入公共池，可能产生互相影响。

通知系统应该显式提供业务执行器：

```java
CompletableFuture
    .supplyAsync(() -> provider.send(command), notificationExecutor)
    .orTimeout(2, TimeUnit.SECONDS)
    .whenComplete((result, error) -> recordOutcome(command, result, error));
```

注意：`orTimeout` 使 Future 超时完成，并不自动保证底层阻塞 I/O 已经停止。HTTP 客户端本身仍需设置连接、请求和读取超时。

## 13. 中断、取消和超时

Java 中通常通过中断请求协作式取消。中断不是强制杀死线程：

- 阻塞方法可能抛出 `InterruptedException`。
- 任务应停止工作、清理必要状态并退出。
- 捕获后如果不能向上抛出，应恢复中断标记。

```java
try {
    queue.take();
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    return;
}
```

错误做法是捕获后什么也不做，这会吞掉取消信号。

## 14. 优雅停机

`shutdown()`：停止接收新任务，让已提交任务继续执行。

`shutdownNow()`：停止处理等待任务，并尝试中断正在执行的任务；它返回尚未开始的任务。官方文档明确说明，这只是尽力尝试，中断不敏感的任务可能无法及时停止。

推荐两阶段关闭：

1. 调用 `shutdown()`。
2. 在限定时间内 `awaitTermination()`。
3. 超时后调用 `shutdownNow()`。
4. 再次等待。
5. 如果当前关闭线程被中断，调用 `shutdownNow()` 并恢复中断状态。

关键业务还需要在应用层先停止接收或暂停 MQ 消费，再等待正在执行的任务进入可恢复状态。

## 15. 线程池监控

至少监控：

- 当前池大小。
- 活跃线程数。
- 历史最大池大小。
- 队列长度与剩余容量。
- 已完成任务数。
- 拒绝次数。
- 任务等待时间。
- 任务执行时间。
- 成功、失败、超时和取消数量。

只监控线程数不够。队列等待时间常常比线程数更早暴露 SLA 风险。

## 16. 动态调整参数

`ThreadPoolExecutor` 支持调整核心线程、最大线程和保活时间，但“可以动态修改”不代表应该自动频繁调整。

动态调整前必须回答：

- 修改依据是什么指标？
- 是否会超过数据库、连接池或供应商容量？
- 调大后如何回落？
- 参数变化是否需要审计和回滚？
- 队列已经积压时，增加线程是否真的能改善吞吐？

如果瓶颈是供应商限流或数据库连接池，增加线程只会制造更多等待。

## 17. 虚拟线程是否替代线程池

Java 21 提供虚拟线程，适合大量“一个任务对应一个阻塞操作”的并发代码。它降低了平台线程的占用成本，但不取消资源边界：

- 外部 API 仍有 QPS 限制。
- 数据库和 HTTP 连接池仍有容量。
- 内存、队列和业务任务仍需控制。
- CPU 密集任务不会因为虚拟线程变快。

使用虚拟线程时，常见做法是让任务拥有独立虚拟线程，同时用 Semaphore、限流器或连接池控制稀缺资源，而不是建立“虚拟线程池”复用虚拟线程。

## 18. NotifyFlow 的推荐边界

```text
API / MQ Consumer
      |
      v
持久化任务状态与幂等事实
      |
      v
渠道调度器
  |-- SMS executor + rate limiter
  |-- Email executor + rate limiter
  `-- In-app executor
      |
      v
供应商客户端（连接/请求/读取超时）
```

设计原则：

- 不同渠道隔离线程池，避免邮件超时拖垮短信。
- 每个池有界，并记录拒绝。
- 供应商 QPS 由限流器控制，不靠线程数碰运气。
- 任务先持久化，线程池拒绝不等于业务事实丢失。
- 所有任务有幂等键、超时、尝试次数和错误分类。
- 应用关闭前暂停消费，等待任务完成或写入可恢复状态。

## 19. 常见错误

### 错误一：直接使用无界队列

短期流量看起来平稳，长期过载时延迟和内存无限增长。

### 错误二：线程越多吞吐越高

超过 CPU、连接池或下游容量后，只会增加竞争、上下文切换和长尾延迟。

### 错误三：静默丢弃任务

发送任务属于业务事实，不能只存在于内存 Runnable 中。

### 错误四：把 CallerRuns 当万能降级

它可能阻塞请求线程或 MQ 消费线程，需要结合调用上下文判断。

### 错误五：只配置 Future 超时

底层 HTTP 请求若无超时，资源仍可能被占用。

### 错误六：吞掉 InterruptedException

导致关闭和取消无法生效。

### 错误七：共用一个全局线程池

不同任务的延迟、优先级和故障会互相影响。

## 20. 本章小结

线程池不是一个孤立 API，而是一套容量治理机制：

- 核心线程、队列、最大线程和拒绝策略共同决定任务接收边界。
- 参数应从任务测量、下游容量、延迟预算和过载策略推导。
- 可靠通知不能依赖内存队列保存业务事实。
- 超时、取消和关闭依赖任务正确响应中断。
- 可观测性和故障实验是线程池设计的一部分。
- 虚拟线程降低线程成本，但不消除资源限制。
