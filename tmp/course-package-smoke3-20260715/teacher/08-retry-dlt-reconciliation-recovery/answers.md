# 练习答案与评分标准

## 一、基础题

### 1. 错误分类（5 分）

- TRANSIENT：短暂网络/偶发 5xx，可有界重试。（1）
- PERMANENT：非法号码/模板禁用，相同请求重试无效。（1）
- POISON：Schema/反序列化错误，隔离 DLT。（1）
- UNKNOWN：超时但供应商可能已执行，需要查询和对账。（1）
- SYSTEMIC：数据库或供应商全局故障，应暂停/熔断而非逐条重试。（1）

### 2. 总尝试次数（4 分）

若包含首次，`maxAttempts=4` 表示首次 + 3 次重试。（2）必须明确，否则业务、框架和监控对 attempt 的解释不同，容易超预算。（2）

### 3. 退避与抖动（4 分）

- 上限退避如果无限尝试，会持续以最大频率冲击下游。（2）
- 无 jitter 时同批任务同步唤醒，形成重试尖峰。（2）

### 4. DLT（4 分）

DLT 只是隔离失败记录。仍需负责人、诊断、代码/数据修复、权限、重放、结果确认和审计。（每项 0.5，最多 4）

### 5. 补偿（3 分）

补偿是一次新的、可观察的业务动作，可能失败、可能不可逆且需要幂等；数据库回滚是在提交前撤销本地事务状态。（3）

## 二、计算题

### 6. 重试放大（5 分）

`3^5=243` 次。（2）改造为单一层负责重试，其他层关闭或只做明确的非重叠重试；设置总 deadline 和预算。（3）

### 7. 最坏耗时（6 分）

尝试耗时：`4 * 3 = 12s`。（2）backoff：`1+2+4=7s`。（1）总计 19 秒。（1）超过 12 秒 deadline，后续尝试已无业务价值；应减少次数/timeout/backoff或异步化。（2）

### 8. 重试流量（4 分）

`1000 * (1 + 0.8) = 1800 QPS`。（4）

### 9. 恢复时间（5 分）

- 净消化：`5000-2000=3000/s`。（2）
- 时间：`3,600,000/3000=1200s=20min`。（2）
- 这是不含重试、热点和性能波动的理论值。（1）

### 10. Spring Kafka 边界（5 分）

- 不支持 batch listener。（2）
- 不能与 container transaction 组合。（2）
- 因此需要选择 record listener、blocking recovery、数据库调度或重新设计事务边界。（1）

## 三、应用题

### 11. 错误策略表（6 分）

- 429：THROTTLED，读取 Retry-After，有界退避和渠道限速。（1）
- 503：TRANSIENT；若比例高则 SYSTEMIC，触发熔断。（1）
- 非法号码：PERMANENT，不重试。（1）
- Schema 不支持：POISON，直接或极少重试后 DLT。（1）
- timeout + providerRequestId：UNKNOWN，查询/回调/对账。（1）
- 连接池耗尽：SYSTEMIC，保护数据库、暂停或降速，不在每条消息内高速重试。（1）

### 12. Unknown 对账（6 分）

- attempt=SENDING，超时转 UNKNOWN，同时唯一创建 reconciliation case。（1.5）
- 查询成功转 SUCCEEDED。（1）
- 查询明确失败再分类为 RETRY_WAIT/PERMANENT_FAILED。（1）
- 无结果按长退避查询，超过 deadline 转 MANUAL。（1）
- 回调按 providerRequestId 去重，状态机拒绝倒退。（1）
- 所有原始回调留审计。（0.5）

### 13. DLT 数据（5 分）

任十项，每项 0.5：eventId、tenantId、aggregateId、原 Topic、Partition、offset、key、event type/version、delivery attempt、异常类型、异常摘要、首次/最后失败时间、payload hash、producer、traceId、owner、状态。payload、异常消息、堆栈、key 和业务 ID 需评估敏感性。

### 14. Replay preview（7 分）

题目列出的七个要素每项 1 分。高分答案还区分原 eventId 与 replayId，并显示已被幂等跳过数量。

### 15. 权限（6 分）

- Viewer 只读脱敏信息。（1）
- Operator 执行授权租户的小批量低风险重放。（1）
- Approver 批准大批量/新 eventId/外部副作用操作。（1）
- Agent 只读和生成建议，无执行权限。（1）
- 跨租户、大批量、新 eventId、关闭幂等、提升 QPS 需要双人或独立审批。（2）

## 四、故障分析

### 16. 重试风暴（8 分）

参考顺序：

1. 确认供应商和范围。（1）
2. 降低/停止自动重试，打开熔断或暂停渠道。（1）
3. 保留任务事实，避免丢弃。（1）
4. 保护线程池、连接池和数据库。（1）
5. 联系供应商并观察恢复证据。（1）
6. 1% 探测后分阶段恢复。（1）
7. 独立处理 Unknown 和对账。（1）
8. 不能先扩 Consumer，因为会把更多并发打向已过载下游。（1）

### 17. DLT 重放二次事故（7 分）

缺陷任选五项：无 preview、无 dry-run、无 QPS、无并发限制、无租户隔离、无审批、无小批量探测、无幂等分析、无暂停、无下游健康检查、无恢复容量计算。修复项与缺陷一一对应；五组 5 分，说明为什么会二次过载 2 分。

## 五、表达与 Agent

### 18. 简历纠错（5 分）

参考：

> 为 NotifyFlow 设计分层故障恢复机制，将错误区分为瞬时、限流、永久、毒消息、Unknown 和系统性故障；使用单点有界重试、上限指数退避、抖动和重试预算控制额外负载，通过 DLT 隔离、供应商查询/回调对账以及带权限、审批和限速的人工重放形成恢复闭环。Agent 只辅助生成带引用的诊断建议，高风险操作由确定性策略和人工审批执行。

评分：不承诺绝对可靠（1）、有分类（1）、有预算（1）、有对账和重放（1）、Agent 边界准确（1）。

### 19. Agent 权限（5 分）

自动辅助任选三项：异常聚类、Runbook 检索、事故摘要、风险清单、过滤条件建议。（2）必须审批任选三项：全量重放、新 eventId、退款、设备反向命令、跨租户操作、修改配额/策略。（3）
