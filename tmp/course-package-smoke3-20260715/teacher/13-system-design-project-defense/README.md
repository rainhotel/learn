# 第 13 章：系统设计与项目答辩

## 章节定位

- 类型：System Design + Project Defense + Reliability Review + Lab Design
- 难度：深入
- 建议学习时间：24-32 小时
- 先修章节：第 04-12 章；重点依赖 MySQL、Redis、Kafka、恢复控制面、可观测性、JVM、网络和部署基础
- 对应项目：NotifyFlow 可靠通知平台与 Agent 事故助手

## 当前状态

- 阶段：八件套完整内容初稿，实验 Pending
- 调研日期：2026-07-15
- 已完成：需求澄清、容量估算、API/数据模型、可靠性、一致性、多实例、可观测性、安全、成本、演进和答辩框架设计
- 未完成：设计评审、真实负载、故障演练、陌生面试官追问和答辩录像证据

本章不能标记为 Lab Verified、Release Candidate 或 Released。

## 相邻章节边界

- 第 04-12 章分别训练数据库、缓存、消息、恢复、观测、JVM、网络和部署能力。
- 第 13 章把这些局部能力组合成一份自洽的系统设计，并训练“为什么这样取舍”的项目答辩。
- 第 14 章以后深入 LLM、RAG 和 Agent；本章只定义事故助手的系统边界、安全合同和后端集成点。
- 第 19 章深入多实例租约、fencing、分片与故障；本章只给出系统级选择和追问入口。

## 核心问题

1. 面对模糊题目，如何先澄清用户、流量、可靠性、顺序、合规和成本约束？
2. 如何把日请求量、峰值系数、扇出、服务时间、保留期转成 QPS、并发、分区、连接和存储预算？
3. API、状态机、数据库、缓存和消息系统各自保存什么事实？
4. 如何处理重复、乱序、超时、UNKNOWN、部分成功和 Provider 回调？
5. 为什么 Transactional Outbox、幂等、对账和安全重放需要组合，而不是单点“保证不丢”？
6. 多实例、限流、背压、优雅下线和恢复预算如何避免故障放大？
7. 如何用 Metrics、Logs、Trace、事件和数据正确性查询证明系统状态？
8. Agent 事故助手怎样引用证据、隔离租户、抵抗 prompt injection，并禁止越权执行？
9. 如何讨论安全、成本、演进和未验证边界，而不是堆砌中间件？
10. 项目答辩时如何承受容量、故障、一致性和个人贡献追问？

## 退出标准

- 能在 5 分钟内完成需求澄清并写出假设、范围和非目标。
- 能手算平均/峰值 QPS、扇出、在途并发、消息积压和存储粗估，并解释误差来源。
- 能画出 NotifyFlow 写入、投递、回调、恢复和事故助手的核心时序。
- 能定义 API 幂等、任务状态机、数据模型、消息 key、缓存边界和一致性来源。
- 能对数据库、Redis、Kafka、Provider、网络和 Agent 失败给出检测、止血、恢复和正确性验证。
- 能说明多实例领取、配额、背压、优雅下线和恢复风暴控制。
- 能给出 SLI、告警、低基数字段、Trace 关联和审计策略。
- 能讨论 PII、租户隔离、RBAC、Secret、内容安全、prompt injection 和高风险审批。
- 能用成本公式和阶段演进说明为什么当前设计不过度复杂。
- 能完成 5/15/45 分钟答辩，并对未运行结果明确标注 Pending。

## 本章交付物

- 一页需求与假设说明。
- 容量估算表和误差敏感性分析。
- 架构图、核心时序、状态机、API 和数据模型。
- 可靠性、降级、恢复、观测、安全和成本决策表。
- 至少五条 ADR（Architecture Decision Record）。
- 设计评审记录、故障演练证据包和项目答辩录像。

## 发布前缺口

- 使用固定版本的 NotifyFlow 实现跑通核心 API、Outbox、Kafka、Provider stub 和对账。
- 在封闭/开放负载下校准容量估算，而不是只保留纸面数字。
- 完成重复提交、消费者崩溃、Provider 超时、Redis 故障、Kafka 积压和数据库慢等演练。
- 完成跨租户、prompt injection、越权 replay 和审计完整性测试。
- 由至少一名陌生评审者完成 45 分钟设计评审和追问。
- 将评审问题、错误假设和修改后的设计形成版本化证据。
