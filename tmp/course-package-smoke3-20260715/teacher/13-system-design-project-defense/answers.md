# 第 13 章参考答案与评分

## 核心要点

1. 需求必须包含用户、规模、SLO、顺序/重复语义、保留期、合规、成本与非目标。
2. 平均创建 QPS 约为 `10,000,000 / 86,400 = 116`；峰值约 926；平均投递峰值约 2315 QPS。结果只是输入假设，需用真实分布校准。
3. 创建 API 使用租户范围内唯一幂等键；重复请求返回同一 taskId。超时后先查询，不生成新键。
4. 状态机必须允许重复和乱序事件，attempt 与 task 分离；UNKNOWN 由查询、回调或对账收敛。
5. MySQL 保存业务真相和审计；Kafka 传递事件；Redis 只承担可重建缓存、限流或短期去重，不成为唯一真相。
6. 恢复必须组合 Outbox、消费幂等、有限重试、DLT case、对账和受控重放，并验证最终数据正确性。
7. 每租户配额和全局容量同时生效；过载时先拒绝/延迟低优先级任务，停止无限排队和多层重试。
8. 观测同时覆盖用户 SLI、资源饱和、依赖、任务状态时间线和数据库正确性查询；唯一 ID 不进入指标 tag。
9. Agent 默认只读、最小权限、结构化 Tool schema、租户隔离、引用证据；高风险动作由确定性控制面审批执行。
10. ADR 不能只写“用了 Kafka”，要写决策上下文、方案比较、代价、风险和重新评估条件。
11. 答辩证据应包含录音、问题清单、无法回答项和修订 diff，不能只保留顺利版本。
12. 未真实做过的中间件不能写入实习；独立项目可写“设计/实现/压测”，但量化结果必须有证据。

## 评分

| 维度 | 分值 |
|---|---:|
| 需求与容量 | 15 |
| API、数据与状态机 | 20 |
| 可靠性与一致性 | 20 |
| 多实例、容量与恢复 | 15 |
| 观测、安全与 Agent 边界 | 15 |
| 取舍、表达与证据诚实性 | 15 |

没有容量假设、故障路径或事实边界时，不得超过 60 分；没有陌生评审和运行证据时不得标记 Released。
