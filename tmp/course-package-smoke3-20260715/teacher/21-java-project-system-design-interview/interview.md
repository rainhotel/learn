# 第 21 章综合面试追问树

## 使用方法

本文件不是逐字背诵稿。训练顺序：

1. 只看问题，90 秒闭卷回答。
2. 让评审者任选一个追问继续。
3. 用“结论、机制、场景、失败、证据、边界”自检。
4. 再阅读参考主线，制作纠错卡。

题目来自课程能力模型和工程机制，不声称是任何公司的真实面试原题。

## 一、Java、JMM 与并发

### 1. HashMap 为什么不线程安全？

HashMap 的 get/put/resize 没有提供并发互斥或跨操作的 happens-before。并发写可能覆盖更新，遍历与修改也没有一致快照保证。即使换成 ConcurrentHashMap，先检查再写的跨操作不变量仍可能竞态，应使用 compute、putIfAbsent、锁或重新设计所有权。

追问：

- equals 与 hashCode 合同是什么？
- 可变 key 有什么风险？
- 为什么不能把 NotifyFlow 任务真相放在内存 Map？

### 2. happens-before 与“代码先执行”有什么区别？

happens-before 是 Java 内存模型对可见性和允许重排的规则，不是简单墙钟顺序。一个线程先执行写、另一个线程后执行读，如果没有同步边，也不能据此证明读一定看到写。程序次序、monitor、volatile、start/join 和传递性是常用边。

追问：

- sleep 能建立 happens-before 吗？
- final 字段发布有什么特殊性？
- 数据竞争一定每次都产生错误吗？

### 3. volatile 与 synchronized 怎么选？

先看不变量。独立状态发布或标志可用 volatile；需要互斥、复合读改写、跨字段一致性时使用 synchronized、Lock 或单线程所有权。synchronized 同时提供 monitor 互斥和 unlock-lock 的可见性。

追问：

- volatile long 是否原子？
- 双重检查单例为什么需要 volatile？
- synchronized 异常退出会怎样？

### 4. synchronized 与 ReentrantLock 怎么选？

synchronized 语义简单、自动释放，通常是默认选择。ReentrantLock 在需要可中断获取、tryLock、超时、公平策略或多个 Condition 时更合适，但必须在 finally 释放。不要只凭过时性能印象选择。

追问：

- 公平锁为什么吞吐可能更低？
- Condition 与 wait/notify 的责任是什么？
- 怎样诊断锁竞争？

### 5. CAS 有什么问题？

CAS 适合单变量条件更新，避免阻塞不等于没有成本。高竞争下反复失败会消耗 CPU；ABA 使值看似未变但中间状态已变化；跨多个变量或外部副作用不能靠一个 CAS 保证原子。

追问：

- AtomicStampedReference 解决什么？
- LongAdder 为什么适合高竞争计数，却不适合精确瞬时余额？
- CAS 自旋何时需要退避？

### 6. ThreadPoolExecutor 怎样接收任务？

worker 少于 core 时创建 worker；否则尝试入队；队列满且 worker 少于 maximum 时扩容；仍不能接收则执行拒绝策略。无界队列常让 maximum 长期不生效，把过载隐藏为排队和内存增长。

追问：

- CPU 与阻塞 I/O 池怎样估算？
- CallerRuns 的风险是什么？
- core timeout 何时有用？
- 如何证明池饱和？

### 7. 拒绝策略怎么选？

选择取决于是否允许丢、是否能向上游反馈和提交线程身份。AbortPolicy 让失败显式；CallerRuns 可反馈降速但会阻塞提交者；Discard 类策略只有在业务允许丢且有指标/审计时才安全。NotifyFlow 关键任务不能静默丢弃。

追问：

- 消息 consumer 中 CallerRuns 会造成什么？
- 如何给低优先级任务单独降级？
- 拒绝后 API 返回什么语义？

### 8. 如何正确处理中断？

中断是协作式取消。阻塞方法抛 InterruptedException 时会清除中断状态；若当前层不能完成取消，应继续抛出或重新设置中断。吞掉异常会让 shutdown 和 deadline 失效。退出前仍要保证状态、锁和资源安全。

追问：

- 为什么不能 Thread.stop？
- finally 中能否执行长时间清理？
- Provider 调用已经成功时中断意味着什么？

### 9. CompletableFuture 常见坑是什么？

默认 common pool 不一定适合阻塞 I/O；thenApply 与 thenCompose 混用会产生嵌套 future；异常可能在链尾才暴露；orTimeout 不保证底层副作用停止；多个异步层独立重试会放大请求。应显式 executor、deadline、异常合同和幂等。

追问：

- allOf 如何获取每个结果和错误？
- exceptionally、handle、whenComplete 有何差别？
- MDC/Trace context 怎样传播？

### 10. Java 21 虚拟线程解决什么？

虚拟线程降低大量阻塞式任务的线程创建和驻留成本，让同步代码可以承载更多并发。它不提升 CPU 算力，也不增加数据库连接、文件描述符或 Provider 配额；固定大小连接池仍会成为边界。pinning、ThreadLocal 成本和监控方式也要评估。

追问：

- 是否还需要线程池？
- synchronized 中阻塞有什么影响？
- 如何限制虚拟线程对下游的并发？

### 11. 并发安全与线程安全有什么区别？

单个类的方法线程安全，不等于业务工作流并发安全。多个线程安全组件组合出的 check-then-act、跨库更新和外部副作用仍可能竞态。要先定义业务不变量、线性化点、幂等键和失败恢复。

追问：

- ConcurrentHashMap 加 AtomicInteger 是否自动保证跨 key 配额？
- 事务能否保护远程调用？
- 状态机如何拒绝陈旧事件？

### 12. 怎样避免并发问题只靠“加锁”？

优先减少共享可变状态：不可变对象、消息传递、分片所有权、Actor/单线程执行、数据库条件更新和幂等状态机。锁是保护明确临界区的工具，不是分布式副作用的一般答案。

## 二、JVM 与生产排障

### 13. JVM 运行时内存有哪些重要区域？

heap 保存对象并受 GC 管理；每线程 stack 保存栈帧；metaspace 保存类元数据；direct/native memory、code cache 和 JVM 内部结构也占用进程/容器内存。容器 OOMKilled 可能发生在 heap 尚未满时。

追问：

- metaspace 泄漏常见原因是什么？
- direct buffer 如何回收？
- Xmx 应否等于容器 limit？

### 14. 对象一定分配在堆上吗？

Java 语义关注对象可观察行为，具体实现可通过逃逸分析、标量替换等优化消除分配。面试中不要把“对象都在堆上”当作不可变实现承诺。排障应看 JFR/分配采样，而不是只靠源码猜测。

### 15. G1 与 ZGC 怎么选？

先明确 heap、停顿目标、吞吐、CPU 和 JDK 版本。G1 是常见均衡选择；ZGC 面向较低停顿并以并发工作换取资源和其他权衡。collector 选择不能替代降低分配、修复泄漏和容量规划，最终要用同一工作负载验证。

追问：

- 为什么平均 GC pause 不够？
- 什么是分配速率和晋升压力？
- collector 切换如何做回归？

### 16. Full GC 多就一定是内存泄漏吗？

不一定。heap 过小、高分配、晋升失败、显式 GC、元空间压力或 collector 行为都可能触发。泄漏需要看到 GC 后存活基线持续上升，并通过 histogram、heap dump、引用链和业务生命周期验证。

### 17. CPU 100% 怎么排查？

先确认容器配额和用户症状，再找到高 CPU 线程/进程，与线程 dump、JFR 热点、GC、重试和流量时间线关联。常见方向包括自旋、死循环、序列化、正则、加密、日志、GC 和任务风暴。先止血再保存足够证据。

追问：

- 单核 100% 与进程 100% 的口径是什么？
- CPU throttling 如何影响 P99？
- 采集 profiler 有什么风险？

### 18. 内存泄漏怎么排查？

区分 heap、native、线程、classloader、direct buffer 和缓存增长。观察 GC 后基线、对象数量和 retained size；在安全条件下获取 histogram/heap dump；从 GC root 路径判断为什么仍可达。一次高 heap 快照不能证明泄漏。

### 19. JFR 有什么价值和边界？

JFR 能以较低开销记录 CPU、分配、锁、线程、GC、I/O 和自定义事件，适合构建统一时间线。它不是自动因果解释器；事件开关、采样率、时间窗和自定义字段都会影响结论。第 09 章只验证了自定义 Provider 事件链路，尚未证明 GC/锁与 P99 因果。

## 三、Spring

### 20. Spring 声明式事务为什么会失效？

常见原因是调用没有穿过事务代理、Bean 不由容器管理、方法不可代理、异常被捕获或不满足回滚规则、异步线程跨边界、使用了不受同一事务管理器控制的资源。答案应画调用链，而不是只列注解。

### 21. self-invocation 如何修复？

优先重新划分服务边界，让外部调用穿过另一个 Bean；也可把事务放到真正的外部入口，或用 TransactionTemplate 显式控制。通过容器取自身代理能工作但耦合和可测试性较差，通常不是首选。

### 22. REQUIRED 与 REQUIRES_NEW 的风险是什么？

REQUIRED 加入当前事务，内层回滚标记可能导致外层最终 UnexpectedRollback。REQUIRES_NEW 挂起外层并创建独立事务，需要额外连接；在高并发和外层持有连接时可能耗尽连接池。它也不让远程副作用与两个本地事务原子。

### 23. 为什么不应在数据库事务里调用慢 Provider？

网络时间不可控，会延长锁持有和连接占用，放大死锁、池耗尽和回滚成本。NotifyFlow 在短事务中写 task/outbox，提交后异步调用 Provider。若业务确实需要同步结果，也要设置 deadline、幂等和补偿。

### 24. Spring 异步方法与事务如何交互？

异步线程不会自动继承调用线程的事务上下文。Async 方法中的数据库操作需要自己建立事务；调用方事务尚未提交时，异步线程还可能读不到数据。更可靠的跨线程触发通常使用提交后事件或 Outbox。

### 25. 如何设计统一异常处理？

将验证、认证、幂等冲突、依赖暂时失败、永久业务失败和 UNKNOWN 区分为稳定错误合同。ControllerAdvice 只负责 HTTP 映射，不应吞掉业务上下文。日志包含 correlation id 和安全字段，不返回堆栈或敏感细节。

## 四、MySQL、Redis 与 Kafka

### 26. 为什么数据库索引常用 B+Tree？

B+Tree 保持有序、扇出高、树高低，叶子适合范围扫描；数据库页式存储下能减少 I/O。回答还要说明哈希索引适合等值但不支持常规范围/排序，是否走索引最终取决于优化器成本。

### 27. 联合索引怎么设计？

从高频查询的过滤、排序、范围和覆盖出发，同时考虑选择性、更新成本和索引大小。最左前缀是访问路径约束，不等于第一列必须是选择性最高。范围条件后的列能否用于定位或仅用于过滤，要结合执行计划。

### 28. 覆盖索引一定更快吗？

覆盖可以减少回表，但更宽索引占用更多空间、降低缓存效率并增加写放大。真实选择要比较查询频率、返回列、分页、写入和执行计划。第 04 章实验支持具体查询下的覆盖差异，不是普遍承诺。

### 29. MVCC 怎样实现一致性读？

InnoDB 使用事务 ID、undo 版本和 read view 判断哪个版本对当前一致性读可见。REPEATABLE READ 通常在事务内复用快照，READ COMMITTED 每次一致性读获取新快照。锁定读/当前读遵循不同路径，不能把所有 SELECT 都归为同一行为。

### 30. 死锁怎么处理？

数据库检测锁等待环并回滚一个 victim。应用应缩短事务、统一锁顺序、使用合适索引减少锁范围，并对可重试事务进行有界重试。重试必须覆盖整个事务，且业务副作用幂等。

### 31. SKIP LOCKED 有什么边界？

它让 worker 跳过已锁记录，提高并行领取，但不保证严格公平，热点或长锁可能导致某些任务延迟。领取要小批、短事务、条件更新；崩溃接管仍需 lease/状态，外部副作用仍需幂等。

### 32. 缓存一致性怎么回答？

先声明数据库是真相源和允许的陈旧窗口。常见策略是写数据库后删除缓存，配合 TTL、版本、请求合并和失败补偿；并发窗口仍可能存在。不能笼统承诺“缓存和数据库强一致”。

### 33. 缓存穿透、击穿、雪崩有什么区别？

穿透是大量不存在 key 绕过缓存；击穿是热点 key 失效时并发回源；雪崩是大范围同时失效或 Redis 故障。分别用输入校验/负缓存、请求合并/逻辑过期、TTL 抖动/分批预热/降级和数据库保护。

### 34. Redis 分布式锁安全吗？

安全取决于故障模型。至少需要唯一 owner token、条件释放、租约和续约边界；客户端停顿可能让租约过期后旧 owner 恢复执行，因此对下游写还需要 fencing token。若能用数据库条件更新、单分区所有权或幂等状态机，通常更直接。

### 35. Redis 做限流有哪些选择？

固定窗口简单但边界突刺；滑动窗口更精确但状态成本高；令牌桶允许受控突发；漏桶强调平滑输出。分布式实现要讨论时钟、原子脚本、故障降级、租户层级和最终 Provider 配额。

### 36. Kafka 为什么会重复消费？

consumer 处理完成但 offset 未提交即崩溃，或 rebalance 后消息会重新投递。自动提交还可能在业务处理前推进 offset。正确策略是稳定业务键、幂等状态更新、合适提交时机和可重入 handler。

### 37. Kafka 如何保证顺序？

只保证单分区内按 log 顺序读取。key 决定分区，因此要明确顺序实体；增加分区、key 变化、并发处理和重试旁路都可能改变业务观察顺序。状态机可使用版本号拒绝陈旧事件。

### 38. Transactional Outbox 的失败窗口是什么？

业务事务内写 aggregate 和 outbox，避免数据库与 Kafka 假原子双写。Publisher 发送成功但未标记 published 时会重复发送；标记策略和扫描领取也会竞争。因此 event id、幂等 consumer、重试和监控 oldest age 仍不可少。

### 39. Kafka EOS 是否等于端到端 exactly-once？

不是。Kafka 事务可在 Kafka 资源范围内协调 consume-transform-produce 和 offset，但 MySQL、HTTP Provider、邮件/短信副作用不自动加入。对外部副作用仍需业务幂等、UNKNOWN、对账和限制性承诺。

### 40. DLT 的作用是什么？

DLT 把无法继续自动处理的事件与主流量隔离，保留上下文供调查或修复。它不是失败终态、永久归档或自动重试队列。需要 owner、告警、分类、保留期、修复验证和安全 replay。

## 五、网络、连接池与容器

### 41. 一个 HTTPS 请求经历什么？

通常经过 DNS、获取连接、TCP 建连、TLS 握手、HTTP 请求写入、服务处理和响应读取；连接复用时部分阶段可省略。每阶段都有 deadline 和错误语义，不能用一个“接口超时”概括。

### 42. connect timeout 与 read timeout 有何区别？

connect timeout 限制建立连接；read timeout 限制等待数据读取。请求还可能卡在 DNS、连接池 acquire、TLS、写入或多次重定向，因此需要 overall deadline 和阶段指标。超时不说明服务端是否执行。

### 43. 连接池为什么不是越大越好？

更大池会把更多并发推给数据库/Provider，增加排队、上下文切换和故障放大。应从下游安全并发、服务时间、到达率和 deadline 初估，再用 pending、timeout、P99、吞吐和下游饱和校准。

### 44. TIME_WAIT 多一定是故障吗？

TIME_WAIT 是主动关闭方保护旧报文和可靠结束连接的正常状态。大量短连接可能使端口和资源承压，但先检查连接复用、关闭方、端口范围、负载均衡和实际失败；不能看到数量大就调内核参数。

### 45. Docker 的隔离原理是什么？

namespace 隔离进程看到的 PID、网络、挂载等视图；cgroup 记账和限制 CPU、内存等资源；分层文件系统构建镜像与容器写层。容器共享宿主机内核，因此安全边界和 VM 不完全相同。

### 46. readiness 与 liveness 怎么设计？

readiness 判断此实例当前是否应接收流量；liveness 判断进程是否处于必须重启才能恢复的状态。数据库短暂失败通常影响 readiness 或业务降级，不应轻易让所有 Pod liveness 失败造成重启风暴。startup probe 可保护慢启动。

### 47. Kubernetes 优雅下线怎样避免重复任务？

先移除 readiness，停止领取/暂停 consumer，有界等待 in-flight，持久化安全状态或提交 offset，再关闭客户端。强杀仍可能发生，所以业务幂等、lease、UNKNOWN 和对账是基础，不应把正确性寄托于 preStop 一定执行完。

## 六、NotifyFlow 项目深挖

### 48. NotifyFlow 解决的核心问题是什么？

它把“接收通知请求”和“外部 Provider 最终副作用”解耦，处理重复、超时、回调乱序、积压和恢复。价值在于可追踪状态和可控恢复，不是简单封装发送 SDK。当前是独立课程工程项目，不是实习生产事实。

### 49. 为什么 MySQL 是任务真相源？

任务、投递、Outbox、审批和审计需要持久约束、事务和查询。Redis 可加速但可丢；Kafka 保存事件流但不是所有业务当前状态和审计的唯一数据库。数据真相边界清晰能让故障恢复可验证。

### 50. 幂等键如何设计？

按 tenant + business operation 定义作用域，设置保留期并保存 request hash。重复 key 且摘要相同返回原任务；key 相同但请求不同返回冲突。客户端 timeout 后查询原 key，而不是换 key 重试。

### 51. Provider timeout 为什么进入 UNKNOWN？

请求可能已经被 Provider 保存，只是响应丢失。直接 FAILED 并新建尝试可能造成重复短信或工单。系统保存稳定 provider request id，进入 UNKNOWN，并由查询、回调或对账推进终态。

### 52. 重试、DLT、对账和 replay 有何区别？

retry 处理短暂失败且受总预算；DLT 隔离不能继续自动处理的事件；reconciliation 比较跨系统状态并收敛 UNKNOWN；replay 是修复后经 preview、审批、配额和审计重新执行。混成一个无限重试队列会制造事故。

### 53. 怎样证明没有重复通知？

不能只看 consumer 日志。需要稳定逻辑 delivery id、provider request/message id、回调唯一键和状态时间线；查询同一逻辑投递是否出现多个成功副作用；验证重复消息、崩溃和 timeout 下最终数据正确性。Provider 不支持幂等查询时，结论必须降级。

### 54. 项目容量数字从哪里来？

设计阶段用日量、峰值系数、扇出和服务时间估算；运行阶段用开放负载和服务端指标校准。已有第 09 章模型与局部线程池/JFR 证据，但 NotifyFlow 端到端 QPS 和提升比例仍不能声称已验证。

### 55. 多实例如何领取和接管？

Kafka consumer group 负责分区并行；数据库 scanner 可用 SKIP LOCKED 或 lease。lease 到期允许接管，旧 owner 恢复后的写需用 version/fencing 拒绝。任何领取机制仍要面对崩溃窗口和重复副作用。

### 56. Agent 事故助手为什么只读？

模型可能幻觉、受 prompt injection、误解上下文或重复调用 Tool。它可以聚合授权证据、生成引用和建议；replay、扩容、offset reset、配额和权限变更由确定性控制面审批执行。Agent Runtime 当前仍为设计 Pending。

## 七、RAG 与 Agent

### 57. RAG 为什么不等于向量数据库？

RAG 包括文档解析、清洗、切分、版本/ACL、检索、融合、重排、context、生成、引用、拒答、评测和运维。向量数据库只是其中一个候选检索组件。

### 58. 为什么做混合检索？

dense 擅长语义相似，sparse/BM25 擅长精确 token、编号、错误码和专有名词。两者融合后再 rerank 可提高不同问题类型的覆盖，但会增加延迟、成本和调参维度，需要按 tag 做消融评测。

### 59. 如何评测 RAG？

分 retrieval、context、generation、citation、refusal、安全和 operations。冻结 corpus/config，保存完整 ranking/context/response；使用 Recall@k、MRR/nDCG、faithfulness、correctness、citation completeness/validity、拒答混淆矩阵、ACL 硬门禁、延迟和成本。

### 60. 引用为什么不能只返回 URL？

URL 可能是错误版本、越权页面或不能支持具体 claim。引用应绑定 document/version/span/hash，并能证明该证据进入本次 context；返回前按当前 identity 再授权。

### 61. Agent 与工作流怎么选？

路径稳定、合规严格、失败代价高时优先确定性工作流。需要对开放问题选择只读工具时可引入 Agent，但必须有状态机、预算和 policy。多 Agent 只有在角色并行或权限隔离收益超过通信与错误放大成本时才采用。

### 62. Memory 应该保存什么？

会话上下文、工作记忆、长期用户偏好、知识库和业务真相分开。模型摘要可压缩上下文，但不能成为任务状态、余额、审批或权限的唯一事实。长期写入需要来源、版本、隐私、过期和删除策略。

### 63. Tool 调用怎样保证可靠？

Tool 合同包含 schema、版本、身份、权限、副作用等级、幂等键、timeout、最大返回、审计和错误分类。Runtime 保存事件和状态，在模型或 Tool timeout 时进入明确 UNKNOWN/failed 状态；高风险动作需要 preview、人工审批和确定性 executor。

### 64. 如何防 prompt injection？

把用户、文档、日志和 Tool 输出视为不可信数据；系统指令与数据分离；检索前 ACL、context 最小化、结构化输出、敏感检查、Tool allowlist、最小权限、审计和 kill switch 共同防护。单纯字符串清洗不够。

## 八、系统设计

### 65. 系统设计第一步是什么？

先澄清用户、核心流程、规模、SLO、重复/顺序语义、保留、地域、合规、成本和非目标。未澄清就画组件，会让后续选型没有判断标准。

### 66. 容量估算有什么用？

它把模糊的“高并发”转成 QPS、扇出、in-flight、分区、连接和存储量级，帮助暴露瓶颈与敏感变量。估算不是生产事实，要注明输入、公式和误差，并用真实负载校准。

### 67. 如何确定数据真相？

为每类状态指定唯一权威来源，缓存和事件只是派生或传输。再定义读一致性、写入原子边界、幂等、状态机、版本和审计。没有真相源，故障恢复会在多个不一致副本间猜测。

### 68. 系统设计怎样讨论故障？

对每个依赖回答：故障如何检测、用户看到什么、是否继续接收、状态如何保存、怎样止血、如何恢复、怎样验证数据正确。只说“主从、重试、熔断”而没有时间线和状态，仍不完整。

### 69. 流量十倍时为什么不能只说加机器？

瓶颈可能在数据库写、索引、Kafka 分区、连接池、Provider 配额、出口网络或单租户热点。先用指标定位，再选择批量、分区、隔离、异步归档或扩容；扩容 Worker 若下游容量不变只会放大故障。

### 70. 如何结束一个系统设计回答？

回顾需求是否满足，列出最大风险、未验证假设、成本和阶段演进；给出负载、故障、安全与正确性验证计划。明确哪些数字是目标，哪些已经实测。

## 九、事实边界必问

### 71. 你实际做了什么？

按“自己实现、自己设计、课程已有、尚未完成”回答，并能打开对应代码、SQL、实验或 ADR。团队方案不等于个人贡献，课程项目不等于实习经历。

### 72. 这个数字怎么来的？

回答环境、版本、输入、负载模型、统计口径、原始输出和限制。缺任一关键项时主动降级措辞或删除数字。

### 73. 哪部分你最没有把握？

指出具体未验证假设和下一步实验，通常比泛泛说“都还可以”更可信。例如 Kafka runtime、Provider UNKNOWN 故障注入或 RAG 真实模型评测仍 Pending。

### 74. 如果重新做一次会改什么？

用现有证据说明一次具体修订：更早定义状态机、缩短事务、隔离重试预算、增加数据正确性查询、先做 baseline 或收紧 Agent 权限。不要为显得反思而虚构事故。
