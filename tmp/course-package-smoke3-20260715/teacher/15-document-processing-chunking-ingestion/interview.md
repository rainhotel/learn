# 第 15 章面试追问

## 1. 为什么文档 ingestion 不能只做成同步上传接口？

解析、OCR、切分和索引耗时与资源波动大，还涉及版本、重试、删除和外部依赖。同步请求容易超时且无法表达部分状态。更合理的是同步鉴权/验参/幂等受理，异步状态机执行，提供状态查询和最终激活语义。

## 2. PDF 有文本层，为什么提取结果仍可能错误？

PDF 保存页面绘制指令，不保证语义阅读顺序。双栏、浮动框、页眉页脚、表格和字符定位都会导致文本顺序错乱；部分页面还可能只有图片，所以要逐页检测并保留坐标和 warnings。

## 3. 何时启用 OCR？

按页检测文本覆盖、字符密度和图像占比后决定，对扫描或低质量文本层页面启用。OCR 输出必须保留引擎/语言/预处理版本、置信度、坐标和原图引用；关键数字还要规则或人工复核。

## 4. 为什么不能把所有文档统一切成固定 500 字？

字符数不等于 token；固定窗口可能切断标题、表格、代码和步骤。chunk 大小还与查询、Embedding、上下文预算和引用粒度相关，应该结构优先并通过固定评测集做消融，而不是给出通用最优常数。

## 5. overlap 越大召回越好吗？

不一定。overlap 可能保留边界上下文，也会产生重复召回、挤占 context、提高存储和成本，并让引用重复。是否启用应看任务评测和失败样本。

## 6. Chunk ID 如何设计？

应同时保留 document/version、strategy/tokenizer version、ordinal、source node/anchor 和 content hash。不要只依赖 ordinal，也不要承诺编辑文档后所有 ID 永远稳定；用 lineage 表达新旧对应关系更诚实。

## 7. ACL 应该在检索前还是生成后过滤？

必须在检索/上下文构建前实施，使越权 chunk 不进入模型。答案后过滤已经造成数据暴露。授权系统异常时 fail closed，并用低延迟缓存或 policy snapshot 优化，而不是跳过检查。

## 8. 如何做到更新时用户不看到新旧内容混合？

在独立 generation 中构建新版本，完成数量、ACL、hash 和质量校验后，原子切 active pointer。查询只读 active generation。旧 generation 延迟回收，构建失败时旧版本继续服务。

## 9. 数据源删除后，删数据库记录够吗？

不够。还要处理 chunk、Embedding、关键词/向量索引、缓存、摘要、原始/规范产物和副本，并考虑法务保留。删除是有状态的异步工作流，需要 tombstone、重试、对账和完成证明。

## 10. 消息重复导致同一文档解析两次怎么办？

至少一次投递是常态。以 tenant/document version/stage/algorithmVersion 做幂等键和数据库唯一约束；产物按 hash 写临时位置，提交 manifest。重复消费者读取既有产物并返回同一结果。

## 11. Parser 调用超时后可以直接重试吗？

先判断是否可能产生远端产物。如果结果 UNKNOWN，应查询 job/artifact hash；确认未发生或幂等写安全后再重试。无界重试可能重复占用昂贵 OCR/GPU 资源并造成恢复风暴。

## 12. Java 与 Python 在 ingestion 中如何分工？

语言不是边界本身。Java 可负责可靠控制面和企业集成；OCR/版面模型可能由 Python/GPU worker 执行。关键是 schema、身份、ACL、timeout、幂等、审计和状态由确定性控制面约束，模型/worker 不能自行激活或越权。

## 13. 如何判断解析器升级没有退化？

对固定 golden corpus 并行运行新旧版本，比较页/节点/表格、关键短语、warnings、资源消耗、chunk 差异，再运行端到端检索与引用回归。高风险差异人工复核，未通过不切 generation。

## 14. Ingestion 最重要的监控是什么？

没有单一指标。要同时看端到端 freshness、stage queue age、失败类别、资源饱和、解析结构质量、chunk 分布、ACL 缺失、active manifest 对账和 deletion lag。任务成功率不能代替数据正确性。

## 15. 你如何在简历中描述这个项目？

分别写清设计、实现和实测。只有真实运行并保存环境、语料、版本和原始结果后，才能写支持格式、吞吐、成功率或延迟数字；本章当前只有设计稿，不能声称已验证生产能力。
