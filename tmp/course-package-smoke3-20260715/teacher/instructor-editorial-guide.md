# 教师、编辑与发布规范

## 1. 目标

确保不同章节、讲师和版本保持一致：内容可教、实验可复核、答案可评分、引用可追溯、状态不夸大。

## 2. 授课前准备

讲师必须完成：

- 阅读章节 README、lesson、project、lab、exercises、answers、interview、teach-back、sources。
- 核对章节状态和所有 Pending，不在课堂上口头扩写为已验证。
- 在固定环境重新运行核心实验；不能运行时准备原始失败记录和替代演示。
- 确认示例数据脱敏、Secret 不在代码/截图/日志中。
- 准备一个正确路径、一个常见错误和一个真实边界。

## 3. 课程交付节奏

### 45-60 分钟标准课

```text
5 分钟：业务问题和学习目标
15 分钟：机制与反例
15 分钟：实验/代码/证据
10 分钟：NotifyFlow 项目应用
10 分钟：练习、面试追问和总结
```

深入章节拆成原理课、实验课和项目答辩课，不为了“单节讲完”压缩故障和证据。

## 4. 答案解锁

- 学习者先提交自己的答案、实验假设或设计图。
- 教师先追问机制和边界，再开放 `answers.md`。
- 参考答案是评分锚点，不是唯一措辞。
- 需要环境的题目必须区分“设计正确”和“运行验证”。
- 学习者复制答案但不能解释反例，不算完成。

## 5. 评分校准

优先评分：

1. 是否理解机制和适用条件。
2. 是否能映射到 NotifyFlow。
3. 是否给出失败路径和数据正确性。
4. 是否保留原始证据和限制。
5. 是否能 Teach-back 并回答追问。

常见扣分：

- 只背定义，无业务状态和反例。
- 只给 YAML/代码，不解释机制和故障。
- 静态检查冒充运行验证。
- 模型/本地数字冒充线上数据。
- Agent 直接执行高风险动作。

## 6. 实验证据审核

每个 Verified 实验至少包含：

```text
date
OS/JDK/framework/component versions
hardware/container resources
source commit or file hash
input/workload
command
raw stdout/stderr
assertions
failure timeline
data correctness
conclusion and limits
```

评审顺序：先确认运行了正确版本和正确代码，再看测试是否覆盖要求，最后判断结论是否超出证据。

## 7. 演示失败处理

现场失败时：

- 不立即修改全局机器配置或删除数据。
- 记录错误、时间和环境，区分代码失败、依赖失败和权限失败。
- 使用已保存的真实证据解释预期，但明确当前演示没有通过。
- 课后修复并重新运行，更新 journal 和章节状态。

## 8. 统一术语

| 术语 | 课程定义 |
|---|---|
| task | NotifyFlow 的业务任务，是最终状态的聚合根 |
| attempt | 一次 Provider/Tool 执行尝试，可处于 UNKNOWN |
| event | 状态变化或待传播事实，使用 eventId |
| Outbox | 与业务状态同事务写入的待发布事件 |
| Inbox | 消费端已处理事件或幂等记录 |
| DLT/DLQ | 达到处理策略终点后的隔离记录，不等于问题解决 |
| UNKNOWN | 副作用结果不确定，禁止普通重试，需对账 |
| replay | 对历史事件/任务的受控重执行，需要 preview/审批 |
| lease | 有期限、可续约的所有权声明 |
| fencing token | 单调版本，用于拒绝旧 owner 的陈旧写 |
| SLI/SLO/SLA | 指标/内部目标/外部承诺，不能混用 |
| Lab Verified | 指定版本真实运行并保存证据 |
| Agent Runtime | 管理模型、状态、工具、权限、预算和恢复的确定性系统 |

首次出现英文术语时给出中文解释；后续保持同一拼写和大小写。

## 9. 写作风格

- 先写为什么重要和真实问题，再写机制。
- 使用短段落、短列表和明确标题。
- 每个正向做法至少配一个失败反例或边界。
- “总是、绝对、零丢失、零停机、exactly-once”必须有严格条件，否则避免使用。
- 参数和代码块注明是示意、草案还是已验证实现。
- 不用“简单来说”掩盖复杂取舍，不用营销词替代证据。

## 10. 代码和命令规范

- Java 主线使用 Java 21，除非章节明确比较其他版本。
- Maven 使用 `mvn.cmd` 或 wrapper；Node 工具遵循仓库 lockfile。
- PowerShell 命令适配 Windows，不直接复制 Bash 指令。
- 代码示例提供 package/import/错误处理边界，避免只能阅读不能运行的片段。
- 真实实验编译产物写入仓库 `tmp/`，课程源码目录保持干净。
- Secret、token、租户 ID、用户 payload 不进入 Git 或课程截图。

## 11. 仓库结构

```text
course/
  README.md
  product-spec.md
  dependency-map.md
  student-workbook.md
  job-readiness-pack.md
  instructor-editorial-guide.md
  NN-topic-slug/
    README.md
    lesson.md
    project-application.md
    exercises.md
    answers.md
    interview.md
    teach-back.md
    sources.md
    lab/
```

章节编号表达课程顺序；目录 slug 使用小写连字符；内容文件名保持 ASCII。

## 12. 版本策略

课程产品版本：

- `0.x`：章节和实验仍在制作，允许结构变化。
- `1.0`：核心承诺、作品包和求职门禁完成。
- patch：错字、链接、解释和不改变作业的修正。
- minor：新增章节、实验或兼容交付物。
- major：学习路径、核心项目或发布承诺变化。

每章在 README 记录资料日期、固定技术版本、当前状态和变更摘要。实验升级版本后必须重新验证，不沿用旧输出。

## 13. 引用与版权

- 优先使用官方文档、规范、JEP、论文和厂商公开指南。
- `sources.md` 记录标题、URL、访问/核验日期、使用结论和边界。
- 不大段复制书籍、付费课程、博客和面试题库正文。
- 图和表尽量自行重绘并标注“依据/改编自”来源。
- 代码示例若来自第三方，核对许可证并保留声明。
- 招聘 JD 只保存完成研究所需的短摘录和链接，不批量转载全文。

## 14. AI 生成内容审核

AI 草稿必须经过：

1. 一手资料核验。
2. 术语和版本检查。
3. 代码/公式静态审阅。
4. 实验运行或明确 Pending。
5. 版权、隐私和经历真实性检查。
6. 学习者 Teach-back 和陌生读者反馈。

AI 不能决定最终项目事实、实验通过、简历数字和高风险操作权限。

## 15. 发布清单

### 内容

- 八件套齐全，链接有效。
- 目标、先修、退出标准和边界清晰。
- 练习与答案可以评分。
- 面试和 Teach-back 覆盖真实追问。

### 技术

- 版本固定，命令可复制。
- 核心实验在干净环境复现。
- 故障和数据正确性有证据。
- 代码/镜像/依赖无 Secret 和明显许可问题。

### 教学

- 至少一次真实学习者作业。
- 至少一次 15 分钟 Teach-back。
- 根据问题修订讲义、答案和实验。

### 销售与求职

- 不承诺 offer、薪资、固定 QPS 或准确率。
- 产品状态与实际完成度一致。
- 简历表述可追溯到事实台账或独立项目证据。
- 当前 JD 结论有日期、样本和来源。

全部通过后才可从 Release Candidate 进入 Released。
