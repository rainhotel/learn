# 面试追问与表达训练

## 使用方法

每道题按三层回答：

1. 30 秒结论。
2. 2 分钟机制。
3. 项目场景、失败路径和替代方案。

不要只背“Spring 事务失效的八种场景”。先判断调用链、代理、传播、异常和资源边界。

## 一、基础层

### 1. `@Transactional` 的原理是什么？

回答要点：

- 注解是事务元数据。
- Spring 通过 AOP 代理拦截匹配的方法调用。
- `TransactionInterceptor` 根据属性使用事务管理器获取或加入事务。
- 方法正常返回时尝试提交，异常退出时依据回滚规则处理。

追问：如果对象是你自己 `new` 出来的呢？

回答：不由 Spring 管理，通常没有 Spring 创建的事务代理，因此注解不会自动生效。

### 2. Spring 事务什么时候会失效？

推荐框架：

1. Bean 是否被容器管理。
2. 事务基础设施是否启用、事务管理器是否正确。
3. 调用是否经过代理，方法是否可被当前代理增强。
4. 异常是否离开代理边界并匹配回滚规则。
5. 是否发生线程切换或操作了事务管理器不能协调的外部资源。

### 3. 为什么同类调用不生效？

回答：外部调用进入代理后，目标对象内部的 `this.method()` 直接调用目标方法，没有再次经过代理，事务拦截器无法运行。JDK 与 CGLIB 代理模式都有这个问题。

### 4. 检查异常会回滚吗？

回答：默认不自动回滚；`RuntimeException` 和 `Error` 默认回滚。可用类型安全的 `rollbackFor` 配置，但应该先定义异常语义并写集成测试。

### 5. `readOnly = true` 有什么作用？

回答：它是传递给事务基础设施和底层资源的只读语义/优化提示，具体效果依赖事务管理器和数据库，不能当作通用写保护或安全权限。

## 二、传播与异常层

### 6. `REQUIRED` 和 `REQUIRES_NEW` 的区别？

回答要点：

- `REQUIRED` 加入现有事务或新建事务，多个逻辑范围通常共享物理事务。
- `REQUIRES_NEW` 挂起外层资源并创建独立物理事务，可独立提交。
- 新事务通常需要额外连接，可能引发连接池耗尽。
- 选择依据是业务原子性，不是哪个“更强”。

### 7. 什么是 `UnexpectedRollbackException`？

回答：内层 `REQUIRED` 参与共享物理事务并将其标记为 rollback-only，外层即使捕获异常并正常返回，也无法真正提交。Spring 在外层提交点抛出该异常，防止调用者误认为提交成功。

追问：如何修复？

回答：先确认业务是否应该整体回滚。通常不要吞异常；可以调整异常传播或拆分事务边界。不能为了消除异常就机械改成 `REQUIRES_NEW`。

### 8. `NESTED` 是独立事务吗？

回答：通常不是。它一般在一个物理 JDBC 事务中使用 Savepoint，局部可以回滚到保存点，但外层最终回滚仍会撤销整个物理事务。

### 9. 事务方法捕获异常会怎样？

回答分两类：

- 如果异常没有导致 rollback-only 且方法正常返回，事务可能提交。
- 如果内层或底层已标记 rollback-only，外层正常返回仍会在提交点回滚并可能得到 `UnexpectedRollbackException`。

## 三、代理与线程层

### 10. JDK 代理和 CGLIB 如何选择？

回答：核心框架通常在目标实现接口时可使用 JDK 代理，否则使用类代理；配置和 Spring Boot 默认值也可能影响选择。面试重点应落在可代理方法、`final/private` 限制和外部调用边界，而不是死记某个版本的默认代理类。

### 11. `private` 方法加事务为什么不可靠？

回答：代理需要拦截可匹配的方法调用；类代理无法覆盖 `private` 方法，外部也不能通过代理调用它。应把事务放在清晰的服务入口，而不是私有工具方法。

### 12. 新线程会继承事务吗？

回答：传统事务通常使用线程绑定资源，新线程没有原线程的事务上下文。异步处理应在新线程中建立独立事务，并通过已提交消息或任务传递工作。

### 13. `@Async` 和 `@Transactional` 同时使用要注意什么？

回答：要确认哪个代理先接收调用以及事务实际在哪个线程建立。不要假设调用方事务传播到异步线程。通常由异步入口在执行线程中调用另一个事务服务，边界最清楚。

## 四、项目与系统设计层

### 14. 为什么不能在事务里调用短信供应商？

回答：数据库回滚不能撤销短信；网络延迟会延长连接和锁占用；超时可能是结果未知而非失败。应该用短事务创建任务与 Outbox，事务外调用供应商，再用短事务确认结果。

### 15. 数据库提交成功但 MQ 没发出去怎么办？

回答：任务和 Outbox 事件在同一数据库事务中写入。后台发布器持续扫描未发布事件并重试。因为发送成功和标记成功不能原子完成，所以允许重复发布，消费者幂等。

### 16. MQ 发成功但数据库标记失败怎么办？

回答：恢复后会重复发送。使用 event id、业务幂等键和消费者去重，使重复消息不产生重复业务效果。

### 17. 供应商超时但可能成功怎么办？

回答：进入 `UNKNOWN`，使用稳定幂等键、供应商请求 id、状态查询、回调和对账确认。没有确认协议时，重试必须经过业务风险评估并保留人工补偿入口。

### 18. Agent 调用创建工单工具，如何防止重复？

回答要点：

- Tool invocation id 与业务幂等键。
- 执行状态持久化。
- 工具侧幂等接口或查询接口。
- 超时进入结果未知，而不是让模型无限重试。
- 租户权限、参数校验、人工审批和审计。

## 五、故障题

### 19. 线上突然出现大量 `UnexpectedRollbackException`，怎么排查？

1. 找完整异常链和首个业务异常，而不是只看提交点异常。
2. 确认外层是否捕获了内层异常。
3. 查看内外方法传播行为和实际代理入口。
4. 确认是否共享同一个事务管理器和物理事务。
5. 用最小集成测试复现 rollback-only 路径。
6. 根据业务原子性决定传播异常、拆分事务或独立记录。

### 20. 连接池耗尽，线程都卡在获取连接，最近刚加了审计事务，怎么判断？

1. 查看线程栈、连接池 active/pending 指标。
2. 搜索 `REQUIRES_NEW` 和外层长事务。
3. 估算每个并发请求最多同时占用几条连接。
4. 检查是否持有外层连接等待内层连接。
5. 临时降低并发不是根治；应缩短事务、减少嵌套新事务或改为异步审计。

### 21. 加了 `@Transactional` 仍然插入了一半数据，怎么排查？

检查顺序：

- 对象是否由 Spring 管理。
- 方法是否由外部通过代理调用。
- 异常是否被吞掉或属于检查异常。
- 是否使用了错误的事务管理器/数据源。
- 批处理是否在新线程中。
- 数据是否来自数据库之外的副作用。

## 七、项目表达模板

> 在 NotifyFlow 中，我没有把供应商调用放进数据库事务。创建请求时用一个短事务原子写入任务和 Outbox；发布器至少一次发送消息，消费者通过业务幂等键去重；Worker 先用短事务领取任务，提交后再调用供应商，最后以 owner 和 version 条件更新结果。这样数据库事务只负责可控的本地原子性，跨系统失败通过状态机、幂等和对账恢复。Spring 侧我专门验证了自调用、检查异常、`REQUIRES_NEW` 和 rollback-only，避免只依赖注解表面行为。

## 自测标准

- 不看资料完成 10 道随机题，正确率至少 80%。
- 每题先讲稳定机制，再讲版本差异。
- 每个传播行为回答都必须说明物理事务和连接占用。
- 每个跨系统问题都必须说明重复、结果未知和恢复方式。
