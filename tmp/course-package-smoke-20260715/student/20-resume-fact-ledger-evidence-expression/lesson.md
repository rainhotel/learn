# 第 20 章讲义：把简历变成可验证的事实接口

## 一、简历的四层结构

一份可靠简历同时服务四层读者：

1. 招聘筛选：几秒内确认岗位、方向、时间和关键能力。
2. ATS/检索：通过真实、自然且与 JD 一致的词汇被找到。
3. 技术面试：每个 bullet 都能展开为问题、决策、实现和证据。
4. 背景核验：公司、时间、角色、项目归属和职责边界不冲突。

因此，简历不能直接从“想获得什么岗位”倒推经历。正确链路是：

```text
原始事实
-> 事实台账
-> 证据索引
-> 安全 claim
-> 岗位版本
-> 逐句压力测试
-> 投递反馈与修订
```

## 二、事实类型与不可跨越的边界

### 2.1 四种来源

| source_type | 含义 | 可使用的动词 | 禁止跨越的边界 |
|---|---|---|---|
| internship | 实习中真实参与的工作 | 负责、实现、排查、协助、交付 | 不得加入实习未使用的技术或虚构业务结果 |
| independent_project | 自己独立实现或主导的工程项目 | 设计、实现、验证、部署 | 不得写成公司生产项目 |
| course_lab | 课程实验和确定环境下的运行 | 实验、复现、测得、对比 | 不得写成线上规模或真实客户流量 |
| design_only | 未运行的架构、方案和研究 | 设计、建模、规划、分析 | 不得写实现、上线、优化或验证 |

同一个主题可以同时存在四种来源，但必须分别记录。例如：实习中真实做过 Java 接口维护；独立项目中实现 Outbox；课程实验中测得线程池拒绝数；设计稿中规划 Kubernetes 部署。它们不能拼成一条看似完整的“实习生产成果”。

### 2.2 大烨实习专用边界

创建 `internship-daye` 独立记录组，只从以下材料还原：

- 原始简历、周报、日报、任务单、提交记录和可公开截图。
- 实习期间真实使用的仓库、技术、数据和业务背景。
- 当时的主管或同事可确认的职责。
- 能合法保留且不泄密的材料。

若无法证明 MySQL、Redis、消息队列、RAG、Agent、Docker 或 Kubernetes 在实习中真实使用，则这些技术必须留在 NotifyFlow、Agent 事故助手或其他独立项目中。

## 三、事实台账的数据模型

每一项原始事实至少包含：

```text
fact_id:
source_type:
organization_or_project:
time_range:
business_context:
task_or_problem:
my_role:
my_actions:
team_actions:
technology_actually_used:
result:
metric_definition:
environment:
evidence_refs:
confidentiality:
confidence:
what_i_did_not_do:
allowed_wording:
forbidden_wording:
```

`confidence` 不等于“我感觉是真的”，而是当前证据完整度：

- A：有可复核原始证据，时间、角色、环境和结果完整。
- B：事实确定，有间接材料，但量化或边界不完整。
- C：依赖记忆，需要寻找材料或向相关人确认。
- D：推断、课程设想或无法确认，不进入简历事实句。

## 四、claim 与证据等级

简历 claim 是从一组事实投影出的短句。课程统一采用以下证据等级：

1. AI 草稿或个人理解。
2. 官方资料核验。
3. 代码、配置或脚本静态检查。
4. 确定性模型实验。
5. 本地真实组件运行。
6. 故障注入、时间线和数据正确性验证。
7. 陌生环境复现或他人独立完成。

对简历的应用：

- “了解/研究/设计”：可以来自 2-3 级，但必须使用对应动词。
- “实现”：至少需要代码、提交或可运行制品，不能只凭讲义。
- “验证/测得”：必须有运行环境和原始输出，通常至少第 5 级。
- “稳定支撑/解决线上事故”：必须有真实业务事件与授权范围内的证据。
- 百分比、QPS、P99、错误率等量化结果：至少第 5 级，并保留基线、样本和环境。

证据等级描述 claim 的可信强度，不表示可以泄露公司材料。涉及保密信息时，只保留合法脱敏的元数据和可口头解释的过程。

## 五、从 STAR/CAR 到一条 bullet

STAR 是 Situation、Task、Action、Result；CAR 是 Challenge、Action、Result。简历中不需要写出标签，但要保留因果链。

推荐句式：

```text
在[可公开场景/约束]下，为解决[具体问题]，
使用[真实技术/方法]完成[本人动作]，
通过[证据口径]得到[结果/发现/交付物]。
```

### 5.1 动词必须匹配参与程度

| 实际参与 | 安全动词 |
|---|---|
| 独立完成主要方案和实现 | 设计并实现、主导 |
| 承担明确模块 | 负责、实现、交付 |
| 与他人共同完成 | 参与、协作完成 |
| 只做研究或方案 | 调研、分析、设计 |
| 只在实验环境运行 | 复现、实验验证、测得 |
| 只跟随教程 | 完成练习、复现示例 |

“主导”“从零到一”“负责整体架构”需要能解释决策权、工作比例、协作者和最终责任。仅提交过少量代码不能支撑这些词。

### 5.2 一条 bullet 只承担一个主结论

低质量写法常把十个技术名词、三个动作和两个结果挤在一起。高质量 bullet 选择一个主结论，并允许面试官自然展开：

- 问题与约束是什么？
- 为什么选这个方案？
- 你写了哪些关键代码或文档？
- 如何测试？
- 哪里失败过？
- 结果如何计算？

## 六、量化不等于编造大数字

没有生产流量时，仍可量化可复核工程事实：

- 功能范围：实现多少类状态、接口、工具或故障场景。
- 测试范围：多少个测试、数据集、故障实验和边界案例。
- 性能：固定机器、版本、负载和持续时间下的吞吐与延迟。
- 可靠性：重复、超时、UNKNOWN、重试、恢复和最终一致性结果。
- 质量：回归通过率、引用正确率、检索 Recall、错误分类覆盖。
- 交付：文档、ADR、Dashboard、Runbook、演示和课程章节。

每个数字必须有六元组：

```text
metric_name + definition + baseline + result + environment + raw_evidence
```

“提升 80%”必须能回答：从什么到什么？样本多少？控制了哪些变量？重复几次？谁测的？是否只在本机？如果不能回答，改写为不带百分比的事实。

## 七、三类岗位版本共用一个事实源

### 7.1 Java 后端版

优先展示：Java 21、集合/并发/JMM、Spring、MySQL、Redis、Kafka、事务、幂等、可观测性、JVM、网络与系统设计。

项目 bullet 的顺序通常是：业务链路 -> 数据正确性 -> 异步可靠性 -> 性能/排障 -> 多实例。

### 7.2 Agent 后端版

优先展示：模型网关、SSE、文档 ingestion、混合检索、Rerank、RAG 评测、Tool Schema、状态机、Memory、安全、成本与可观测性。

不能只写“调用大模型 API”。需要说明后端工程问题：超时、取消、流式断线、权限、幂等、引用、拒答、评测和故障恢复。

### 7.3 先进制造数字化版

优先展示：工单/任务/设备或质量数据的可靠处理、可追溯、权限、系统集成、长事务拆分、消息通知、异常恢复、部署和长期运维。

不得为贴合制造业而虚构 MES、PLC、OPC UA、工业协议或真实工厂经验。若只做过领域研究，写“调研/建模”，不要写“负责产线系统”。

### 7.4 版本控制

维护一份事实主简历，不维护三套彼此冲突的事实。岗位版本只允许改变：

- 摘要与目标标题。
- bullet 的选择和排序。
- 与 JD 一致的真实同义词。
- 不影响事实的篇幅压缩。

公司、时间、角色、技术是否使用、结果和数字不能随版本变化。

## 八、ATS 关键词的正确使用

ATS 是不同产品的统称，不存在可以保证通过所有系统的神秘格式。安全策略是可读、可解析、与目标岗位一致：

1. 保存目标 JD 原文和采样日期。
2. 区分 must-have、nice-to-have、业务词和职责动词。
3. 只选择能由正文证据支撑的关键词。
4. 首次出现时使用行业常见全称和缩写，例如 Retrieval-Augmented Generation（RAG）。
5. 将关键词自然放入项目动作和技能，不重复堆砌。
6. 使用清晰标题、标准时间格式和普通文本结构。
7. 导出后重新解析 PDF 文本，确认顺序没有错乱。

关键词矩阵建议字段：

```text
keyword, jd_count, target_role, must_or_nice,
supported_fact_ids, current_evidence, resume_section, gap_action
```

JD 出现了但自己没有的能力进入学习缺口，不进入技能栏。

## 九、各模块写作规则

### 9.1 顶部摘要

应回答：你是谁、主方向、最强证据、目标岗位。应届生通常 2-3 行足够。避免“热爱学习、责任心强、精通各种技术”等无证据自评。

### 9.2 实习经历

按真实组织、职位和时间书写。bullet 优先描述业务场景、本人动作和可证结果。团队系统的整体规模不自动等于个人成果。

### 9.3 独立项目

明确标注“独立工程项目”“个人项目”或“课程项目”。给出代码、文档、演示和实验报告入口。设计稿和真实运行结果分开写。

### 9.4 教育经历

学校、专业、学位、时间必须一致。课程、奖项和排名只有与岗位相关且可核验时保留。不要用课程名称冒充项目经验。

### 9.5 技能栏

技能栏是面试题目录。建议按语言、框架、数据与消息、AI/Agent、工程工具分组。用“熟悉/了解”不能免除追问；更可靠的方式是让正文项目证明技术，再由技能栏做索引。

## 十、简历审计

### 10.1 事实审计

- 公司、项目、时间、角色是否一致？
- 每项技术是否真的在该来源中使用？
- “我”和“团队”的贡献是否拆开？
- 数字是否有定义、环境和原始证据？
- 是否把设计写成实现，把本地写成生产？

### 10.2 技术审计

- 术语、版本和机制是否准确？
- bullet 中的因果关系是否能由实验或事件证明？
- 是否能解释替代方案、失败模式和局限？
- 项目仓库、文档和简历说法是否一致？

### 10.3 可读性与解析审计

- 目标岗位和最强证据是否在上半页？
- 标题、时间、列表层级是否清楚？
- 链接是否可访问且权限正确？
- PDF 能否正常复制、提取文本和搜索关键词？
- 文件名、页数、字体和语言是否适合投递要求？

### 10.4 合规审计

- 是否包含客户、密钥、内部域名、真实业务数据或未公开架构？
- 截图、代码和数据是否有保留与公开权限？
- 是否暴露不必要的身份证号、家庭地址等个人信息？
- 是否夸大职位、雇佣关系、奖项、论文或开源贡献？

## 十一、逐句追问压力测试

对每条 bullet 做六层追问：

1. 复述：这句话准确是什么意思？
2. 归属：哪些是你做的，哪些是团队做的？
3. 实现：关键代码、数据结构、SQL、配置或流程是什么？
4. 取舍：为什么不用另一个方案？
5. 证据：原始数据、环境、日志和计算方法在哪里？
6. 反事实：条件变化、故障发生或规模扩大后会怎样？

每条 claim 标记：

- Green：证据、解释、边界完整。
- Yellow：事实成立但措辞过强、数字不完整或细节需复习。
- Red：无法证明、来源混淆、存在虚构或保密风险。

Red 必须删除或重写；Yellow 必须补证据或降级动词；只有 Green 进入投递版。

## 十二、常见失败模式

- 技术栈包装：把刚学的 Redis/Kafka/RAG 塞进实习经历。
- 名词堆砌：一条 bullet 罗列 Spring Cloud、Redis、MQ、K8s，但没有动作和结果。
- 因果跳跃：做了缓存就宣称性能提升，却没有基线和测量。
- 范围偷换：团队系统 QPS 被写成个人优化成果。
- 环境偷换：本地实验被写成生产稳定性。
- 状态偷换：设计完成被写成上线完成。
- 精通泛化：技能栏写“精通”，却无法解释机制、边界和排障。
- ATS 迷信：隐藏文字、关键词重复或虚假同义词破坏可读性和诚信。

## 十三、学习与投递闭环

```text
每周采样 JD
-> 更新关键词矩阵
-> 选择已有证据
-> 生成岗位版本
-> 事实/技术/解析/合规审计
-> 模拟追问
-> 投递
-> 记录反馈
-> 回写学习章节与证据台账
```

简历不能替代能力建设。关键词频繁出现但无事实支撑时，应回到对应章节完成实验和项目，再更新 claim。
