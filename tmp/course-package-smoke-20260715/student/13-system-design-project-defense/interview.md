# 第 13 章面试追问

## 为什么不能直接“数据库写成功后发 Kafka”？

数据库提交与消息发送是两个资源，任一步失败都会形成不一致。NotifyFlow 使用同事务 Outbox，再由发布器发送；重复发布仍由业务键和消费幂等处理。

## Kafka 能保证通知恰好一次吗？

不能把 Kafka 的 EOS 外推到 MySQL 和外部 Provider。外部副作用仍需要幂等键、状态机、查询/回调、UNKNOWN 对账和审计。

## Redis 挂了怎么办？

先按用途回答。缓存可降级到数据库并保护流量；限流要有本地/网关兜底；短期幂等丢失仍由数据库唯一约束保证。恢复时防止缓存击穿和流量洪峰。

## 连接池和线程池怎么定？

从下游安全并发、服务时间、到达率和 deadline 反推，用 Little's Law 做初估，再通过开放负载验证排队拐点、拒绝率和数据正确性。

## Provider 超时为什么不是失败？

响应丢失时副作用可能已发生。应记录 UNKNOWN，复用幂等键，通过查询、回调或对账收敛，而不是立即产生第二次发送。

## 多实例怎样避免重复领取？

可用数据库 `SKIP LOCKED`、Kafka 分区或 lease；但任何机制仍需业务幂等。涉及旧 owner 写入时增加 fencing token。

## Agent 为什么不能直接修复事故？

模型输出具有不确定性且可能受恶意内容影响。它可以读取授权证据并建议；重放、扩容和配置变更由确定性权限、审批、审计和回滚控制。

## 你实际做了什么？

按事实拆分个人实现、团队已有能力、设计但未实现项和实验 Pending。面试官追问到任何指标时，能指出原始证据、环境和限制。
