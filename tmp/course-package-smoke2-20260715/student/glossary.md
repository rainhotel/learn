# 课程统一术语表

本术语表是《Java 后端与 Agent 工程》课程的统一用词规范。讲义、实验报告、项目文档、简历、面试回答和销售页面出现歧义时，以本文件和对应章节的真实证据为准。

## 1. 使用规则

1. 第一次出现缩写时先写中文或英文全称，例如“服务等级目标（Service Level Objective, SLO）”。
2. 机制、实现、实验和生产结论必须分开。写了设计或代码，不等于运行通过；本地通过，不等于生产成立。
3. 指标必须同时给出环境、版本、数据集/流量、口径、时间窗口和限制。单独的百分比或 QPS 不构成可复核结论。
4. `Pending`、`Lab Verified`、`Release Candidate` 等状态使用英文标准写法，不自造“基本完成”“应该可用”等模糊状态。
5. `Agent`、`Tool`、`Memory`、`RAG` 在课程中是有工程边界的术语，不作为“用了大模型”的营销同义词。
6. “保证”“零丢失”“恰好一次”“生产级”“高并发”等强表达，只有在定义故障模型并提供相称证据时才能使用。

## 2. Java 与并发

| 标准术语 | 课程定义与标准用法 | 易混淆边界 |
|---|---|---|
| Java 内存模型（Java Memory Model, JMM） | 规定线程之间读写共享内存时的可见性、顺序和同步规则。 | 不是 JVM 内存区域划分，也不是堆、栈和方法区的同义词。 |
| 原子性（atomicity） | 一个操作在所讨论的观察边界内不可被看见为部分完成。 | 单次变量读写原子，不代表“读取—计算—写回”复合操作原子。 |
| 可见性（visibility） | 一个线程的写入能否按 JMM 规则被另一个线程观察到。 | 看见新值不等于复合状态一致，也不等于没有竞态。 |
| 有序性（ordering） | 编译器、JIT 和 CPU 重排仍必须满足程序与同步规则允许的观察结果。 | 不是要求机器严格按源码逐行执行。 |
| happens-before | JMM 中保证写入对后续读取可见并建立顺序的关系。 | 它是形式化关系，不是墙钟时间上的“先发生”。 |
| 数据竞争（data race） | 两个线程并发访问同一位置，至少一个为写，且访问之间缺少 happens-before。 | 竞态条件更宽；即使没有 JMM 意义的数据竞争，业务协议仍可能存在竞态。 |
| 竞态条件（race condition） | 结果依赖不可控的执行时序，导致业务或程序行为不稳定。 | 不等同于“线程多”，也不一定只靠加锁解决。 |
| 线程安全（thread safety） | 在声明的并发使用方式和不变量下，组件保持正确。 | 必须说明作用域；“用了 `ConcurrentHashMap`”不能证明整个复合流程线程安全。 |
| 临界区（critical section） | 访问共享可变状态且需要满足同一同步协议的代码区域。 | 临界区越小通常竞争越少，但机械移出慢 I/O 可能引入状态变化窗口。 |
| `synchronized` | 提供互斥和 monitor 进入/退出建立的可见性关系。 | 不是“重量级锁”的固定同义词，也不自动解决跨进程并发。 |
| `volatile` | 对单个变量提供可见性与特定顺序保证，适合标志或不可变快照引用。 | 不保证 `count++`、check-then-act 等复合操作原子。 |
| 安全发布（safe publication） | 通过正确同步、不可变对象、静态初始化等方式，让其他线程看到构造完整的对象。 | 把引用放进普通共享字段不一定是安全发布。 |
| 中断（interrupt） | Java 的协作式取消信号；任务需要检查状态或正确处理 `InterruptedException`。 | 不是强制终止线程；捕获后静默吞掉会破坏取消协议。 |
| 取消（cancellation） | 请求任务停止并让资源、状态和调用方得到一致结果的协议。 | Future 进入取消状态，不证明底层阻塞 I/O 已停止。 |
| 虚拟线程（virtual thread） | Java 21 中降低阻塞式并发线程成本的轻量线程。 | 不增加数据库连接、CPU、供应商配额，也不消除 timeout、限流和背压。 |
| 有界线程池（bounded executor） | 线程数和等待队列都有明确上限的执行资源。 | “线程池存在”不等于容量受控；无界队列可能把过载变成内存和长尾问题。 |
| 拒绝策略（rejection policy） | 线程池饱和后对新任务采取的明确行为。 | 拒绝是过载信号，不应默认静默丢弃；持久化业务事实不能只依赖内存队列。 |
| 背压（backpressure） | 下游或执行资源饱和时，向上游传播减速、拒绝或排队限制。 | 不等同于无限排队；无限排队只是延迟和内存风险后移。 |

课程标准表达：

- 写“在 JDK 21、给定并发度和样本下复现了可见性/拒绝路径”，不写“证明 Java 并发绝对安全”。
- 写“虚拟线程降低该阻塞场景的线程占用成本”，不写“虚拟线程解决高并发”。
- 写“线程池参数受 CPU、连接池、下游配额和延迟预算共同约束”，不写“核心线程数按固定公式设置即可”。

## 3. 数据、消息与可靠性

| 标准术语 | 课程定义与标准用法 | 易混淆边界 |
|---|---|---|
| 事实源（source of truth） | 对某类业务事实拥有最终判定权的持久化系统。NotifyFlow 通常以数据库任务/事件记录为核心事实。 | Redis、搜索索引、向量库和模型上下文通常是派生视图，不应默认成为事实源。 |
| 本地事务（local transaction） | 单个事务管理器范围内满足提交/回滚语义的事务。 | Spring 注解存在不等于代理生效；数据库事务也不自动覆盖 Kafka 或外部 HTTP。 |
| MVCC | 数据库通过多版本记录支持一致性读及并发控制的机制。 | 不代表所有读都无锁，也不代表不会出现写冲突、死锁或业务竞态。 |
| 幂等（idempotency） | 在定义的作用域和保留期内，同一业务请求重复执行不会产生第二个不允许的业务副作用。 | “接口返回相同”不等于幂等；必须定义幂等键、请求摘要、唯一约束、结果复用和过期策略。 |
| 去重（deduplication） | 识别并过滤重复消息、请求或记录。 | 去重是实现幂等的一种手段，不等于端到端幂等；去重窗口过期后重复仍可能出现。 |
| 至少一次（at-least-once） | 消息或动作可能重复，但系统尽力避免永久遗漏。 | 必须与消费者幂等、重试上限、DLT、对账和重放共同讨论。 |
| 至多一次（at-most-once） | 消息或动作最多处理一次，失败时可能丢失。 | 不是“更可靠”，只是用丢失风险换取不重复。 |
| 恰好一次（exactly-once） | 在明确边界和前提内，观察到一次有效结果的语义。 | 课程不把它当端到端营销承诺；Broker 事务语义不能自动覆盖数据库、HTTP Provider 和人的操作。 |
| 事务 Outbox | 在同一本地事务中写业务事实和待发布事件，再由独立发布器投递。 | 它缩小“写库成功、发消息失败”的双写窗口，但仍需要重复发布处理、幂等消费和积压监控。 |
| 重试（retry） | 对被判定为暂时性且可安全重复的操作，在有限次数和预算内再次尝试。 | 不应重试确定性校验错误、权限错误或未知副作用；重试必须有退避、抖动和总预算。 |
| 指数退避（exponential backoff） | 随尝试次数扩大等待时间的重试间隔。 | 单独退避仍可能同步冲击，下游恢复时通常还需要 jitter。 |
| Full Jitter | 在退避上限内随机选择等待时间以打散重试。 | 只能降低同步重试风险，不能修复非幂等副作用或无限重试。 |
| 重试放大（retry amplification） | 多层组件同时重试，使一次故障变成成倍下游请求。 | 应指定唯一重试所有者或严格分配各层预算。 |
| 死信主题（Dead Letter Topic, DLT） | Kafka 语境下保存超过重试上限或无法自动处理记录的主题。 | DLQ/DLT 在产品中可能含义不同；本课程谈 Kafka 时优先写 DLT，并说明原消息、错误和尝试元数据。 |
| 重放（replay） | 从可追溯事实或消息重新驱动处理流程。 | 不是把失败请求原样无审计地再发一次；需权限、范围、preview、幂等、速率限制和结果核对。 |
| 补偿（compensation） | 用新的业务动作抵消已发生副作用，而不是回滚历史。 | 补偿也可能失败，且不保证恢复到物理上完全相同的旧状态。 |
| 对账（reconciliation） | 比较期望事实与实际状态，识别遗漏、重复或长期不收敛记录并修复。 | 不是普通定时重试；它需要独立事实来源、差异分类和可审计决策。 |
| UNKNOWN | 请求方无法判断远端副作用是否已经发生的业务状态。 | timeout 不等于失败；UNKNOWN 不能直接当作可安全重试，需要查询、幂等、回调或对账收敛。 |
| 租约（lease） | 带到期时间的临时所有权，用于多实例领取和故障接管。 | 不是永久锁；暂停、网络分区和时钟问题可能让旧 owner 继续工作。 |
| fencing token | 单调递增的所有权代次，资源端拒绝旧 owner 的过期写入。 | 只有锁服务返回 token 不够，下游写入路径必须实际比较并执行拒绝。 |
| 限流（rate limiting） | 对时间窗口内请求或资源消耗设置上限。 | 不等于并发限制；QPS 相同但服务时间变长时，并发仍会增长。 |
| 并发限制（concurrency limiting） | 限制同时在途的工作数量。 | 不直接控制长期平均速率，通常需要与 rate limit、队列和 deadline 配合。 |
| 熔断（circuit breaker） | 在连续失败或慢调用达到阈值后暂时快速失败，避免继续消耗资源。 | 不等于重试，也不能替代故障根因修复、fallback 和恢复探测。 |
| 降级（degradation/fallback） | 在依赖不可用或预算不足时，使用能力较弱但边界明确的替代路径。 | 必须显式标记，例如 `ranking_mode=FUSION_FALLBACK`，不得伪装成完整链路。 |

NotifyFlow 的标准可靠性表述是：

> 端到端采用至少一次传递、业务幂等、UNKNOWN 状态、有限重试、DLT、对账和受控重放组合；不同边界分别说明，不能笼统宣称“消息绝不丢、绝不重复”。

## 4. 网络、连接池与容量

| 标准术语 | 课程定义与标准用法 | 易混淆边界 |
|---|---|---|
| 超时（timeout） | 某一阶段允许等待的最大时长，超出后调用方结束等待或执行替代策略。 | timeout 描述调用方观察，不自动证明服务端未执行，也不自动停止底层工作。 |
| 截止时间（deadline） | 整个请求剩余预算对应的绝对或可传递终止时间。 | 多层各自设置同样 timeout 会突破总预算；下游 timeout 应受剩余 deadline 约束。 |
| 取连接超时（pool acquire timeout） | 等待从连接池获得可用连接的上限。 | 与建立 TCP 连接超时不同；请求可能尚未发到远端。 |
| 连接超时（connect timeout） | 建立 TCP 连接允许的时间。 | 不覆盖 DNS、连接池等待、TLS、请求发送和响应读取的全部阶段。 |
| TLS 握手超时 | 建立加密会话允许的时间。 | TCP 建连成功不代表 TLS 或应用协议已就绪。 |
| 读取超时（read timeout） | 等待响应数据到达的阶段性上限，具体语义取决于客户端。 | 可能是两次读取间隔，而不是整个响应总时长；SSE/流式响应要单独定义 idle timeout。 |
| 写入超时（write timeout） | 发送请求数据时允许阻塞的上限。 | 写入本地 socket 成功不证明远端已处理业务。 |
| 整体超时（overall timeout） | 从调用开始到最终结果的总时长上限。 | 必须包含排队、DNS、池等待、连接、TLS、重试和响应处理，否则只是局部 timeout。 |
| 连接池（connection pool） | 复用有限数量的数据库、HTTP 或 Redis 等连接，控制建立成本和下游并发。 | 不是越大越好；大池可能把数据库或 Provider 压垮，小池会形成 acquire queue。 |
| 线程池（thread pool） | 调度和复用执行线程的资源池。 | 与连接池不是一回事；线程数量超过连接数量时，更多线程可能只是在等待连接。 |
| 连接泄漏（connection leak） | 借出的连接未在协议要求内归还或因阻塞长期占用。 | “active 很高”不一定泄漏，也可能是下游变慢或流量增长，需要时间线和调用证据。 |
| `TIME_WAIT` | 主动关闭 TCP 连接一侧为处理迟到报文和端口复用安全而保留的状态。 | 不是看到数量多就能判定故障；要结合新建连接率、端口范围、复用和失败指标。 |
| 临时端口耗尽（ephemeral port exhaustion） | 到同一目标建立大量短连接时，本地可用源端口不足。 | 不能只靠扩大端口范围；应检查连接复用、关闭行为、NAT 和请求模式。 |
| 服务时间（service time） | 工作实际占用处理资源的时间。 | 响应时间通常还包含排队和网络等待。 |
| 响应时间/延迟（response time/latency） | 从观察点发出请求到得到结果的耗时。 | 必须说明观察点、成功/失败样本和分位数；平均值不能代表长尾。 |
| 吞吐（throughput） | 单位时间完成的工作量，如 requests/s、tasks/s 或 tokens/s。 | QPS 只是特定请求口径；不同负载、响应长度和成功率下不可直接比较。 |
| Little's Law | 稳态系统中平均在途量 `L = λW`，用于连接、线程和队列容量直觉。 | 依赖稳定口径和近似稳态，不能替代长尾、突发和故障实验。 |
| 开放负载模型（open model） | 到达率独立于系统响应速度，系统慢时仍按目标速率到达。 | 更容易暴露积压和拒绝；不能用封闭模型结果冒充开放流量容量。 |
| 封闭负载模型（closed model） | 固定数量虚拟用户完成一次后再发下一次，系统变慢时到达率自然下降。 | 适合用户循环，但会对过载产生协调遗漏（coordinated omission）风险。 |
| P50/P95/P99 | 延迟分布的分位数。P99 表示约 99% 样本不超过该值。 | 不能说“P99 是最慢请求”；样本量、窗口和直方图配置会影响可信度。 |
| 长尾（tail latency） | 高分位延迟显著高于中位数的现象。 | 不能只看最大值或平均值解释长尾，需要关联排队、GC、锁、I/O 和下游时间线。 |
| 服务等级指标（SLI） | 对可靠性结果的可测量口径，如成功率或 P99 延迟。 | 指标存在不等于目标合理。 |
| 服务等级目标（SLO） | 在时间窗口内对 SLI 的目标。 | 不等于对外合同，也不等于“永不失败”。 |
| 错误预算（error budget） | SLO 允许的未达标空间，用于平衡可靠性和发布速度。 | 不是允许忽略数据正确性、安全或合规错误。 |
| Server-Sent Events（SSE） | 服务端通过单条 HTTP 连接持续向客户端发送事件的单向流。 | 断线重连、事件 ID、重复片段、最终状态查询和取消需要独立协议。 |

## 5. Docker、Kubernetes 与多实例

| 标准术语 | 课程定义与标准用法 | 易混淆边界 |
|---|---|---|
| 镜像（image） | 由只读文件层和运行元数据组成的可分发模板。 | 不是正在运行的进程，也不应包含运行时 Secret。 |
| 容器（container） | 基于镜像启动、带可写层和隔离配置的进程集合。 | 容器共享宿主机内核，不是虚拟机的简单同义词。 |
| namespace | Linux 提供进程、网络、挂载等资源视图隔离的机制。 | 隔离不等于安全边界绝对可靠，还需权限、seccomp、capability 等控制。 |
| cgroup | 对进程组进行资源记账、限制和调度的机制。 | 写了 memory limit 不代表应用能自动适应；JVM、线程池和 HPA 仍需协调。 |
| 镜像层（layer） | 镜像构建中的只读增量文件系统层。 | 构建步骤删除 Secret 不保证旧层没有 Secret；应使用构建 Secret 和供应链检查。 |
| bind mount | 把宿主机指定路径映射进容器。 | 与 Docker 管理的 volume 不同，对宿主路径和权限耦合更强。 |
| volume | 由容器平台管理生命周期和位置的数据卷。 | 不是数据库备份，也不自动提供高可用。 |
| Pod | Kubernetes 最小调度单位，包含一个或多个共享网络和部分存储的容器。 | 不是永久服务器；Pod 可被替换，业务状态不能只放在本地可写层。 |
| Deployment | 管理无状态 Pod 副本、滚动更新和回滚的控制器。 | 不提供稳定网络入口，也不保证应用层优雅停止。 |
| Service | 为一组 Pod 提供稳定发现与四层流量入口的抽象。 | 不等同于应用服务代码，也不自动解决跨区域容灾。 |
| Ingress/Gateway | 将集群外 HTTP 等流量按规则路由到 Service 的入口能力。 | 具体能力取决于控制器实现；资源对象存在不等于入口已可用。 |
| ConfigMap | 保存非敏感配置的 Kubernetes 对象。 | 不适合 Secret；配置更新是否被应用读取取决于挂载和应用机制。 |
| Secret | 保存敏感配置的 Kubernetes 对象及分发机制。 | 默认编码不等于加密；仍需 RBAC、静态加密、轮换和日志脱敏。 |
| readiness probe | 判断实例是否应接收新流量。 | 下游短暂故障可影响就绪，但不要用 liveness 代替流量摘除。 |
| liveness probe | 判断进程是否陷入无法自愈状态并需要重启。 | 把下游失败写进 liveness 可能制造重启风暴。 |
| startup probe | 为慢启动应用提供独立启动检查窗口。 | 不是延长所有请求 timeout，也不替代正确的启动失败处理。 |
| requests/limits | requests 用于调度资源基线，limits 约束容器可使用上限。 | CPU limit 可能引发 throttling，内存超限可能 OOMKill；配置值不是实际容量证明。 |
| 水平自动扩缩（Horizontal Pod Autoscaler, HPA） | 根据指标调整 Pod 副本数。 | 扩容有延迟，且不能突破数据库连接、Kafka 分区或 Provider 配额。 |
| 优雅下线（graceful shutdown） | 摘除流量、停止领取、等待有界在途任务、保存可恢复状态并退出的协议。 | 收到 SIGTERM 不等于已优雅；需要 readiness、`preStop`、termination grace period 和应用逻辑配合。 |
| 多实例（multi-instance） | 同一服务同时运行多个进程/Pod，共同处理请求或任务。 | 不自动等于分布式正确；需要幂等、领取、租约、fencing、限流和共享事实。 |
| 多机分布式（multi-node distributed system） | 组件跨独立故障域运行，面对网络分区、节点失效、延迟和部分成功。 | 在单进程内模拟多个 worker 只能验证部分算法，不证明多机故障语义。 |
| 静态 YAML 检查 | 对资源字段、语法和约束进行离线检查。 | 不能证明镜像可拉取、探针有效、滚动发布成功或集群网络正常。 |

课程标准表达：

- 写“Deployment/YAML 已完成静态检查，集群运行 Pending”，不写“已完成 Kubernetes 部署”。
- 写“在指定 Docker Engine 与 Compose 版本完成本地容器运行”，不写“具备生产容器化能力”。
- 写“单机多进程验证了租约/接管模型的某个场景”，不写“验证了多机容灾”。

## 6. 大语言模型原理与推理

| 标准术语 | 课程定义与标准用法 | 易混淆边界 |
|---|---|---|
| 大语言模型（Large Language Model, LLM） | 基于大量参数和语料训练、按上下文预测 token 分布的模型。 | 不等同于知识库、搜索引擎、Agent 或业务事实源。 |
| tokenizer | 把文本编码为 token ID，并将生成 token 解码回文本的组件。 | 字符数、汉字数和 token 数不能固定换算。 |
| token | 模型词表中的离散处理单位。 | 不等同于“单词”；代码、中文、URL 和 JSON 的切分差异很大。 |
| embedding | 将 token、查询或文档映射到向量空间的表示。 | 向量更近只表示模型空间中的相似，不证明事实正确或权限允许。 |
| Transformer | 以注意力、前馈网络、残差和归一化等模块构成的序列模型架构。 | 不等同于某个具体模型，也不是 RAG 或 Agent 的同义词。 |
| 自注意力（self-attention） | 序列内部位置通过 Query、Key、Value 计算加权信息聚合。 | “关注某词”是简化解释，不能把注意力权重直接当作可靠因果解释。 |
| 因果掩码（causal mask） | 自回归生成时阻止当前位置读取未来 token 的掩码。 | 与权限 ACL、敏感数据遮罩不是同一概念。 |
| 上下文窗口（context window） | 单次模型请求可处理的 token 总范围，通常包含输入和输出预算。 | 能放入不等于能稳定利用；长上下文也有成本、延迟和中间信息丢失问题。 |
| prefill | 一次处理输入上下文并建立 KV cache 的推理阶段。 | 通常影响 TTFT，不能与逐 token decode 吞吐混为一谈。 |
| decode | 在已有上下文上逐 token 生成的推理阶段。 | 单请求输出速度和批量系统吞吐不是同一个指标。 |
| KV cache | 保存历史注意力 Key/Value 以减少后续 decode 重复计算的缓存。 | 降低重复计算但占用显存；不是 RAG 缓存或会话 Memory。 |
| 首 token 时间（Time to First Token, TTFT） | 从请求开始到收到第一个输出 token 的时间。 | 不代表完整回答时间或内容质量。 |
| token 间延迟（inter-token latency） | 流式输出相邻 token 之间的延迟。 | 平均值可能掩盖卡顿；还需观察完整生成和断流。 |
| temperature/top-p/top-k | 调整候选 token 采样分布的参数。 | `temperature=0` 也不保证跨服务、硬件和版本完全确定。 |
| 结构化输出（structured output） | 让模型输出满足明确 schema，并由确定性代码验证。 | 不是只在 prompt 中说“返回 JSON”；仍需解析、校验、错误分类和安全执行。 |
| 幻觉（hallucination） | 输出流畅但缺乏事实支持、与证据矛盾或凭空生成内容。 | 有引用不代表没有幻觉；引用可能无关、越权或不支持具体 claim。 |
| 量化（quantization） | 用更低精度表示权重或激活以降低内存/计算成本。 | 不自动意味着更快，也不应在未评测时宣称质量无损。 |
| 模型版本 | 能唯一确定提供方、模型身份及重要配置的版本信息。 | 同名 API 模型可能后端更新；评测和结论要记录日期、区域和快照条件。 |

## 7. RAG、检索、引用与评测

| 标准术语 | 课程定义与标准用法 | 易混淆边界 |
|---|---|---|
| 检索增强生成（Retrieval-Augmented Generation, RAG） | 先从授权语料检索证据，再将证据提供给模型生成可追溯回答的链路。 | 不是“接了向量数据库”；完整链路还包括 ingestion、版本、ACL、评测、引用、拒答和安全。 |
| ingestion | 将源文档解析、OCR、清洗、规范化、切分、赋元数据、生成索引并发布的可恢复流水线。 | 不是简单文件上传；必须处理版本、幂等、失败重试、删除和权限传播。 |
| 文档（document） | 业务来源及其版本的事实单位。 | 搜索索引中的 chunk 是派生单元，不能取代原文档和版本。 |
| chunk | 从文档切出的最小检索和引用单元，携带稳定 ID、来源、版本、位置、租户和 ACL。 | 固定长度不是唯一切分策略；overlap 增加召回机会也增加重复和成本。 |
| 稀疏检索（sparse retrieval） | 基于词项统计和倒排索引的检索，如 BM25。 | 对错误码、编号、类名和专有名词常有优势，不应因有向量库就删除。 |
| 稠密检索（dense retrieval） | 将查询和 chunk 映射到向量空间后按距离检索。 | 相似度分数跨模型、距离和索引不可直接比较。 |
| 精确向量搜索 | 计算查询与全部候选向量距离并排序。 | 规模增大时成本高，但可作为 ANN 召回评估基线。 |
| 近似最近邻（Approximate Nearest Neighbor, ANN） | 用索引结构换取更低延迟和资源成本的近似向量搜索。 | “近似”意味着需要用精确基线评估召回损失；参数不能凭经验宣称最优。 |
| 混合检索（hybrid retrieval） | 同时使用 sparse、dense 等召回通道，再融合候选。 | 不是简单相加原始分数；需要校准、rank fusion 或路由策略。 |
| 互惠排名融合（Reciprocal Rank Fusion, RRF） | 按各召回列表名次计算融合分数的 rank fusion 方法。 | 它缓解跨通道原始分数不可比，不保证在所有数据集优于单路检索。 |
| rerank | 对有限候选使用更昂贵的相关性模型重新排序。 | 它不能找回首阶段完全漏掉的文档；超时 fallback 必须显式记录。 |
| 过滤（filter） | 按租户、ACL、版本、有效期和业务字段限制候选。 | 权限过滤是安全与正确性边界，不是生成后再删文本的装饰步骤。 |
| context selection | 从检索和 rerank 结果中选择、去重、排序并控制 token 预算的上下文构建。 | top-k 越大不一定越好，可能加入噪声、冲突和无授权内容。 |
| Recall@k | gold 相关项是否出现在前 k 个检索结果中的召回指标。 | 必须定义 gold、相关性粒度和分母；不能直接表示回答正确率。 |
| MRR | 对每个查询第一个相关结果排名倒数求平均。 | 更关心首个命中位置，不完整反映多个相关结果的排序质量。 |
| nDCG | 按位置折损并支持分级相关性的排序指标。 | 依赖可靠的相关性标注；不同 cut-off 的值不可混写。 |
| 引用（citation） | 回答中的具体 claim 到授权 chunk、文档版本和位置的可追溯映射。 | 拼接 URL 或列参考资料不等于引用；引用存在也不证明它支持该 claim。 |
| 引用准确性（citation precision） | 返回引用中实际支持相关 claim 的比例。 | 与“回答里有引用的句子比例”不同。 |
| 引用完整性（citation completeness/recall） | 需要证据支持的 claim 中，具有有效支持引用的比例。 | 不能只统计引用数量。 |
| 忠实性/有据性（faithfulness/groundedness） | 回答是否由提供的证据支持且不与其矛盾。 | 不等同于事实世界中的最终正确性；语料本身可能错误或过期。 |
| 回答正确性（answer correctness） | 回答相对参考事实或专家判定是否正确。 | 与相关性、流畅度和 groundedness 分开评测。 |
| 拒答（abstention/refusal） | 在无证据、证据冲突、越权或高风险条件下明确不作确定回答。 | 不是系统错误；需要评测正确拒答和错误拒答。 |
| 评测集（evaluation dataset） | 包含查询、期望证据/答案、权限、风险类别和版本的冻结样本集合。 | 随意挑几个顺利案例不能代表评测集；训练/调参样本与最终测试集要隔离。 |
| baseline | 在相同数据、环境和口径下作为比较参照的冻结方案。 | 不是“业内平均值”，也不能在每次结果不佳时悄悄更换。 |
| 消融实验（ablation） | 一次移除或替换一个组件，测量其对质量、延迟、成本和安全的影响。 | 多项同时变化无法可靠归因。 |
| 离线评测 | 在冻结语料和数据集上可重复运行的检索、生成与安全评测。 | 不能完全代表真实用户分布和线上交互。 |
| 在线评测 | 在真实或受控线上流量中观察系统、用户和质量代理指标。 | 点赞、引用点击等是代理信号，不直接等于 ground truth。 |
| 回归门禁（regression gate） | 新版本相对冻结 baseline 必须满足的质量、安全、延迟和成本条件。 | 为让发布通过而临时降阈值不留记录，属于破坏门禁。 |
| Prompt injection | 用户、文档或工具结果中的不可信内容试图覆盖系统规则、窃取数据或诱导动作。 | 仅靠一段 system prompt 不能消除；需检索前权限、最小权限、schema、隔离、验证和审计。 |

课程标准表达：

- 写“在冻结评测集、指定模型和索引参数下，Recall@k 相对 baseline 的变化为……”，不写“RAG 准确率提升”。
- 写“关键 claim 可追溯到授权文档版本与 chunk”，不写“有引用所以没有幻觉”。
- 写“向量数据库是可重建索引，数据库文档版本是事实源”，不写“向量库保存全部业务真相”。

## 8. Agent、Tool 与 Memory

| 标准术语 | 课程定义与标准用法 | 易混淆边界 |
|---|---|---|
| 工作流（workflow） | 路径和状态转换主要由确定性代码预先定义的执行流程。 | 有 LLM 节点也仍可能是工作流，不必包装成 Agent。 |
| Agent | 模型在受限候选中参与决定下一步、工具或参数，而 Runtime 约束执行。 | 不是让模型自由循环，也不是聊天接口、RAG 或自动化脚本的统称。 |
| 多 Agent（multi-agent） | 多个角色或模型协作的系统。 | 不是默认升级；会增加通信、状态、成本、延迟和错误传播，必须相对单 Agent/工作流基线评测。 |
| Agent Runtime | 管理状态机、模型调用、Tool、权限、预算、超时、审批、审计、取消和恢复的确定性运行时。 | 模型本身不是 Runtime，也不能成为唯一业务状态存储。 |
| Plan | 模型或代码生成的候选步骤序列。 | 计划不是已执行事实；每步仍需授权、验证和状态迁移。 |
| Tool | 由版本化 schema、权限、timeout、幂等、side effect 等级和审计合同约束的外部能力。 | 不是只注册一个函数名；模型生成的参数不能绕过服务层校验。 |
| Tool proposal/call | 模型提出的工具和参数请求。 | 不等于工具已执行或成功；课程文档应分别记录 proposed、authorized、executed、verified。 |
| Tool execution | 确定性执行器完成授权、幂等检查、调用、结果校验和审计的过程。 | HTTP 200 也不自动等于业务成功；timeout 可能进入 UNKNOWN。 |
| 副作用（side effect） | 改变外部可观察业务状态的动作，如重放、写库、扩容或修改权限。 | 查询通常为只读，但高成本查询、敏感读取和跨租户读取仍需权限和预算。 |
| 只读默认（read-only by default） | Incident Agent 默认只查询时间线、日志、Runbook 并生成带证据建议。 | “只读”不代表无风险；仍需 ACL、脱敏、速率限制和审计。 |
| 人工在环（Human-in-the-loop, HITL） | 在高风险或不确定节点由有权限的人审批、修正或接管。 | 不是把责任简单转给用户；系统必须提供证据、差异、风险和可撤销范围。 |
| preview/approval request | 对高风险动作生成的可审阅计划和审批请求。 | 不是动作已执行；审批后也应由确定性控制面执行并复核结果。 |
| checkpoint | 可持久化的运行状态快照，用于崩溃后从明确边界恢复。 | 不是只保存聊天文本；需包含状态、版本、步骤、工具调用引用和并发控制信息。 |
| Working memory | 当前 run 的计划、步骤和工具结果引用，通常有 TTL。 | 不是永久知识库，也不能作为订单、通知或审批的事实源。 |
| Episodic memory | 从历史 run 提炼的经验或摘要。 | 摘要可能丢失约束或被污染，写入和召回必须有来源、版本和评测。 |
| Semantic/knowledge memory | 可长期检索的知识内容，通常由受控 RAG 语料实现。 | 不等于模型参数，也不应混入未授权会话或 Secret。 |
| Business state | 订单、通知任务、审批和工具执行等必须持久化的业务事实。 | 不能只放在 prompt、聊天历史或向量库。 |
| reflection/critic | 让模型复查或批评中间结果的模式。 | 可能修复错误，也可能增加成本和自信错误；必须通过消融评测决定是否启用。 |
| 停止条件（stop condition） | 最大步骤、token、成本、工具次数、墙钟 deadline、取消、权限拒绝或人工接管等硬边界。 | “模型认为完成”不是唯一停止条件。 |
| 控制面（control plane） | 管理策略、审批、重放、扩缩容、权限和恢复操作的确定性系统。 | Agent 建议不等于控制面决定；高风险副作用不得由模型文本直接触发。 |
| 数据面（data plane） | 承载正常请求、消息和任务实际处理的运行路径。 | 控制面恢复操作应与数据面流量隔离并限速。 |
| confidence | 系统或模型给出的置信提示。 | 不默认是经过校准的真实正确概率，不能单凭高 confidence 自动执行高风险动作。 |

NotifyFlow Incident Agent 的标准边界是：

> Agent 负责授权范围内的证据检索、异常聚类、摘要、假设和建议；重放、清队列、扩缩容、回滚和权限变更必须经过 preview、审批、确定性执行与审计。

## 9. 证据、事实与实验

| 标准术语 | 课程定义与标准用法 | 可以证明什么 | 不能证明什么 |
|---|---|---|---|
| 事实（fact） | 可由经历记录、代码、日志、合同或其他可靠材料核对的真实事项。 | 某项工作或结果确实发生。 | 不自动证明因果、个人贡献或可迁移能力。 |
| 主张（claim） | 在讲义、简历、答辩或销售页中希望读者相信的陈述。 | 定义需要哪些证据。 | 主张本身不是证据。 |
| 证据（evidence） | 能直接支持特定主张且可复核的材料。 | 在其环境和范围内支持结论。 | 不能越过证据边界外推到生产、其他数据或个人经历。 |
| 设计（design） | 架构、状态机、接口、DDL、实验方案或风险分析。 | 已理解问题并形成可评审方案。 | 不证明已实现、已运行或达到指标。 |
| 实现（implemented） | 代码、配置或脚本已经落盘。 | 某方案被编码。 | 不证明可编译、可启动、正确或可复现。 |
| 静态检查（static check） | 对源码、配置、语法、类型或结构进行不启动目标基础设施的检查。 | 文件满足该检查器覆盖的规则。 | 不证明真实组件行为、网络、权限、性能或故障恢复。 |
| 确定性模型实验（deterministic model experiment） | 用受控代码模拟容量、状态机或算法结果。 | 在模型假设下逻辑和趋势可复现。 | 不证明真实 Redis、Kafka、Kubernetes 或网络运行行为。 |
| 本地真实组件实验 | 在记录版本的真实数据库、中间件、JVM、容器或模型服务上运行。 | 该环境、数据和命令下观察到结果。 | 不自动证明生产规模、高可用、多机或长期稳定。 |
| 故障注入 | 主动制造 timeout、拒绝、崩溃、网络异常或数据冲突并记录系统响应。 | 在声明故障模型下恢复路径和数据结果。 | 未覆盖的故障、组合故障和生产条件仍未知。 |
| 原始证据（raw evidence） | 未经过结论化改写的命令、日志、SQL、JFR、指标快照或评测逐例结果。 | 允许他人复核摘要和计算。 | 单份日志不必然解释因果。 |
| 可重复（repeatable） | 同一操作者在相同环境按说明能再次得到可接受范围内结果。 | 本环境过程稳定。 | 不等于陌生环境可复现。 |
| 可复现（reproducible） | 陌生操作者或环境按版本化材料能独立重建并验证结果。 | 证据达到更强外部验证。 | 不等于已完成生产验证。 |
| 相关（correlation） | 两个指标或事件在时间/样本上共同变化。 | 提供排障线索。 | 不单独证明因果。 |
| 因果证据（causal evidence） | 通过对照、单变量实验、时间线或机制验证支持原因与结果关系。 | 对声明条件下的原因提供较强支持。 | 不能无限外推到未测试环境。 |
| 量化结果 | 带环境、口径和原始数据的数字结论。 | 在该条件下的性能、质量或成本观察。 | 无基线不能写“提升”；无重复运行不能写“稳定”。 |

### 9.1 课程证据等级

证据从弱到强统一为：

1. 个人解释或设计稿。
2. 官方文档核验。
3. 源码、配置或脚本静态检查。
4. 确定性模型实验。
5. 本地真实组件运行。
6. 故障注入、时间线和数据正确性验证。
7. 陌生环境复现与学习者独立完成。

简历量化结果至少达到第 5 级并注明环境；课程发布结论应尽量达到第 6-7 级。低等级证据不是“没价值”，但必须使用与其强度匹配的表述。

### 9.2 实习事实与独立项目

| 内容 | 标准写法 | 禁止写法 |
|---|---|---|
| 大烨实习真实完成内容 | 按真实职责、代码、文档和可核验结果写入事实台账。 | 把暑期后学的 MySQL、Redis、MQ、RAG、Agent 迁入实习经历。 |
| NotifyFlow | 写为独立工程化重构/学习项目，并标明个人完成部分和实验状态。 | 暗示为企业生产系统、真实客户系统或实习上线项目。 |
| 本地压测 | 写明机器、JDK/组件版本、数据、负载模型、时长和限制。 | 写成“线上承载 X QPS”“生产性能提升 X%”。 |
| 模拟数据 | 明确写“模型实验”“合成数据”或“故障注入”。 | 包装成真实用户、企业事故或线上监控数据。 |

## 10. 内容与发布状态

状态按门禁单向提升；后续发现证据错误、版权风险或回归失败时可以降级。章节内容完整度、实验状态和课程发布状态应分别记录。

| 标准状态 | 必须满足 | 不代表 |
|---|---|---|
| Research | 研究问题、范围和一手来源已确定。 | 八件套已写完。 |
| Draft | 单章八件套内容初稿齐全，机制、反例和项目应用可评审。 | 实验已经运行或学习者已掌握。 |
| Lab Verified | 指定版本真实运行，命令、环境和原始输出可复核，且结论不超出实验覆盖范围。 | Teach-back、陌生读者和课程发布已经通过。 |
| Teach Pending | 内容/实验可进入教学，但仍等待学习者真实作业、试讲或独立复现。 | 教学效果已经得到验证。 |
| Release Candidate（RC） | 实验、作业和试讲达到门槛，关键反馈已修订，可进入发布审计。 | 已经正式销售或不会再改。 |
| Released | 陌生读者验证、版权/隐私检查、版本归档和发布清单全部完成。 | 承诺 offer、薪资、生产适用或永久无缺陷。 |

辅助标记：

| 标记 | 标准含义 | 使用限制 |
|---|---|---|
| Pending | 某个明确实验、作业、审批或外部验证尚未完成。 | 必须写清待完成对象；不能用“预计通过”替代结果。 |
| Partial Lab | 审计描述：只有部分实验获得证据。 | 不是正式发布状态，不得简写成 `Lab Verified`。 |
| Blocked | 已定位阻塞条件，当前步骤需权限、依赖或外部状态变化才能继续。 | 已完成的设计和零依赖工作仍可推进；阻塞不等于失败。 |
| Failed | 已按记录条件运行且结果未满足预期或门禁。 | 失败结果是有效证据，应保留命令、输出、假设和下一步。 |
| Passed | 某个明确检查或实验满足预先声明的验收条件。 | 必须写范围，例如“`node --check` 通过”；不能省略成“第 09 章全部通过”。 |

当前课程的标准成熟度表述是“内部 Alpha 学习系统：完整课程骨架、部分真实实验、多章教学初稿”。在所有发布门禁完成前，不得称为完整 V1.0 售卖课程。

## 11. 禁止夸大表达与替代表达

| 不应直接使用 | 问题 | 推荐替代表达 |
|---|---|---|
| “精通 Java/Redis/Kafka/K8s/Agent” | 无作用域且难以证实。 | “能够解释并在指定项目中实现……；已完成的实验为……” |
| “高并发系统” | 没有流量、并发、延迟和资源口径。 | “在某环境以开放/封闭模型运行 X 负载，观察到……；生产容量未知。” |
| “生产级/企业级” | 容易把本地学习项目包装成生产事实。 | “按生产关注点设计，已覆盖……；尚未覆盖……；当前为本地工程项目。” |
| “消息零丢失” | 未定义故障边界、保留期和事实核验。 | “在已注入的故障场景中，任务最终由 Outbox/对账收敛，未发现缺失；未覆盖场景仍 Pending。” |
| “恰好一次” | 容易忽略跨数据库、Broker、HTTP 和人的边界。 | “至少一次传递 + 业务幂等 + 对账，在声明边界内实现一次有效副作用。” |
| “timeout 就是失败” | 远端可能已经执行。 | “调用方超时，业务结果进入 UNKNOWN，随后通过查询/回调/对账收敛。” |
| “用了分布式锁所以安全” | 锁过期、旧 owner 和下游写入仍可能冲突。 | “使用租约、owner 与 fencing token，并在资源端拒绝旧代次写入；已验证场景为……” |
| “Docker 是轻量虚拟机” | 忽略共享内核和隔离机制。 | “容器是基于 namespace/cgroup 等机制隔离和限制的进程集合，共享宿主机内核。” |
| “已完成 K8s 部署” | 可能只有 YAML。 | “YAML 静态检查通过；集群创建、镜像拉取、探针、滚动更新和回滚仍 Pending。” |
| “RAG 消除幻觉” | 检索、引用和语料本身都可能错误。 | “RAG 提供可追溯证据，并通过 groundedness、citation 和拒答评测降低无证据回答风险。” |
| “向量相似度高所以答案正确” | 相似不是事实正确或权限正确。 | “该 chunk 在指定 embedding 和距离下排名靠前，仍需 ACL、rerank、引用和答案验证。” |
| “Agent 会自主解决事故” | 隐藏权限、状态和副作用风险。 | “Agent 默认只读检索和生成建议；高风险动作经审批并由确定性控制面执行。” |
| “多 Agent 效果更好” | 未与简单基线比较。 | “在冻结任务集上相对工作流/单 Agent 比较完成率、成本、延迟和失败传播。” |
| “准确率提升 X%” | 指标、基线和统计口径不明。 | “在数据集 D、版本 V、指标 M 下，由 A 到 B 的绝对/相对变化为……，重复运行波动为……” |
| “实验已验证” | 未说明验证对象。 | “JDK 21 下线程池拒绝路径 Lab Verified；数据库、Docker 或多机结论不在该证据范围内。” |
| “保证 offer/薪资/命中原题” | 课程无法控制招聘结果。 | “课程提供能力训练、作品证据和面试反馈闭环，不承诺录用结果。” |

## 12. 写作与答辩句式模板

### 12.1 机制说明

> 在【作用域】内，【机制】通过【关键约束】解决【问题】；它不能解决【边界】，因此还需要【补充机制】。

示例：

> 在任务投递边界内，Outbox 通过同一本地事务写业务事实和待发布事件，缩小数据库与 Kafka 双写窗口；它不能消除重复发布，因此还需要幂等消费、积压监控和对账。

### 12.2 实验结论

> 在【机器/版本/数据/负载】下，按【命令】运行【次数】，观察到【原始结果】；该结果支持【窄结论】，不证明【未覆盖结论】。

### 12.3 Pending 说明

> 当前已完成【设计/实现/静态检查】，真实【组件/故障/学习者】验证为 Pending；验收条件是【条件】，在获得原始证据前不填写【指标或强结论】。

### 12.4 简历项目表达

> 我在独立工程项目【项目名】中负责【个人动作】，使用【机制】处理【问题】；在【环境】完成【证据等级】验证，结果为【可复核指标】，限制是【边界】。

### 12.5 面试纠偏

> 我需要收窄刚才的说法：现有证据只证明【已证明内容】，尚不能证明【过度外推内容】。若继续验证，我会补【实验/数据/故障场景】。
