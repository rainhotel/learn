# 第 22 章项目应用：NotifyFlow 中的数据结构与算法判断

## 1. 项目边界

本文件把算法能力映射到 NotifyFlow 可靠通知平台与 Agent 事故助手，但不声称下列方案已经实现或压测。生产系统首先依赖清晰的数据合同、数据库索引、消息语义和可观测性；算法只有在真实约束下才有价值。

当前状态：方案与实验设计完成，运行验证 Pending。

## 2. 场景地图

| 真实需求 | 候选结构/算法 | 为什么可能适用 | 必须验证的风险 |
|---|---|---|---|
| 合并用户免打扰时间段 | 区间排序与合并 | 得到规范化区间，快速判断可投递时间 | 时区、跨日、闭开边界 |
| 每租户滑动窗口限流 | deque/时间桶 | 维护时间范围内请求状态 | 内存、分布式一致性、时钟 |
| 找出积压最多的 Top K 租户 | 小顶堆 | 扫描统计后保留 K 个最大值 | 数据来源、近似误差、指标基数 |
| DLT case 按风险与年龄调度 | 优先队列 | 组合优先级和等待时间 | 饥饿、公平性、持久化 |
| Agent Tool 依赖执行 | DAG + 拓扑排序 | 发现依赖顺序和环 | Tool 副作用、失败补偿、权限 |
| 事故影响关系遍历 | BFS/DFS | 从服务、租户、任务关系扩展影响面 | 图过大、错误边、租户隔离 |
| 任务按 worker 分片 | 一致性哈希/固定分片 | 减少扩缩容迁移或稳定路由 | 热点、再均衡、fencing |
| 幂等键短期去重 | HashMap/Redis set | 快速查找重复键 | TTL、容量、最终事实来源 |
| 重试时间轮/延迟任务 | 堆、时间轮或 broker 延迟能力 | 按到期时间唤醒 | 持久性、故障恢复、时钟漂移 |

## 3. 案例一：免打扰区间规范化

### 3.1 合同

输入是同一用户、同一时区的一组半开区间 `[start, end)`。输出是排序、无重叠的规范区间。跨日区间需要先拆分或使用带日期的绝对时间，不能含糊地把 `23:00-07:00` 当成普通递增区间。

### 3.2 算法

1. 按开始时间排序，开始相同则按结束时间排序。
2. 维护当前合并区间。
3. 若下一区间开始小于等于当前结束，扩展结束；否则输出当前区间并开始新区间。

排序主导时间复杂度 O(n log n)，合并扫描 O(n)，结果外辅助空间取决于是否允许修改输入。

### 3.3 工程追问

- 相邻 `[09:00,10:00)` 和 `[10:00,11:00)` 是否合并由产品合同决定。
- 时区规则更新和夏令时不能只靠整数分钟表达。
- 如果数据存储在数据库，可能更适合写入时规范化，而不是每次投递重算。

## 4. 案例二：Top K 积压租户

若已有每租户 backlog 统计，扫描 `T` 个租户并维护大小为 `K` 的小顶堆，时间 O(T log K)，空间 O(K)。

这不代表应把 tenantId 做成监控标签。高基数指标会放大时序数量；Top K 更适合作为受控查询或周期报告，并保留统计窗口、数据延迟和采样方法。

测试至少覆盖：`K=0`、`K>T`、并列积压、空租户集、积压值超过 int、比较器溢出。

## 5. 案例三：DLT 公平调度

只按风险分数排序可能让低风险 case 永久饥饿。可定义随等待时间增长的有效优先级：

```text
effective_priority = base_risk + aging_rate * waiting_time
```

直接把随时间变化的值放进普通优先队列会产生问题：队列不会自动重排所有元素。可选方案包括周期重建、分层队列加权轮询、固定时间桶，或把调度交给持久化任务系统。

面试价值不在写出堆，而在识别“动态优先级破坏堆内顺序”这一合同变化。

## 6. 案例四：Agent Tool 依赖 DAG

事故助手可能先查任务时间线，再查 Provider 状态，最后生成只读诊断。若 Tool 计划显式声明依赖，可进行拓扑排序：

- 入度为零的只读 Tool 可并行候选执行。
- 拓扑结果数量少于节点数表示存在环。
- 拓扑合法不代表允许执行；每个节点仍需租户、RBAC、参数 schema 和风险策略校验。
- 有副作用 Tool 不应因为图上“可执行”就自动运行，必须进入确定性审批控制面。

图算法只解决依赖顺序，不解决权限、幂等、超时、补偿和审计。

## 7. 案例五：滑动窗口限流

精确日志窗口可用 deque 保存时间戳，单请求摊还 O(1)，但高 QPS、多租户下内存可能不可接受。时间桶降低内存和操作量，但引入近似误差。分布式场景还需回答：

- 状态放在本机、Redis 还是网关？
- 多实例时如何原子更新？
- 使用客户端还是服务端时间？
- Redis 不可用时 fail-open 还是 fail-closed？
- 热租户如何避免单 key 热点？

因此，面试题中的 deque 解法只是机制原型，不能直接包装成生产级分布式限流。

## 8. 案例六：事故影响图

将任务、消息、Provider、租户和服务建成图后，BFS 可用于回答“从这个失败节点向外若干跳，可能影响哪些实体”。但真实系统必须限制：

- 最大深度、最大节点数和查询超时。
- 每条边的租户权限与来源可信度。
- 图数据版本和事件时间。
- 错误或过期依赖边导致的误报。

Agent 输出应引用原始证据，不能把图遍历到的关联自动陈述为因果。

## 9. 从算法题迁移到工程的五问

1. 数据是否全部在内存，还是需要跨数据库、缓存或消息系统？
2. 输入规模、更新频率、读取频率和延迟目标是什么？
3. 单机结构在多实例下由谁维护一致性和故障恢复？
4. 算法输出出错时会影响可用性、正确性、安全还是成本？
5. 是否有更简单的数据库索引、离线计算或中间件原语？
